🔴 Fix 1 — Routes OCR : auth + rate limit obligatoires

Le danger : les 3 routes /api/ocr/bulletin-situation, /api/ocr/prescription, /api/ocr/generic n'avaient aucune vérification d'authentification. N'importe qui pouvait spammer ces URLs et brûler ta quota Anthropic (~$0.01-$0.05/appel).

Solution : helper centralisé lib/apiAuth.js

Nouveau fichier qui expose 2 fonctions :

  • requireAuth(req) — lit le header Authorization: Bearer ..., vérifie le token via supabase.auth.getUser(), retourne 401 si invalide
  • checkRateLimit(userId, opts) — rate limiter en mémoire Map, défaut 10 requêtes/min/user, retourne 429 + header Retry-After si dépassé

Application sur les 3 routes OCR

// 0.56.20 : protection auth — sans Bearer valide, 401
const authCheck = await requireAuth(req);
if (!authCheck.ok) return authCheck.response;
const { user } = authCheck;

// 0.56.20 : rate limit 10 OCR/min/user
const rate = checkRateLimit(user.id, { maxRequests: 10, windowMs: 60_000 });
if (!rate.ok) return rate.response;

// Seulement maintenant on continue
const apiKey = process.env.ANTHROPIC_API_KEY;
// ...

Côté front : envoi du token Bearer

Les pages /scan/bulletin-situation, /scan/prescription et /scan/ocr récupèrent maintenant le token Supabase et l'envoient dans le header :

const token = (await supabase.auth.getSession())
  .data?.session?.access_token;

const res = await fetch("/api/ocr/bulletin-situation", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    ...(token ? { Authorization: `Bearer ${token}` } : {}),
  },
  body: JSON.stringify({ image_base64: base64, media_type: file.type }),
});

🔴 Fix 2 — Mot de passe retiré des tests publics

Le mot de passe Molotof46! apparaissait dans 2 tests publics sur GitHub :

  • __tests__/v055-12-password-policy.test.js:65-66
  • __tests__/v055-26-security.test.js:32

Ces tests démontraient la validité de la policy de mot de passe et le redact du logger — mais en utilisant un secret réel. N'importe quel bot scannant GitHub pouvait le trouver et l'utiliser pour se connecter à ton compte Supabase.

Fix appliqué : remplacement par des chaînes neutres :

// Avant
checkPassword("Molotof46!Aveho");
redact({ user: "cedric", password: "Molotof46!" });

// Après
checkPassword("CustomP@ss42!Strong");
redact({ user: "cedric", password: "FakeTestPass123!" });

🛡️ Fix 4 — Patch SQL : grants + search_path

Patch supabase/aveho-PATCH-vers-0.56.20.sql à exécuter dans Supabase SQL Editor.

(1) Grant execute sur 21 fonctions oubliées

Ces fonctions étaient appelables côté front mais sans grant execute elles renvoient un 403 permission denied au runtime :

  • mes_etablissements, mes_structures
  • search_patients, search_materiels
  • refresh_medecin_stats
  • auto_rattach_admin_etabs, auto_rattach_admins_to_new_etab
  • ensure_single_active_template, get_consent_validity_days
  • patients_set_updated_at

(2) ALTER FUNCTION ... SET search_path

16 fonctions SECURITY DEFINER sans set search_path sont vulnérables à une attaque par search path injection : un attaquant qui crée un schéma "public" malveillant peut détourner les calls de fonctions.

Le patch boucle sur toutes les fonctions DEFINER de public et applique set search_path = public, pg_temp à celles qui n'en ont pas.

(3) Vérification finale

Le patch termine par un SELECT qui compte les fonctions encore vulnérables après hardening — devrait être 0.
