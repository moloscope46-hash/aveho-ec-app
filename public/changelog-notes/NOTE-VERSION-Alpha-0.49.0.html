AV utilise la table user_notification_preferences existante depuis 0.29. Build clean, 869 tests verts (+25), test runtime validé sur 5 routes.

5 modules + 1 bonus livrés :
🆕 Bonus Badge v0.49.0 cliquable dans la TopBar à côté du logo (caché sur ≤520px) — clic vers /changelog.
AY Composant <MultiEtabSummary /> affiché en tête de /accueil uniquement si l'user a > 1 établissement : grille avec 3 mini-KPIs (patients, DI ouvertes, DI ce mois) + badge "EN COURS" + click pour switcher.

AV Notifications par catégorie

  • Table existante user_notification_preferences (créée en 0.29, étendue en 0.33) avec un champ prefs jsonb
  • Composant <NotifCategories /> dans app/NotifCategories.js
  • 7 catégories avec icône + couleur sémantique + description :
    • 🛠️ DI (rouge)
    • 🛒 Achats (orange)
    • 🔧 Maintenance (teal foncé)
    • 💬 Signalements (teal)
    • 🚚 Transferts (bleu)
    • 🛍️ Commandes (teal foncé)
    • 🛡️ Consentement à renouveler (orange)
  • Toggle iOS-style : pill 38×22 avec rond blanc qui slide. Vert quand activé.
  • Convention : prefs[key] !== false → toutes les catégories sont activées par défaut, seule l'opt-out explicite désactive
  • Persistance : upsert sur { user_id, structure_id, prefs, updated_at } avec onConflict: "user_id" (PK)
  • Rollback en cas d'erreur : si le upsert échoue, le state local revient à l'ancien
  • Toast confirmation "Préférences sauvegardées" qui disparaît après 2.5s
  • Intégration : nouvelle section rétractable dans /profil (entre historique digest et aide)

AD Onboarding par rôle

  • Refactor du tableau monolithique en 3 constantes : BASE_STEPS (3 étapes), ADMIN_STEPS (1 étape), FINAL_STEP
  • Détection rôle via auth.role.nom === "Administrateur" OU auth.can("gerer_roles") (le 2nd couvre les rôles custom avec cette permission)
  • Construction dynamique en tête du composant : 
    const TOUR_STEPS = [
  ...BASE_STEPS,
  ...(isAdmin ? ADMIN_STEPS : []),
  FINAL_STEP,
];
  • Nouvelle étape admin : pointe sur .version-badge et explique "outils admin" (direction, perf SQL, webhooks)
  • Result : user simple → 4 étapes · admin → 5 étapes

AA Migration 8 confirm() vers dialogs.confirm()

  • Script Python de mass-replace ciblé sur 5 pages prioritaires
  • Pattern : 
    // Avant :
if (!confirm(`Supprimer ${x} ?`)) return;
// Après :
if (!await dialogs.confirm({ title: `Supprimer ${x} ?`, variant: "danger" })) return;
  • Import auto ajouté en haut de chaque fichier modifié si pas déjà présent
  • Distribution :
    • /signalements : 1
    • /achats : 5
    • /tags-materiel : 1
    • /etiquettes : 1
    • Total : 8 confirm() migrés
  • Reste à migrer dans les futures versions : /patients, /parametres-rgpd, /ConsentementRGPD, /etablissement/edition, app/crud.js (les plus risqués car nécessitent que les fonctions deviennent async)

Procédure d'application

  1. Aucun SQL à exécuter 🎉
  2. Décompresser le zip par-dessus C:\aveho-ec-app\
  3. Cache + tests + dev (PowerShell) : 
    cd C:\aveho-ec-app
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue
npm install
npm test
npm run dev
    Attendu : 869 tests verts.
  4. Tester :
    • Badge : visible à côté du logo en haut de toutes les pages, "v0.49.0". Clic → /changelog (404 acceptable, on créera la route plus tard)
    • AY : avec un compte rattaché à plusieurs établissements, /accueil affiche en tête une grille avec mini-KPIs par étab. Clic sur un autre étab → switch
    • AC : /transferts → cocher 2-3 lignes → bandeau bleu sticky → export CSV (ou suppression si droit)
    • AV : /profil → section "Catégories de notifications" → toggler une catégorie OFF → recharger → l'état persiste
    • AD : DevTools → effacer localStorage["aveho_onboarding_done"] → relogger en admin → tour à 5 étapes (avec étape "Outils Administrateur"). Idem en user simple → tour à 4 étapes
    • AA : sur /achats, cliquer un bouton "Valider" / "Annuler" → modal stylée ConfirmModal (plus de confirm() natif laid)
