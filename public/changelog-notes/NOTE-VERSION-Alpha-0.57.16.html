🐛 Le bug

Signalé par l'utilisateur : "api siret ne fonctionne plus"

Cause racine : depuis 0.56.21, le hardening sécurité a protégé toutes les routes API avec requireAuth (Bearer token Supabase obligatoire). Mais 7 fichiers caller utilisaient encore fetch() direct au lieu de fetchWithAuth() → toutes ces fonctionnalités renvoyaient 401 'Non authentifié (Bearer token manquant)' en prod.

Pourquoi pas détecté plus tôt : ces routes étaient peu testées en E2E. Les smoke tests internes utilisent volontairement fetch() sans auth pour vérifier le refus 401, donc passaient verts à tort. Aucun test ne vérifiait que les callers utilisaient bien fetchWithAuth.

🔧 Le fix type (répété sur 7 fichiers)

AVANT — fetch direct sans token

// app/SireneSearch.js
import { useState, useEffect, useRef } from "react";

// ...
const res = await fetch(url);   // → 401 Unauthorized en prod depuis 0.56.21
const data = await res.json();

APRÈS — fetchWithAuth qui ajoute Authorization: Bearer

// app/SireneSearch.js
import { useState, useEffect, useRef } from "react";
import { fetchWithAuth } from "../lib/fetchWithAuth";  // 0.57.16

// ...
const res = await fetchWithAuth(url);  // 0.57.16
const data = await res.json();

fetchWithAuth() récupère la session Supabase via supabase.auth.getSession(), extrait le token JWT, et l'ajoute dans le header Authorization: Bearer <token> avant d'appeler fetch().

🛡️ Test anti-régression critique (le plus important)

Pour que ce bug ne revienne jamais, j'ai ajouté un test Vitest qui :

  1. Parcourt récursivement app/ (hors app/api et hors changelog)
  2. Détecte tous les await fetch("/api/...") et await fetch(`/api/...`)
  3. Liste les routes protégées par requireAuth (15 routes actuellement)
  4. FAIL si un fetch() direct pointe vers une route protégée
// __tests__/v057-16-hotfix-fetchwithauth.test.js
function findDirectFetches() {
  const bugs = [];
  const protectedRoutes = getProtectedRoutes();  // routes avec requireAuth
  walk(path.join(projectRoot, "app"));
  // → cherche /await fetch\(["'`]\/api\// dans tous les .js
  // → matche contre les routes protégées (15 actuellement)
  // → renvoie [{file, route}] si bug détecté
  return bugs;
}

it("Aucun fetch() direct vers une route avec requireAuth", () => {
  const bugs = findDirectFetches();
  expect(bugs).toEqual([]);  // ← FAIL si quelqu'un ajoute un fetch oublié
});

Garantie : si tu ajoutes une nouvelle route protégée + un caller, et que tu oublies fetchWithAuth, le test échoue avant même le push.

🤖 Script Python pour automatiser le fix

Le fix manuel sur 7 fichiers aurait pris ~30 min avec risque d'oubli. J'ai utilisé un script Python qui :

  1. Liste les fichiers cassés avec leurs routes appelées
  2. Pour chaque fichier :
    • Ajoute l'import fetchWithAuth après le dernier import existant (si absent)
    • Remplace await fetch("/api/...") par await fetchWithAuth("/api/...")
    • Préserve tous les autres fetch() non-API (ex: APIs externes, /api/version qui n'est PAS protégée)
  3. Fix terminé en 2 secondes

Pattern reproductible pour les futurs hotfixes de masse.

⚠️ Pourquoi ce bug est resté 4 jours en prod

Plusieurs facteurs combinés :

  • Hardening 0.56.21 silencieux : ajouter requireAuth aux routes ne fait pas casser le build, ni les tests Vitest, ni les tests E2E (en mode SMOKE sans auth, les routes renvoient 401 mais c'est ce qui est attendu...)
  • Smoke tests interne appellent les routes sans auth pour vérifier qu'elles refusent → passent verts à tort, masquent le bug
  • Tests E2E ne couvrent pas ces features spécifiques (SireneSearch, OCR, archive prescriptions n'étaient pas dans les 74 tests E2E des 0.57.12-15)
  • Pas de monitoring 401 en prod : sans alerting sur les codes HTTP des routes API, le 401 passe inaperçu

Mitigations pour le futur

  • ✅ Test anti-régression automatique en Vitest (fait dans 0.57.16)
  • 📋 À faire : ajouter monitoring Vercel/Sentry pour alerter sur 401 en prod
  • 📋 À faire : étendre E2E à ces features (SIRET search, OCR upload, archive) une fois Supabase de test configuré
