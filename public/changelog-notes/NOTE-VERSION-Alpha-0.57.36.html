🚨 Le problème : bruteforce login non-limité côté client

Supabase Auth a un rate-limit serveur (visible dans Dashboard → Logs → Auth) mais aucun rate-limit côté client/UI. Conséquences :

  • L'attaquant peut hammer notre page de login avec du credential stuffing (combos email/password leakés)
  • Consomme notre quota d'auth Supabase + crédits facturés
  • Pas de feedback UX : l'attaquant ne sait pas qu'il est rate-limited côté serveur
  • Pas de protection contre l'automation naïve qui n'a pas de logique de retry

Scénarios d'attaque

  • Credential stuffing : un attaquant teste 10 000 combos volés sur d'autres sites → notre page accepte tout
  • Spray attack : un seul email × 1000 passwords courants → notre page accepte tout
  • DoS : 100 emails × 100 passwords par minute → notre quota Supabase explose

2️⃣ Intégration dans app/login/page.js

async function submit() {
  // ✅ Check AVANT de hit Supabase
  const block = checkLoginBlock(email);
  if (block.blocked) {
    throw new Error(`Trop de tentatives. Réessaie dans ${formatBlockTime(block.remainingMs)}.`);
  }

  const { error } = await supabase.auth.signInWithPassword({ email, password: pwd });

  if (error) {
    // ✅ Incrémenter sur échec
    const r = recordFailedLogin(email);
    if (r.blocked) {
      throw new Error(`Bloqué pour ${formatBlockTime(r.remainingMs)}.`);
    }
    // UX : affiche les tentatives restantes si <= 2
    if (r.attemptsLeft <= 2) {
      throw new Error(`${error.message} (${r.attemptsLeft} restante(s))`);
    }
    throw error;
  }

  // ✅ Reset après login réussi
  resetLoginAttempts(email);
}

⚠️ Limites assumées

Ce helper est côté client uniquement. Un attaquant déterminé peut :

  • Vider son localStorage avant chaque tentative
  • Changer d'IP / utiliser un VPN
  • Faire des appels directs à l'API Supabase Auth (qui a son propre rate-limit)

C'est une protection UX + anti-spam basique, le vrai rate-limit reste côté Supabase Auth.

Ça protège effectivement contre :

  • Bruteforce manuel/script naïf qui ne pense pas au clear localStorage
  • Credential stuffing automatisé basique
  • DoS sur notre page (consommation quota Supabase)

🛡️ Bonus : check origin SW handler (defense-in-depth)

Le SW handler CLEAR_USER_CACHE de 0.57.35 ne vérifiait pas l'origin du message envoyeur. Risque exploitable réel quasi-nul (les SW ne reçoivent normalement que des messages same-origin par contrat browser), mais defense-in-depth.

self.addEventListener("message", (event) => {
  if (!event.data || event.data.type !== "CLEAR_USER_CACHE") return;

  // 0.57.36 : check origin defense-in-depth
  if (event.source && event.source.url) {
    try {
      const sourceUrl = new URL(event.source.url);
      const myUrl = new URL(self.location.href);
      if (sourceUrl.origin !== myUrl.origin) {
        console.warn("[SW] Refus message origin différente", sourceUrl.origin);
        return;
      }
    } catch (e) {
      return;  // fail-secure si parsing impossible
    }
  }

  event.waitUntil(/* vide DATA + PAGE caches */);
});

it("Toute page qui appelle signInWithPassword doit avoir rate-limit", () => {
  // Scan toutes les pages sous app/, exception inscription/[token]/ (login auto)

  for (const page of findPages()) {
    const src = fs.readFileSync(page, "utf-8");

      if (!/checkLoginBlock|recordFailedLogin/.test(src)) {
        violations.push(page);
      }

  expect(violations).toEqual([]);
