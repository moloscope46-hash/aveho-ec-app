3. Cron renouvellement

3.1 Fonctionnement

Chaque matin à 7h UTC (9h Paris), pg_cron appelle l'Edge Function send-renouvellement-rappels. La fonction :

  1. Lit v_consents_a_notifier : consentements signés, non archivés, expirant dans les 30 prochains jours, jamais notifiés.
  2. Groupe par structure pour éviter le spam : 1 notif par structure avec compteur.
  3. Envoie en parallèle :
    • Push notification à tous les membres de la structure (tag consent_a_renouveler) via send-push
    • Webhook Teams/Slack si configuré via send-webhook
    • Email HTML brandé au DPO si structures.parametres.dpo_email renseigné
  4. Appelle la RPC mark_consent_notified pour marquer notification_30j_envoyee=true sur tous les IDs traités.
  5. Retourne un JSON résumé : { count, structures, push_sent, webhooks_sent, emails_sent, errors }.

3.2 Email DPO

Template HTML autonome :

  • Header navy avec logo Aveho et eyebrow "RAPPEL DPO — RENOUVELLEMENT RGPD"
  • Salutation + résumé : "X consentements approchent de leur échéance"
  • Tableau détaillé patient/expire le/échéance en couleur (orange ou rouge selon urgence)
  • Bouton CTA "Voir dans Aveho" qui pointe vers /consentements?filter=a_renouveler
  • Footer avec mention sur la modification du paramètre DPO

Note : L'envoi effectif via SendGrid/Resend est à brancher (le code log l'email + compteur pour validation). Voir Reste à faire.

3.3 Anti-doublon

La colonne notification_30j_envoyee évite que le DPO reçoive le même email tous les jours pendant 30 jours d'affilée. Quand un consentement est renouvelé (= nouvelle ligne créée), le nouveau démarre avec notification_30j_envoyee=false et le cycle recommence proprement.

4. Page audit scans QR

4.1 Accès restreint

Réservée aux administrateurs (auth.can("gerer_roles") ou role.systeme === "admin"). Les autres utilisateurs voient un message d'accès refusé.

4.2 KPIs

KPISignification
Total vérificationsNombre total de scans QR effectués sur les consentements de la structure
7 derniers joursTendance récente (activité d'audit)
Valides ✓Hash fournis correspondant au registre
Invalides ✗Tentatives échouées (potentielle altération)

4.3 Tableau et modale

Affichage limité aux 500 plus récentes vérifications. Tableau :

  • Date + relativeTime ("il y a 2h")
  • Patient (ou "Inconnu" si consentement supprimé)
  • Résultat en badge vert/rouge
  • Origine (IP) en monospace
  • Navigateur / OS détectés depuis user-agent par la vue SQL (icônes Tabler)

Modale de détail (clic œil) :

  • Header coloré vert (valide) ou rouge (invalide)
  • Métadonnées complètes : date, patient, signé le, statut, IP, navigateur, OS
  • Hash fourni dans le QR (en monospace, copiable)
  • User-agent complet (raw)
  • Si invalide : encart "Alerte de sécurité" avec causes possibles (copie altérée, lien manipulé, usurpation)
  • Bouton "Voir le consentement" pour rebondir vers /consentements?id=...

4.4 Détection navigateur/OS côté SQL

La vue v_audit_verifications utilise des case when user_agent ilike '%xxx%' pour extraire navigateur (Chrome, Firefox, Safari, Edge) et OS (Windows, macOS, iOS, Android, Linux). Affichage avec icônes ti-brand-*. Évite tout JS côté client pour ce parsing.

5. Durée configurable

5.1 UI dans /parametres

Nouvelle section Conformité RGPD avec icône bouclier navy :

  • Durée de validité : select avec 5 options
    • 1 an (365 jours)
    • 2 ans (730 jours)
    • 3 ans (1095 jours) — recommandé, par défaut
    • 5 ans (1825 jours)
    • 10 ans (3650 jours)
  • Email du DPO : input email avec placeholder
  • Rappel CNIL dans un encart teal informatif

5.2 Stockage

Dans structures.parametres jsonb :

{
  "consent_validite_jours": 1095,
  "dpo_email": "dpo@ehpad-tilleuls.fr",
  ...autres params existants
}

5.3 Utilisation

À chaque ouverture de la modale ConsentementRGPD, on lit structures.parametres.consent_validite_jours. Le calcul de date_expiration utilise cette valeur (au lieu de 3 ans en dur). Si pas configuré, fallback sur 1095 jours.

5.4 Application

S'applique uniquement aux nouveaux consentements signés. Les consentements existants conservent leur date_expiration. C'est volontaire : modifier rétroactivement la durée pourrait invalider des consentements valides ou en valider des expirés, ce qui poserait problème en audit.

6. Patch SQL 0.23.0

Le script aveho-PATCH-vers-0.23.sql (156 lignes) effectue :

  1. ALTER TABLE structures : ajout colonne parametres jsonb default '{}' si pas déjà présent
  2. Backfill : consent_validite_jours = 1095 pour structures qui ne l'ont pas
  3. Fonction helper get_consent_validity_days(uuid) avec fallback 1095
  4. Vue v_consents_a_notifier : enrichie avec collectivite_nom, dpo_email, etablissement_nom, jours_restants
  5. Vue v_audit_verifications : join avec consentement + détection navigateur/OS
  6. RPC mark_consent_notified(consent_ids uuid[]) SECURITY DEFINER

Idempotent (if not exists, create or replace). Rejouable.

10. Procédure d'application

  1. SQL d'abord dans Supabase → SQL Editor → coller aveho-PATCH-vers-0.23.sql → Run.
  2. Vérifier : 
    select id, nom, parametres->>'consent_validite_jours' as validite
from structures;
-- Toutes les structures doivent avoir validite = 1095
  3. Déployer la Edge Function : 
    cd C:\aveho-ec-app
supabase functions deploy send-renouvellement-rappels
  4. Programmer le cron dans Supabase SQL Editor (voir section 7.2)
  5. Décompresser le zip par-dessus C:\aveho-ec-app
  6. npm install + tests + dev : 
    npm install
npm test       # 117 passed
npm run dev
  7. Tester :
    • Aller dans /parametres → vérifier la nouvelle section Conformité RGPD
    • Modifier la durée à 2 ans + saisir un email DPO → Enregistrer
    • Créer un nouveau patient + signer son consentement → vérifier que date_expiration = signature + 730 jours en base
    • Aller dans /consent-verifications → voir l'historique des scans QR
    • Tester le cron manuellement (voir section 7.3)
  8. Pousser sur Vercel.
