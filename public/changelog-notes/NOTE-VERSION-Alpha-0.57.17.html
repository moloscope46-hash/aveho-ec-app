🔒 1. Content-Security-Policy (CSP) — mitigation XSS critique

CSP est la défense la plus efficace contre les XSS côté browser. Aveho l'avait pas → ajouté en mode REPORT-ONLY pour observer sans casser.

12 directives configurées

default-src 'self'                                    # deny by default
script-src 'self' 'unsafe-eval' 'unsafe-inline'       # + Next.js bootstrap
  https://api.gouv.fr https://*.googleapis.com
style-src 'self' 'unsafe-inline'                      # + styled-jsx
font-src 'self' data:                                 # Quicksand + Tabler
img-src 'self' data: blob:                            # uploads OCR
  https://*.tile.openstreetmap.org                    # tuiles Leaflet
connect-src 'self' https://*.supabase.co              # Supabase
  wss://*.supabase.co                                 # realtime WS
  https://api.gouv.fr https://*.api.gouv.fr           # RPPS/SIRENE/FINESS
  https://recherche-entreprises.api.gouv.fr           # SIRET search
  https://maps.googleapis.com                         # Places API
worker-src 'self' blob:                               # service worker
frame-src 'none'                                      # ZÉRO iframe externe
object-src 'none'                                     # pas de Flash/Java
form-action 'self'                                    # anti-CSRF forms
frame-ancestors 'self'                                # anti-clickjacking
upgrade-insecure-requests                             # force HTTPS sub-res

Pourquoi REPORT-ONLY au lieu d'enforcing

Mode REPORT-ONLY = le browser ne bloque pas ce qui violerait la policy, il rapporte juste ce qu'il aurait bloqué dans la console DevTools. Permet de valider qu'aucun script légitime n'est cassé avant de durcir.

Plan de durcissement

  1. Déployer 0.57.17 en prod → CSP report-only active
  2. Observer la console DevTools pendant 3-5 jours en prod
  3. Si 0 erreur CSP légitime : bascule en 0.57.18 (header Content-Security-Policy sans -Report-Only)
  4. À terme : retirer 'unsafe-inline' + 'unsafe-eval' via nonce dynamique dans middleware.js (chantier 0.58.x)

🔒 2. HSTS preload — force HTTPS dès la 1ère visite

Aspect0.57.40.57.17

Que fait 'preload'

Le flag preload permet de soumettre aveho-ec-app.vercel.app au site officiel hstspreload.org de Google. Une fois listé (process automatique après soumission), tous les browsers (Chrome, Firefox, Safari, Edge) baked-in la liste dans leur binaire — donc ils forcent HTTPS dès la 1ère visite, sans même avoir besoin du header.

Protège contre les attaques MITM sur la toute première connexion (avant que le user ait vu le header HSTS au moins une fois).

Action recommandée

Après le déploiement, soumettre Aveho à hstspreload.org. Note : ça implique un engagement de ne plus jamais downgrade en HTTP, donc à faire seulement si Aveho restera en HTTPS sur le long terme (ce qui est le cas avec Vercel).

🔒 4. Cross-Origin Resource Policy + COOP (anti-Spectre)

Les attaques side-channel CPU (Spectre, Meltdown, MDS) peuvent leak des données cross-origin via le timing des branches. La mitigation côté web standard :

HeaderValeurEffet
Cross-Origin-Opener-Policysame-origin-allow-popupsIsole window.opener (déjà en 0.57.4)
Cross-Origin-Resource-Policysame-originNOUVEAU 0.57.17 : seules les pages de aveho-ec-app.vercel.app peuvent charger nos ressources

Exception : /tabler-icons/* en cross-origin

Les fonts Tabler peuvent être loadées depuis n'importe où (CDN externes, embeds...) car ce sont des ressources publiques sans donnée sensible. Cache-Control immutable 1 an pour gain perf.

🔒 5. poweredByHeader désactivé (anti-fingerprinting)

Par défaut, Next.js envoie un header X-Powered-By: Next.js qui permet à un attaquant de :

  1. Savoir qu'on utilise Next.js
  2. Cibler des CVE spécifiques aux versions Next 14/15/16
  3. Construire des payloads adaptés (ex: SSRF dans middleware Next, RCE RSC, etc.)

Avec poweredByHeader: false dans next.config.js, plus d'info gratuite. Vérifié mesuré : le header est ABSENT des réponses HTTP.

🔒 6. Auth standardisée routes /from-ocr

Les 2 routes OCR (/api/patients/from-ocr et /api/prescriptions/from-ocr) faisaient leur propre vérification Bearer token avec ~15 lignes de boilerplate dupliqué. Refactor : utiliser requireAuth() du lib/apiAuth.js comme les 15 autres routes.

Avant (boilerplate dupliqué)

const SUPABASE_URL = process.env.NEXT_PUBLIC_SUPABASE_URL;
const SUPABASE_ANON = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY;
if (!SUPABASE_URL || !SUPABASE_ANON) {
  return Response.json({ ok: false, error: "Supabase non configuré" }, { status: 500 });
}
const auth = req.headers.get("Authorization") || "";
const token = auth.replace(/^Bearer\s+/i, "");
if (!token) {
  return Response.json({ ok: false, error: "Non authentifié (Bearer token manquant)" }, { status: 401 });
}
const supabase = createClient(SUPABASE_URL, SUPABASE_ANON, {
  global: { headers: { Authorization: `Bearer ${token}` } },
});
const { data: { user } } = await supabase.auth.getUser();
if (!user) return Response.json({ ok: false, error: "Token invalide" }, { status: 401 });

Après (3 lignes propres)

const authCheck = await requireAuth(req);
if (!authCheck.ok) return authCheck.response;
const { user, supabase } = authCheck;

Comportement strictement identique mais : (1) maintenable, (2) un fix dans requireAuth bénéficie à toutes les routes, (3) tests anti-régression couvrent toutes les routes uniformément.

🛡️ Test anti-régression critique (le plus important)

Pour empêcher qu'un dev oublie requireAuth dans une nouvelle route POST/PUT/DELETE :

// __tests__/v057-17-security-hardening.test.js
const WHITELIST = ["/version", "/health"];  // health-checks publics par design

it("Toute route POST/PUT/DELETE utilise requireAuth", () => {
  const routes = listApiPostRoutes();
  const violations = routes.filter(r =>
    !WHITELIST.includes(r.path) && !r.src.includes("requireAuth")
  );
  expect(violations.map(v => v.path)).toEqual([]);
});

Garantie : si quelqu'un ajoute /api/dump-all-patients/route.js avec un POST sans requireAuth, le test échoue avant même le push. La whitelist ne peut être étendue qu'en modifiant ce test explicitement, ce qui force le reviewer du PR à se poser la question.

📋 Après déploiement : observer la console DevTools

Le CSP est en mode REPORT-ONLY donc il ne casse rien. Mais pendant les premiers jours, observe la console (F12) sur la prod :

  • S'il y a des erreurs [Report Only] Refused to load the script... → c'est qu'un script légitime est bloqué. Il faut ajouter sa source dans la directive script-src de next.config.js
  • S'il y a des erreurs [Report Only] Refused to connect to... → ajouter dans connect-src
  • S'il y a des erreurs [Report Only] Refused to load the image... → ajouter dans img-src

Quand tu n'as plus aucune erreur CSP en prod pendant 3-5 jours d'usage normal, on bascule en enforcing (version 0.57.18) en retirant -Report-Only du nom du header.
