1 SQL — vues stats DI invisibles côté API

Erreur dans la console navigateur sur /statistiques-interventions :

GET /rest/v1/v_stats_di_global?... 404 (Not Found)
GET /rest/v1/v_stats_di_par_type?... 404 (Not Found)
GET /rest/v1/v_stats_di_par_urgence?... 404 (Not Found)
GET /rest/v1/v_stats_di_heatmap?... 404 (Not Found)
GET /rest/v1/v_stats_di_top_demandeurs?... 404 (Not Found)
GET /rest/v1/v_stats_di_par_mois?... 404 (Not Found)
statistiques-interventions: 503 (Offline)

Diagnostic surprenant :

-- En base, les 6 vues sont bien créées
select viewname from pg_views where viewname like 'v_stats_di%';
-- Retourne les 6 lignes attendues ✓

Cause : PostgREST (la couche API REST de Supabase) garde en mémoire un cache du schéma au démarrage du projet. Quand on crée de nouvelles vues via SQL Editor, ce cache n'est pas invalidé automatiquement. Résultat : la vue existe en base, mais l'API ne sait pas qu'elle existe → 404.

Correction : envoyer un NOTIFY à PostgREST pour qu'il recharge son cache.

notify pgrst, 'reload schema';

Si après ça les 404 persistent, c'est qu'il manque aussi les GRANT SELECT explicites au rôle authenticated. Supabase ajoute automatiquement des grants par défaut sur le schema public mais ça n'est pas garanti sur toutes les configurations. Le hotfix donc ajoute les 6 grants explicites :

grant select on v_stats_di_global         to authenticated;
grant select on v_stats_di_par_type       to authenticated;
grant select on v_stats_di_par_urgence    to authenticated;
grant select on v_stats_di_heatmap        to authenticated;
grant select on v_stats_di_top_demandeurs to authenticated;
grant select on v_stats_di_par_mois       to authenticated;
notify pgrst, 'reload schema';

Leçon : à la fin de tout patch SQL qui crée des vues ou RPC, ajouter systématiquement :

  1. grant select on <view> to authenticated; (ou grant execute on function <rpc> ...)
  2. notify pgrst, 'reload schema'; à la toute fin

2 SQL — duplication templates RGPD multi-etabs bloquée

Erreur au clic sur "Dupliquer vers HÔPITAL CÉDRIC" depuis un template v1.0 :

Erreur duplication : duplicate key value violates unique constraint 
"consent_templates_structure_id_version_key"

Cause : la table consent_templates a été créée en 0.34 avec une contrainte :

unique (structure_id, version)

En 0.42, j'ai ajouté la colonne etablissement_id pour permettre les templates spécifiques par établissement, mais j'ai oublié de mettre à jour la contrainte unique. Du coup, dès qu'on veut dupliquer un template existant v1.0 vers un autre etab en gardant la même version, le couple (structure_id, version) est déjà pris → rejet.

Correction : remplacer la contrainte par un index unique qui inclut etablissement_id. Avec un piège Postgres à gérer : par défaut NULL ≠ NULL dans les contraintes unique, donc un simple unique(structure_id, etablissement_id, version) autoriserait 2 templates globaux (etab=NULL) avec la même version. On utilise coalesce() avec un UUID zéro pour traiter NULL comme une valeur distincte :

- alter table consent_templates add constraint unique (structure_id, version);
+ alter table consent_templates drop constraint if exists consent_templates_structure_id_version_key;
+ create unique index consent_templates_struct_etab_version_key
+   on consent_templates (
+     structure_id,
+     coalesce(etablissement_id, '00000000-0000-0000-0000-000000000000'::uuid),
+     version
+   );

Maintenant on peut avoir :

  • Template v1.0 global (etab=NULL)
  • Template v1.0 pour HÔPITAL CÉDRIC
  • Template v1.0 pour EHPAD LES TILLEULS
  • … tous en même temps, sans collision.

Bonus côté front : message d'erreur amélioré dans app/parametres-rgpd/page.js pour distinguer les 2 cas (hotfix non appliqué vs vrai doublon de version) :

- if (error) throw error;
+ if (error) {
+   if (error.code === "23505" || error.message?.includes("duplicate")) {
+     throw new Error(
+       "Un template avec cette version existe déjà pour au moins un " +
+       "des établissements sélectionnés.\n\n" +
+       "Soit l'hotfix SQL de la 0.43 n'a pas été appliqué, soit tu as " +
+       "déjà un template v" + source.version + " pour un de ces établissements."
+     );
+   }
+   throw error;
+ }

Leçon : à chaque fois qu'on ajoute une colonne à une table qui a une contrainte UNIQUE existante, vérifier si la contrainte doit être étendue à la nouvelle colonne. C'est exactement le grep réflexe sur les schémas de tables, mais étendu aux contraintes.

À retenir pour les prochaines versions

Quatre grep réflexes à faire avant d'écrire du SQL ou du front impactant la BDD :

  1. Pattern RLS : grep "create policy.*structure_id" supabase/*.sql → utiliser mes_structures()
  2. Schéma + contraintes d'une table : 
    grep -A 25 "create table.*<table>" supabase/*.sql
    Vérifier les noms de colonnes mais aussi les contraintes UNIQUE qui doivent peut-être être étendues si on ajoute une colonne discriminante.
  3. Dates en JS : new Date(getTime() + n * 86400000), jamais setDate(getDate() + n) à cause des DST.
  4. Fin de tout patch SQL créant des vues/RPC : 
    grant select on <new_view> to authenticated;
-- OU pour une RPC :
grant execute on function <new_function>(...) to authenticated;

-- À la toute fin du fichier :
notify pgrst, 'reload schema';
    Ces 2 lignes économisent un aller-retour de debug à chaque livraison.
