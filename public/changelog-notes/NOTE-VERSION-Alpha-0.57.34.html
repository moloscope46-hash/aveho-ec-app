🔒 Axe 1 — AdminGuard sur les 9 pages admin

Le problème

Les 9 pages app/admin/* (avis-google, bulletins-archive, doublons-forces, mail-diagnostic, medecins-prescripteurs, prescriptions-archive, referentiels-sante, rpps-diagnostic, rpps-dump) n'avaient aucun check de rôle côté client. N'importe quel user authentifié pouvait accéder à leurs URLs.

Le RLS Postgres bloquait l'accès aux données sensibles, mais conséquences pour un user non-admin :

  • UI cassée → croyait à un bug
  • Découverte de la structure interne (noms tables/routes via erreurs 401/403)
  • Mauvais retour utilisateur (pas de blocage clair)

Le fix : composant AdminGuard réutilisable

// app/components/AdminGuard.js (130 lignes)
export default function AdminGuard({ children, fallbackUrl = "/accueil" }) {
  const auth = useAuth();
  const router = useRouter();

  // 4 checks defense-in-depth (compatibles legacy + nouveau système)
  const isAdmin =
    auth.can?.("gerer_roles") ||
    auth.can?.("manage_collectivite") ||
    auth.role?.systeme === "admin" ||
    auth.role?.nom === "Administrateur";

  if (!auth.ready) return <Spinner />;          // chargement
  if (!auth.user) return null;                  // useAuth redirige vers /login
  if (!isAdmin) return <AccesRestreint />;     // blocage clair + bouton retour
  return children;                              // admin OK
}

🚨 Axe 2 — XSS dans toast realtime (user A → user B)

Le bug critique

lib/useRealtimeTable.js faisait :

toast.innerHTML = `
  <div>
    <i class="ti ${icon}" style="color: ${color};"></i>
    <div style="color: ${color};">${title}</div>
    <div>${message}</div>
  </div>
`;

Les variables title et message viennent d'événements Supabase Realtime (changements en BDD par d'autres users).

Scénario d'attaque

  1. User A (malveillant) crée une intervention avec titre : <img src=x onerror=alert(document.cookie)>
  2. Supabase Realtime broadcast le changement → user B reçoit un toast
  3. toast.innerHTML = ...${title}... injecte le HTML → exécution du JS
  4. Le JS tourne dans le contexte de l'onglet authentifié de user B → exfiltration du Bearer Supabase possible

CVSS estimé : 6.5 MEDIUM (exploit nécessite Realtime activé + 2 users connectés)

Le fix : 3 helpers de sanitization

// 1. escapeHtml standard
function escapeHtml(s) {
  return String(s ?? "")
    .replace(/&/g, "&amp;").replace(/</g, "&lt;")
    .replace(/>/g, "&gt;").replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;");
}

// 2. Whitelist class Tabler icons (empêche injection CSS)
function safeIconClass(icon) {
  if (typeof icon !== "string") return "ti-bell";
  if (!/^ti-[a-z0-9-]{1,40}$/.test(icon)) return "ti-bell";
  return icon;
}

// 3. Whitelist couleur hex
function safeColor(color) {
  if (typeof color !== "string") return "#185FA5";
  if (!/^#[0-9a-fA-F]{3,6}$/.test(color)) return "#185FA5";
  return color;
}

// Sanitize TOUS les inputs AVANT innerHTML
const safeTitle = escapeHtml(title);
const safeMessage = escapeHtml(message);
const safeIcon = safeIconClass(icon);
const safeColorVal = safeColor(color);

toast.innerHTML = `... ${safeTitle} ... ${safeMessage} ...`;

🛡️ Axe 3 — Defense-in-depth pdfPreview

lib/pdfPreview.js injectait ${titre} direct dans innerHTML. En pratique appelé avec des constantes hardcodées ("Aperçu de la prescription"), mais si demain du contenu BDD transite par cette fonction → XSS. Fix : safeTitre = escapeHtml(titre) appliqué.

🔧 Axes bonus — fixes build

Fix prerender SSG /statistiques-interventions

Erreur de build observée : Error: @supabase/ssr: Your project's URL and API key are required. Cause : Next.js essayait de pré-rendre la page au build SANS les env vars Supabase. Fix : export const dynamic = "force-dynamic" → désactive le SSG, rend la page à chaque request.

Fix test v055-15-sql-modal

Le test acceptait uniquement le pattern aveho-PATCH-vers-X.Y.Z.sql mais le nouveau script aveho-supabase-securite-COMPLET-0.57.33.sql ne matchait pas. Élargissement du regex pour accepter les 2 patterns historiques.
