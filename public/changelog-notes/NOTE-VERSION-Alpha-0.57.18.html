🚨 Bug 1 : /api/finess?q=lom → 401 Unauthorized

Signalé par l'utilisateur :

GET https://aveho-ec-pnzuew0c1-fleos-projects.vercel.app/api/finess?q=lom&limit=12 401 (Unauthorized)

Cause : FinessSearch.js (autocomplete de recherche établissements de santé) utilisait fetch(url) au lieu de fetchWithAuth(url). Même pattern de bug que SireneSearch.js fixé en 0.57.16.

MAIS, le LINT anti-régression de 0.57.16 ne l'a pas détecté car le pattern est différent :

Pourquoi le LINT 0.57.16 n'a rien vu

// Pattern DÉTECTÉ par le LINT v1 (0.57.16) :
await fetch("/api/sirene?...")          // littéral ← match
await fetch(`/api/sirene?${params}`)    // template ← match

// Pattern NON DÉTECTÉ par le LINT v1 → bug passe en prod :
let url;
if (isFinessNumber) {
  url = `/api/finess?finess=${val}`;    // <- url assignée
} else {
  url = `/api/finess?${params}`;
}
const res = await fetch(url);            // <- fetch(url) — pas en littéral
//                          ^^^^
//                          LINT v1 ne sait pas que `url` contient "/api/..."

🛡️ Bug 2 : Alertes Supabase Security Advisor

Email reçu le 31 mai 2026 :

  • 🚨 Table publicly accessible — Une table publique sans RLS, accessible en lecture/écriture/suppression par n'importe qui
  • 🚨 User data exposed through a view — Une view expose auth.users (données utilisateurs publiques)

Impact potentiel : si un attaquant connaît l'URL du projet Supabase + la clé anon (publique par design), il peut directement requêter ces tables/views via l'API REST sans authentification. C'est critique pour Aveho car ça concerne des données médicales (RGPD).

📋 Solution : Script SQL audit + fix livré

J'ai créé scripts/audit-rls-supabase.sql qui s'utilise en 2 phases :

PARTIE 1 : Audit (lecture seule, à lancer en premier)

SectionCe qui est listé
1.1Tables du schéma public sans RLS activé
1.2Tables avec RLS activé mais aucune policy (= cassées, personne ne peut lire)
1.3Views exposant auth.users / auth.identities / auth.sessions
1.4Fonctions SECURITY DEFINER (potentielle privilege escalation)
1.5Récap de toutes les policies par table (visibilité globale)
1.6Grants anon / authenticated par table (quelles tables sont exposées via REST)

PARTIE 2 : Templates de fix (commentés)

SectionTemplate fourni
2.1Batch ALTER TABLE ... ENABLE ROW LEVEL SECURITY pour toutes les tables sans RLS
2.2Policy "lecture authenticated" pour les tables référentiel (NAF, CCAM...)
2.3Policy "isolation par structure_id" pour les tables métier (patients, commandes, etc.)
2.4Recréer une view auth.users en security_invoker=true + filtre auth.uid()
2.5Figer search_path sur les fonctions SECURITY DEFINER

Tout est COMMENTÉ par défaut pour éviter l'exécution accidentelle. À décommenter un bloc à la fois après audit.

🚀 Comment l'utiliser (workflow recommandé)

  1. Se connecter à Supabase Dashboard
  2. Projet aveho-ec → SQL Editor
  3. Coller le contenu de scripts/audit-rls-supabase.sql
  4. Run PARTIE 1 seulement (les 6 requêtes SELECT) → noter ce qui ressort :
    • Quelles tables sont sans RLS
    • Quelle view expose auth.users
    • Quelles fonctions SECURITY DEFINER existent
  5. 📸 Faire un snapshot/backup avant la PARTIE 2 (Dashboard → Database → Backups → Create snapshot)
  6. Décommenter UN bloc à la fois dans la PARTIE 2 :
    • Pour les tables métier (patients, commandes, etc.) → bloc 2.3 isolation par structure_id
    • Pour les tables référentiel (NAF, CCAM, etc.) → bloc 2.2 lecture authenticated
    • Pour les views auth.users → bloc 2.4 security_invoker
    • Pour les fonctions SECURITY DEFINER → bloc 2.5 search_path figé
  7. Adapter le template au nom exact de ta table/view/fonction
  8. Run le bloc
  9. Vérifier dans l'app Aveho que tout fonctionne encore (lire un patient, en créer un, etc.)
  10. Recommencer pour la table/view/fonction suivante

Si quelque chose casse : restaurer le snapshot ou faire le DROP POLICY + ALTER TABLE ... DISABLE ROW LEVEL SECURITY temporairement.

💡 Pattern de policy le plus courant Aveho

La majorité des tables métier Aveho ont une colonne structure_id qui identifie la collectivité du PSAD. Pattern : un user voit/édite SEULEMENT les lignes de sa structure.

-- Pour une table 'patients' (exemple) :

ALTER TABLE public.patients ENABLE ROW LEVEL SECURITY;

-- 4 policies (SELECT, INSERT, UPDATE, DELETE) :

CREATE POLICY "Lecture par structure" ON public.patients
  FOR SELECT TO authenticated
  USING (
    structure_id IN (
      SELECT structure_id FROM membres_structure WHERE user_id = auth.uid()
    )
  );

CREATE POLICY "Insertion dans ma structure" ON public.patients
  FOR INSERT TO authenticated
  WITH CHECK (
    structure_id IN (
      SELECT structure_id FROM membres_structure WHERE user_id = auth.uid()
    )
  );

CREATE POLICY "Modification dans ma structure" ON public.patients
  FOR UPDATE TO authenticated
  USING (
    structure_id IN (
      SELECT structure_id FROM membres_structure WHERE user_id = auth.uid()
    )
  )
  WITH CHECK (
    structure_id IN (
      SELECT structure_id FROM membres_structure WHERE user_id = auth.uid()
    )
  );

CREATE POLICY "Suppression dans ma structure" ON public.patients
  FOR DELETE TO authenticated
  USING (
    structure_id IN (
      SELECT structure_id FROM membres_structure WHERE user_id = auth.uid()
    )
  );

Si tu as plusieurs tables avec ce pattern, je peux te générer un script qui les fait toutes d'un coup — il te suffit de me dire la liste des tables à protéger.
