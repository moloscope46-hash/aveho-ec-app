🔍 Pourquoi ces 2 tables sont sans RLS

Les tables caisses_assurance_maladie et mutuelles sont des référentiels partagés :

  • Données communes à toutes les structures PSAD (pas de colonne structure_id)
  • Importées depuis des sources externes (RPPS, INAMI, ROC, etc.) par le backend Aveho
  • Utilisées par tous les utilisateurs pour auto-link les patients lors de l'OCR bulletin

Probablement créées au début du projet sans qu'on pense à activer RLS car "c'est juste un référentiel, ya rien de sensible". Mais en l'absence de RLS, n'importe qui avec l'URL Supabase + la clé anon (publique par design) peut :

  • ❌ SELECT toutes les caisses + tous les codes organisme CPAM
  • ❌ INSERT de fausses caisses pour fausser l'application Aveho
  • ❌ UPDATE/DELETE des entrées existantes

C'est exactement ce que Supabase Security Advisor alertait.

✅ Fix : script SQL personnalisé livré

J'ai créé scripts/fix-rls-aveho.sql spécifique à tes 2 tables. Pattern : lecture authenticated, écriture service_role only.

-- 1. Vérification pré-fix (lecture seule)
SELECT table_name,
  COUNT(*) FILTER (WHERE column_name = 'structure_id') AS has_structure_id
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN ('caisses_assurance_maladie', 'mutuelles')
GROUP BY table_name;
-- Attendu : has_structure_id = 0 → confirme que ce sont des référentiels

-- 2. Fix caisses
ALTER TABLE public.caisses_assurance_maladie ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Lecture caisses pour utilisateurs authentifiés"
  ON public.caisses_assurance_maladie
  FOR SELECT TO authenticated
  USING (true);

-- 3. Fix mutuelles (identique)
ALTER TABLE public.mutuelles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Lecture mutuelles pour utilisateurs authentifiés"
  ON public.mutuelles
  FOR SELECT TO authenticated
  USING (true);

-- 4. Vérification post-fix
SELECT t.tablename, t.rowsecurity AS rls_enabled,
  COUNT(p.policyname) AS nb_policies
FROM pg_tables t
LEFT JOIN pg_policies p ON p.tablename = t.tablename
WHERE t.tablename IN ('caisses_assurance_maladie', 'mutuelles')
GROUP BY t.tablename, t.rowsecurity;
-- Attendu : rls_enabled=true, nb_policies=1 pour chacune

🔒 Pourquoi PAS de policy INSERT/UPDATE/DELETE pour authenticated

RLS bloque tout par défaut. Si on n'écrit AUCUNE policy pour INSERT/UPDATE/DELETE, les utilisateurs authentifiés ne peuvent PAS écrire dans ces tables. C'est exactement ce qu'on veut pour un référentiel :

  • ✅ Tous les users PSAD peuvent LIRE (via la policy SELECT)
  • ❌ Aucun user PSAD ne peut ÉCRIRE (pas de policy = refus)
  • ✅ Le service_role (utilisé en backend Aveho pour les imports CSV/RPPS) bypass RLS par défaut → peut tout faire

Pattern réutilisable pour tout référentiel partagé futur.

🐛 Bug 1 : Test Vitest échouait sous Windows

Symptôme : un seul test échouait quand tu lançais npm test sous Windows :

AssertionError: expected [ '\health\route.js', …(1) ] to deeply equal [ '/health', '/version' ]

Cause

Le test faisait .replace("/route.js", "") AVANT de normaliser les séparateurs Windows \\. Sous Windows, fs.readdirSync renvoie des paths avec \\, donc /route.js ne matche jamais.

// AVANT (cassé sous Windows) :
const apiPath = full
  .replace(path.join(process.cwd(), "app/api"), "")
  .replace("/route.js", "")     // ← ne matche pas \\health\\route.js
  .replace(/\\/g, "/");         // ← trop tard

// APRÈS (0.57.19) :
const apiPath = full
  .replace(path.join(process.cwd(), "app/api"), "")
  .replace(/\\/g, "/")           // ✓ normalise d'abord
  .replace("/route.js", "");     // ✓ matche maintenant partout

Le même bug existait dans 2 endroits du test 0.57.17 : test "Seules /api/version et /api/health" + test "POST/PUT/DELETE doit avoir requireAuth". Les 2 fixés. Le test 0.57.16 (LINT v2) avait déjà l'ordre correct.
