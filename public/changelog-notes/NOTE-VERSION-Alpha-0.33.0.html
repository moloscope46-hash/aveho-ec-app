Résumé

Aveho EC avait déjà 2 canaux de notification : push VAPID (PWA, 0.17) et webhooks Teams/Slack (0.18). Resend était branché pour les emails DPO uniquement (rappels renouvellement RGPD, 0.24).

La 0.33 ajoute le 3e canal manquant : les emails directs aux utilisateurs pour les workflows métier (DI urgentes, achats refusés, maintenance planifiée, etc.). Le tout en respectant les préférences user via une nouvelle ligne dans NotificationPreferences.

Opt-in strict pour les emails. Contrairement au push (ON par défaut sauf archivage), les emails sont OFF par défaut pour toutes les catégories. L'utilisateur doit cocher explicitement chaque case email_X qu'il veut activer dans /profil. Logique : un email est plus intrusif qu'un push, on évite le spam.

1. Edge Function send-email

API d'appel

await supabase.functions.invoke("send-email", {
  body: {
    structure_id: "...",
    target_user_id: "...",     // OU target_emails: [...] pour externes
    event_type: "di",           // mapping catégorie prefs
    subject: "DI urgente assignée",
    body_html: "<p>...</p>",
    body_text: "...",           // fallback texte
    cta_label: "Voir la DI",    // optionnel
    cta_url: "https://...",     // optionnel
  }
})

Logique de résolution des destinataires

  1. Cas 1 — target_emails fourni : envoie direct (utile pour DPO externe, partenaire, etc.)
  2. Cas 2 — target_user_id fourni : résout l'email via v_users_emails (rapide) ou fallback auth.admin.getUserById
  3. Cas 3 — ni l'un ni l'autre : broadcast à tous les membres de la structure

Filtrage opt-in par event_type

Pour chaque destinataire avec un user_id, l'Edge Function regarde prefs.email_{event_type} :

  • Clé absente → pas d'envoi (opt-in strict)
  • email_di = true → envoie
  • email_di = false → pas d'envoi
  • target_emails (sans user_id) → toujours envoyé (bypass filtre)

Template HTML brandé

Tous les emails sont enveloppés dans un template HTML responsive :

  • Header navy avec logo "aveho" et accent teal
  • Body : titre H1 + body HTML libre
  • Bouton CTA centré (si cta_url + cta_label fournis) en bleu Aveho
  • Footer gris : "Tu peux désactiver les notifications email dans ton profil →" avec lien
  • Responsive (table-based pour compat Outlook)
  • Échappement HTML de tous les champs dynamiques (XSS-safe)

2. Intégration dans logEvent

Relais transparent

Aucun changement nécessaire dans les pages métier. logEvent relaie automatiquement vers send-email en parallèle de send-push et send-webhook quand notif: true :

// Aucun changement requis dans les pages métier
await logEvent(supabase, auth, {
  action: "creer", entite: "intervention", entite_id: di.id,
  titre: "DI urgente créée",
  message: `${di.numero} : ${di.objet}`,
  lien: `/interventions?id=${di.id}`,
  notif: true,   // → déclenche push + webhook + email (si opt-in)
});

Pour les events où on veut désactiver l'email seulement (ex: hot reload, événements de masse silencieux), nouveau flag :

await logEvent(supabase, auth, {
  ...,
  notif: true,
  skipEmail: true,  // push + webhook mais pas d'email
});

buildEmailBody — corps automatique

Génère un body HTML structuré à partir des champs ev :

  • Message principal en paragraphe (si différent du titre)
  • Mini-tableau des ev.details (numéro, motif, statut, etc.) en gris pâle
  • Tous les valeurs sont passées dans escapeHtml() (XSS-safe)
  • Fallback : si aucune donnée riche, juste le titre dans un <p>

3. NotificationPreferences refondu

Grille 2 colonnes par catégorie

Avant : 1 case par catégorie (push seulement). Après : 2 cases (push + email) sur la même ligne.

┌────────────────────────────────────────────┬──────┬───────┐
│ Catégorie                                  │ Push │ Email │
├────────────────────────────────────────────┼──────┼───────┤
│ 🔧 Demandes d'intervention                 │  ☑   │   ☐   │
│ 🛒 Workflow achats                         │  ☑   │   ☑   │
│ 🔄 Transferts                              │  ☑   │   ☐   │
│ 💬 Signalements / Idées                    │  ☑   │   ☐   │
│ 🔧 Maintenance préventive                  │  ☑   │   ☑   │
│ 🛡️ Renouvellement RGPD                     │  ☑   │   ☐   │
│ 📦 Archivage RGPD mensuel                  │  ☐   │   ☐   │
└────────────────────────────────────────────┴──────┴───────┘
ℹ️ Push : 6/7 — Email : 2/7

Comportement

  • Push : ON par défaut sauf consent_auto_archive (inchangé depuis 0.29)
  • Email : OFF par défaut pour toutes (opt-in strict)
  • Les 2 toggles sont indépendants : on peut activer push sans email (cas le plus courant) ou email sans push (cas "silencieux mobile" : pas dérangé par notif PWA mais reçoit l'email)
  • Compteurs affichés en haut : "Push : 6/7 · Email : 2/7"
  • Encart violet d'info : "Les emails sont désactivés par défaut pour éviter le spam. Active-les uniquement pour les catégories où tu veux recevoir aussi un email en plus de la notification push."

4. Stockage

Pas de schema migration nécessaire. La table user_notification_preferences (0.29) accepte n'importe quelle clé dans son champ prefs jsonb. On ajoute juste des clés préfixées :

{
  "di": true,          // push DI (existait déjà)
  "email_di": true,    // email DI (nouveau 0.33)
  "achat": true,
  "email_achat": false, // ou absent → off
  ...
}

Vue v_users_emails

Vue minimaliste qui expose id, email, nom_affiche, created_at depuis auth.users. Accessible uniquement par service_role (les Edge Functions). RLS publique non nécessaire car la table auth.users n'est pas exposée à l'API REST de toute façon.

5. Sécurité

  • XSS escape strict sur tous les champs dynamiques (titre, message, details, valeurs) via escapeHtml()
  • Mode dégradé : si RESEND_API_KEY n'est pas configuré → log warning + retour 200 (ne plante pas l'app)
  • Rate limit Resend géré naturellement : 1 appel par destinataire, pas de batch (évite les erreurs 429)
  • Erreurs partielles : si 3 destinataires sur 10 échouent, les 7 autres reçoivent quand même (retour {sent, failed, errors})
  • CORS preflight OPTIONS géré

Procédure d'application

  1. SQL d'abord dans Supabase → SQL Editor → coller aveho-PATCH-vers-0.33.sql → Run. 
    -- Vérifier que la vue existe
select count(*) from v_users_emails;
-- Doit fonctionner (tu as les droits service_role en SQL Editor)
  2. Déployer la nouvelle Edge Function : 
    cd C:\aveho-ec-app
supabase functions deploy send-email
  3. Vérifier les secrets Resend dans Supabase (Settings → Edge Functions → Secrets) :
    • RESEND_API_KEY (déjà configuré depuis 0.24)
    • RESEND_FROM_EMAIL = "Aveho EC <no-reply@aveho.fr>" (ou ton domaine vérifié sur Resend)

    Important : ton domaine d'envoi doit être vérifié sur resend.com/domains. Sinon les emails partiront du onboarding@resend.dev (mode test) qui ne fonctionne que pour ton compte propriétaire.

  4. Décompresser le zip par-dessus C:\aveho-ec-app\.
  5. npm install + tests + dev : 
    npm install
npm test       # 370 passed
npm run dev
  6. Tester :
    • Aller dans /profil → section "Mes notifications"
    • Voir la nouvelle grille 2 colonnes (Push | Email)
    • Activer email_di par exemple → Enregistrer
    • Créer une DI urgente quelque part → tu dois recevoir un email avec le template brandé Aveho
