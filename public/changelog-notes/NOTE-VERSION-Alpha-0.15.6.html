1. Résumé exécutif

L'Alpha 0.15.6 est l'aboutissement d'une session de migration intensive où nous sommes partis d'une base 0.1 existante en production pour arriver à un déploiement 0.15 fonctionnel. La 0.15.0 initiale livrait 5 chantiers fonctionnels (Achats, Cmd+K, Journal, Étiquettes, Excel). Les 6 hotfix consécutifs ont corrigé les écarts entre le schéma de base existant (0.1) et les hypothèses du code applicatif (0.15).

Cette note est la version consolidée finale qui documente tout : les fonctionnalités livrées, les bugs rencontrés, les pièges à éviter, et les commandes de récupération.

2 scripts SQL livrés :
• aveho-PATCH-vers-0.15.sql — patch idempotent pour une base 0.1 existante
• aveho-0.15-complet.sql — création from scratch pour une nouvelle base

3. Détail des fonctionnalités

3.1 Module Achats — workflow 7 statuts

Brouillon → À valider → Validée → Commandée → Reçue

Plus deux statuts annexes : Refusée (motif obligatoire visible par le demandeur) et Annulée. KPIs cliquables par statut + KPI Budget engagé en gradient navy/teal. Lignes détaillées par commande (table achats_lignes). Notifications via logEvent à chaque transition.

3.2 Recherche globale Cmd+K

5 préfixes pour filtrer instantanément : p: patients, m: matériels, d: demandes d'intervention, s: signalements, a: achats. Panneau d'aide visuelle quand l'input est vide. Navigation clavier ↑↓ Enter Échap.

3.3 Journal d'activité

Page /journal avec timeline visuelle groupée par jour. Trait vertical, points colorés par action, phrasé naturel, badges colorés par entité. Filtres : période (1/7/30/90j), entité, utilisateur. Source : table audit_log.

3.4 Étiquettes patient

Sur la fiche patient, bouton dashed "Gérer" à côté des pastilles d'étiquettes. Modale avec toggles directs. Mise à jour optimiste + persistance Supabase.

3.5 Export Excel multi-feuille

Bouton "Export Excel" sur Statistiques. Charge SheetJS depuis CDN au premier appel, génère bilan-aveho-2026-XX-XX.xlsx avec 7 feuilles : Patients, Matériels, DI, Maintenances, Stock, Achats, Informations.

5. Corrections détaillées

5.1 Collision de noms — table commandes

Le module Achats utilisait initialement les tables commandes et commande_lignes, qui existaient déjà dans la base 0.1 pour le workflow panier magasin. Résultat : le create table if not exists ne créait rien et le code plantait à l'exécution.

Correction : renommage en achats et achats_lignes. Le code Next.js a été mis à jour partout. Les tables 0.1 commandes / commande_lignes restent intactes pour le panier magasin.

5.2 RLS avec dépendance à ms.role

Les scripts SQL initiaux 16 et 17 contenaient des politiques RLS qui joignaient roles r on r.id = ms.role. Or la colonne role de membres_structure est text (legacy), tandis que role_id est uuid. La jointure plantait avec ERROR: operator does not exist: uuid = text.

Correction : les politiques RLS de signalements, achats, achats_lignes n'utilisent plus aucune référence à roles. La sécurité repose uniquement sur mes_structures().

5.3 useAuth qui cherche permissions_json au lieu de droits

La table roles dans les anciennes bases utilise droits (jsonb). Le code useAuth faisait select(...,roles(id,nom,permissions_json)) qui plantait.

Correction côté code : fallback en deux temps, accepte les deux noms, gère les deux formats (array ["write","read"] ou objet par module {"stock":["read"]}).

Correction côté SQL : le script 06_utilisateurs.sql ajoute désormais une colonne permissions_json en alias de droits.

5.4 Page Journal cassée — table evenements (hotfix 0.15.1)

Première version de /journal/page.js requêtait evenements et membres_structure.prenom/nom/email. La vraie table d'audit s'appelle audit_log et membres_structure n'a qu'une colonne nom_affiche.

Correction : app/journal/page.js et app/patient/[id]/page.js requêtent désormais audit_log, récupèrent l'auteur depuis nom_affiche, et tombent sur audit_log.user_email en fallback.

5.5 Établissement : colonne etages.niveau inexistante (hotfix 0.15.2)

Le code triait les étages par order("niveau") et envoyait un payload {niveau: form.niveau}. Mais la table etages a juste id, structure_id, batiment_id, nom, created_at.

Correction : tri par nom, retrait du champ niveau du payload et du formulaire. L'ordre des étages se gère via le nom (R-2, R-1, RDC, R+1, R+2).

5.6 RLS étanche : payload sans structure_id (hotfix 0.15.3)

La RLS batiments_write_etab exige structure_id IN mes_structures() AND (etablissement_id IS NULL OR etablissement_id IN mes_etablissements()). Le code n'envoyait que etablissement_id, jamais structure_id → 403 Forbidden systématique.

Correction : payload.structure_id = auth.structureId ajouté systématiquement, et la création de hiérarchie (batiment / étage / service / chambre / lit) inclut toujours structure_id.

Côté base : l'utilisateur admin doit être explicitement rattaché aux établissements via membres_etablissements (oubli de seed à corriger en 0.16) :

insert into membres_etablissements (user_id, etablissement_id)
select '<user_id>', e.id
from etablissements e
where e.structure_id = '<structure_id>'
  and not exists (
    select 1 from membres_etablissements me
    where me.user_id = '<user_id>' and me.etablissement_id = e.id
  );

5.7 Services type rétabli (hotfix 0.15.4 → 0.15.6)

La colonne type de la table services a été désactivée en 0.15.4 (n'existait pas en base), puis rétablie en 0.15.6 après application de alter table services add column if not exists type text; dans la base. Le menu déroulant Médecine / Chirurgie / Soins de suite / EHPAD / Urgences / Maternité / Pédiatrie / Réanimation est de retour.

5.8 Patients & Calendrier : selects compatibles 0.1 (hotfix 0.15.5)

Plusieurs requêtes cherchaient des relations ou colonnes inexistantes :

  • patients?select=*,services(nom) → la table patients (0.1) stocke la localisation en text (champs chambre, batiment), pas en FK. Retrait de la jointure.
  • interventions.due_date → colonne absente. Retrait du select dans /calendrier.

Pour rétablir due_date en 0.16 : alter table interventions add column if not exists due_date date;

6. Pièges connus (8 cas) IMPORTANT

⚠️ Piège n°1 : ne PAS supprimer commande_lignes

Table du workflow panier magasin 0.1. Si supprimée par mégarde, /panier casse avec "Could not find the table commande_lignes". Récupération via le bloc 2 du aveho-PATCH-vers-0.15.sql.

⚠️ Piège n°2 : ne PAS toucher à la table commandes

Table du workflow panier magasin 0.1. Le module Achats utilise achats, jamais commandes.

⚠️ Piège n°3 : auth.uid() retourne NULL dans le SQL Editor

Le SQL Editor tourne avec le rôle postgres, pas le user authentifié. Pour insérer manuellement avec un user_id, va dans Authentication → Users du Dashboard Supabase, récupère l'id, et utilise-le en littéral dans tes requêtes.

⚠️ Piège n°4 : mot de passe en clair dans les logs console

Si tu colles les logs F12 pour debug, vérifie qu'il n'y a pas de <input type="password" value="XXX">. Bonne pratique : magic link uniquement, pas de mot de passe stocké.

⚠️ Piège n°5 : table d'audit = audit_log

Pas evenements. Pour insérer manuellement un événement :

insert into audit_log (structure_id, user_id, user_email, action, entite, entite_id, details)
values ('<sid>', '<uid>', 'email', 'creer', 'patient', null, '{}'::jsonb);

⚠️ Piège n°6 : membres_structure n'a que nom_affiche

Pas de prenom / nom / email séparés. C'est un seul champ text. Le code récupère le nom complet depuis nom_affiche, et tombe sur audit_log.user_email en fallback.

⚠️ Piège n°7 : admin de structure ≠ admin d'établissement

Être dans membres_structure avec role=admin ne suffit pas pour écrire dans batiments/étages/services. Il faut aussi être dans membres_etablissements pour les établissements concernés. Voir le SQL d'auto-rattachement dans la section 5.6.

⚠️ Piège n°8 : Service Worker PWA et 503 Offline

Une PWA installée et son service worker peuvent servir un cache obsolète et retourner 503 (Offline) même quand le serveur tourne. Procédure de purge :

  • Edge → edge://apps/ → désinstaller la PWA Aveho
  • F12 → Application → Service Workers → Unregister
  • F12 → Application → Storage → Clear site data
  • Ctrl+Shift+R pour forcer le rechargement
  • Ou test ultime : ouvrir l'app en navigation InPrivate

8. Procédure de migration

Cas A — Base vierge (nouveau déploiement)

  1. Dans Supabase → SQL Editor → coller aveho-0.15-complet.sql → Run
  2. Cela crée toutes les tables, RLS et données démo
  3. Configure l'auth, déploie le code, c'est parti

Cas B — Base 0.1 existante (cas Cédric)

  1. Exécuter les scripts 02_referentiel.sql → 17_commandes.sql dans l'ordre. Ignorer les warnings "already exists".
  2. Exécuter le aveho-PATCH-vers-0.15.sql pour les cas de récupération.
  3. Pour le rétablissement complet des features : 
    alter table services add column if not exists type text;
alter table interventions add column if not exists due_date date;
  4. Rattacher l'utilisateur admin aux établissements (voir section 5.6).
  5. Vérifier les tables : 31 attendues.

Cas C — Base 0.15 partielle (récupération)

  1. Exécuter aveho-PATCH-vers-0.15.sql intégralement. Idempotent.
  2. Si /panier plante → section 2 du patch récupère commande_lignes
  3. Si boutons création invisibles → section 1 du patch ajoute permissions_json
  4. Si /signalements ou /achats plantent → sections 3 et 4 du patch créent les tables

Côté code (tous cas)

  1. Sauvegarder le .env.local
  2. Décompresser aveho-ec-app.zip dans le dossier projet (écrase le code)
  3. Remettre le .env.local
  4. PowerShell :
    cd C:\aveho-ec-app
npm install
npm run build
npm run dev
  5. Tests : Cmd+K affiche les 5 préfixes, /achats et /journal accessibles, boutons de création visibles, hiérarchie créable
  6. Mise en ligne : 
    git add . ; git commit -m "Aveho EC 0.15.6" ; git push
