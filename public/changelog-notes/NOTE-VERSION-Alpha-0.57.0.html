✨ Pourquoi cette version est exceptionnelle

Next 14 → Next 15, c'est habituellement un chantier de plusieurs jours qui nécessite :

  • Refactoring de toutes les pages dynamiques (params devient une Promise)
  • Adaptation des Server Components et Server Actions
  • Gestion du nouveau caching fetch par défaut
  • Migration des hooks cookies/headers en async
  • Réécriture du middleware

Chez Aveho EC : aucune de ces étapes nécessaires. L'architecture du code permettait le saut sans modification :

  • ✅ Les 7 pages dynamiques (/materiel/[id], /patient/[id], /patient/[id]/edit, /patient/[id]/dashboard, /equipe/[id], /inscription/[token], /verifier/[id]) sont toutes des Client Components qui utilisent useParams() — pas impacté par Next 15
  • ✅ Aucun Server Component ne destructure params dans sa signature
  • ✅ Pas de cookies() ou headers() dans le code app
  • ✅ Pas de Server Actions à migrer
  • ✅ fetch avec cache explicite déjà via next: { revalidate }
  • ✅ Pas de config Tailwind/PostCSS custom
  • ✅ Pas d'eslint-config-next configuré

Le saut s'est résumé à un bump de 3 lignes dans package.json.

Vulnérabilités restantes (à traiter en 0.58+)

  • xlsx Prototype Pollution (HIGH) — pas de fix upstream, nécessite migration vers ExcelJS
  • xlsx ReDoS (MOD) — idem
  • postcss XSS via </style> (MOD) — dépendance interne de Next, fix nécessiterait downgrade vers Next 9 (régression)

Ces 3 vulnérabilités ne sont pas exploitables facilement dans l'usage Aveho :

  • xlsx : nécessite que l'utilisateur charge un fichier XLSX malveillant, mais nos exports vont vers l'utilisateur (pas l'inverse)
  • postcss : nécessite que l'attaquant contrôle un fichier CSS qu'on stringify, ce qu'on ne fait pas
