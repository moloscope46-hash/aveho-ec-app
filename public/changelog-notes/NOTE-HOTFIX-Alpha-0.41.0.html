1 SQL — table d'appartenance user ↔ structure

Erreur au déploiement du patch SQL :

ERROR: 42P01: relation "users_structures" does not exist

Cause : j'avais inventé le nom users_structures. La vraie table d'Aveho s'appelle membres_structure, et il existe un helper SQL mes_structures() (security definer stable) utilisé partout dans les RLS du projet (patients, articles, materiels...).

Correction dans la policy de maintenance_recurrences :

- using (structure_id in (
-   select structure_id from users_structures where user_id = auth.uid()
- ))
+ using (structure_id in (select mes_structures()))

Et dans la Edge Function send-digest (mode force_send qui crée une pref temporaire) :

- .from("users_structures")
+ .from("membres_structure")

Leçon : avant d'écrire une nouvelle policy RLS, faire un grep "create policy.*structure_id" supabase/*.sql pour copier le pattern existant.

2 SQL — colonnes et statuts de la table maintenances

Erreur au déploiement (après fix #1) :

ERROR: 42703: column m.cloturee_le does not exist
LINE 97: avg(extract(epoch from (m.cloturee_le - m.created_at)) / 86400)

Cause : j'avais inventé une colonne cloturee_le en timestamptz et les statuts Clôturée / En cours. Les vraies colonnes sont :

  • date_realisee date (renseigné quand effectuée)
  • statut text : Planifiée / À faire / Faite / En retard / Annulée

Correction dans la vue v_stats_maintenances :

- count(*) filter (where m.statut = 'Clôturée') as nb_cloturees,
- count(*) filter (where m.statut = 'En cours') as nb_en_cours,
- avg(extract(epoch from (m.cloturee_le - m.created_at)) / 86400)
-   filter (where m.cloturee_le is not null) as duree_moy_jours
+ count(*) filter (where m.statut = 'Faite') as nb_cloturees,
+ count(*) filter (where m.statut in ('Planifiée', 'À faire', 'En retard')) as nb_en_cours,
+ avg(m.date_realisee - m.created_at::date)
+   filter (where m.date_realisee is not null) as duree_moy_jours

Au passage, la nouvelle formule date - date retourne directement un int en jours, plus simple et plus correct que l'extract(epoch …)/86400 qui avait des arrondis flottants.

Vérif que le front maintenance est resté cohérent (depuis le début il utilise bien les vrais statuts "Faite", "À faire", "En retard") — seul mon SQL était erroné.

Leçon : avant d'écrire une vue SQL agrégeant une table métier, faire un grep -A 20 "create table.*<table>" supabase/*.sql pour vérifier les vrais noms de colonnes et les valeurs de statuts attendues.

3 Test — bug DST sur calcul de récurrence

Échec test à l'exécution locale chez toi (Marne-la-Vallée, UTC+2 en été) :

FAIL __tests__/v041-features.test.js > Récurrences maintenance > dernière + 90j
AssertionError: expected '2026-03-31' to be '2026-04-01'
  - Expected: 2026-04-01
  + Received: 2026-03-31

Cause : bug DST classique. Le calcul traversait le passage à l'heure d'été du 29 mars 2026 :

new Date("2026-01-01")            → 2026-01-01T00:00:00Z (UTC)
                                    = 2026-01-01T01:00:00 local (UTC+1, heure hiver)
setDate(getDate() + 90)            → 91e jour calculé en local
                                    = 1 avril 01:00 local
                                    MAIS le 1er avril on est en UTC+2 (heure été)
UTC                                = 2026-03-31T23:00:00Z   ← perd 1h !
toISOString().slice(0, 10)         → "2026-03-31"   ✗

Correction : arithmétique en millisecondes directement, qui ne traverse aucun fuseau local.

- function calcProchaine(derniere, frequence_jours) {
-   if (!derniere || !frequence_jours) return null;
-   const next = new Date(derniere);
-   next.setDate(next.getDate() + frequence_jours);
-   return next.toISOString().slice(0, 10);
- }
+ function calcProchaine(derniere, frequence_jours) {
+   if (!derniere || !frequence_jours) return null;
+   const t = new Date(derniere).getTime();
+   return new Date(t + frequence_jours * 86400000)
+     .toISOString().slice(0, 10);
+ }

Impact : test uniquement. La fonction n'est pas utilisée dans le code de prod (helper de test). La table maintenance_recurrences a un champ prochaine_due qui pourra être calculé côté SQL (derniere_realisee + frequence_jours) sans aucun souci de fuseau.

Leçon : pour toute arithmétique de date en JS, préférer getTime() + n*86400000 à setDate(getDate() + n). Le piège ne se manifeste qu'au passage de DST mais le test devient flaky selon le fuseau ET la date d'exécution.

À retenir pour les prochaines versions

Trois grep réflexes à faire avant d'écrire du SQL ou des dates :

  1. Pattern RLS : 
    grep "create policy.*structure_id" supabase/*.sql | head -5
    → identifier le helper exact (ici mes_structures()) et coller le pattern.
  2. Schéma d'une table : 
    grep -A 20 "create table if not exists <table>" supabase/*.sql
    → vérifier les vrais noms de colonnes et les valeurs de statuts utilisées.
  3. Dates en JS :
    • Pour additionner des jours : new Date(t.getTime() + n * 86400000)
    • Pour parser une date ISO en UTC sans bonus local : new Date(s + "T00:00:00Z")
    • Éviter setDate(getDate() + n) dès qu'on traverse mars ou octobre (DST en zone Europe)
