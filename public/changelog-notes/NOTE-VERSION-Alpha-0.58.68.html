🚨 Fix critique : Changelog page n'affichait plus les nouvelles versionsCache HTTP infini résolu par cache-busting via version

Date : 6 juin 2026 Version : v0.58.68-alpha Sévérité : Critique 🔴 Impact : Toutes les MAJ depuis 0.57.11 invisibles sur la page changelog

🚨 Symptôme rapporté

"les changelog sur la pge du soft manque plein de maj tu poublie de les mettre a chaque fois" — Cédric

Les versions 0.58.x récentes (.60, .61, .62, .63, .64, .65, .66, .67) n'apparaissaient pas dans la page /changelog du soft en prod, alors qu'elles étaient bien déployées et présentes dans les fichiers source.

🔍 Diagnostic

Le code de la page changelog a évolué en 0.57.11 : le fichier versions-index.js (qui contenait toutes les versions sous forme de constante JS dans le bundle) a été scindé en :

  • app/changelog/versions-index.js : ne contient plus que les THEME_LABELS (~2 KB)
  • public/changelog-data/versions-index.json : contient toutes les versions (~836 KB), fetché en lazy au mount de la page

Cette refonte avait pour but de réduire le bundle initial de -269 KB (-84 KB après gzip). Excellent gain de perf ! Mais le fetch utilisait cache: "force-cache" :

// app/changelog/page.js (0.57.11 → 0.58.67)
const [versionsRes, extraRes] = await Promise.all([
  fetch("/changelog-data/versions-index.json", { cache: "force-cache" }),
  fetch("/changelog-data/chantiers-extra.json", { cache: "force-cache" }),
]);
❌ Comportement de force-cache Le navigateur utilise toujours la version en cache HTTP, sans même valider auprès du serveur. C'est l'équivalent de max-age=infinity, immutable.
🐛 Conséquence pratique À la première visite, le JSON est mis en cache. Aux releases suivantes, même si le fichier sur le serveur a changé, le navigateur ne le sait pas et continue d'afficher l'ancienne liste de versions.

✅ Fix appliqué

Cache-busting par version : on ajoute ?v=0.58.68 à l'URL. À chaque release, la version change → l'URL change → le navigateur considère que c'est un nouveau fichier → re-fetch frais. Et cache: "default" respecte les Cache-Control normaux (cache pour les performances mais avec revalidation).

// 0.58.68 - app/changelog/page.js
import pkg from '../../package.json';

useEffect(() => {
  (async () => {
    const v = pkg.version || 'dev';  // ← 0.58.68 ici
    const [versionsRes, extraRes] = await Promise.all([
      fetch(`/changelog-data/versions-index.json?v=${encodeURIComponent(v)}`, { cache: 'default' }),
      fetch(`/changelog-data/chantiers-extra.json?v=${encodeURIComponent(v)}`, { cache: 'default' }),
    ]);
    // ...
  })();
}, []);
✅ cache: "default" Le navigateur cache normalement (selon les headers Cache-Control du serveur Vercel) mais revalide à expiration. Pas de cache infini accidentel.
✅ Cache-busting ?v=0.58.68 À chaque release, l'URL change. Le navigateur voit un nouveau fichier et le re-fetch. L'ancien JSON cached reste en cache (différente URL) mais n'est plus matché.

🧊 Bonus : SW VERSION bumpé

Le Service Worker (public/sw.js) a aussi sa propre version (utilisée comme préfixe des Cache Storage). En la bumpant à aveho-ec-0.58.68, on force le SW à jeter tout son cache et à re-télécharger les ressources au prochain reload. Belt-and-suspenders : navigateur + SW invalidés simultanément.

📚 Leçon pour la suite

cache: "force-cache" est seulement approprié pour des assets vraiment immutables :

  • ✅ Fichiers JS/CSS avec hash dans le nom : bundle-a8f3e2.js (le hash change quand le contenu change → nouveau nom)
  • ✅ Images /static/img-12345.webp qui ne changent jamais
  • ❌ JSON qui contient des données mutables (changelog, config, etc.) qui gardent le même nom de fichier

Pour ces derniers, soit on met un hash dans le nom, soit on fait du cache-busting via query string comme ici. cache: "default" est suffisant côté JS.
