🔧 1. Fix warning CSP upgrade-insecure-requests

Symptôme dans la console DevTools :

The Content Security Policy directive 'upgrade-insecure-requests'
is ignored when delivered in a report-only policy.

Explication

La directive upgrade-insecure-requests force les browsers à upgrader automatiquement les ressources HTTP en HTTPS. Mais elle ne peut être appliquée qu'en mode enforcing (Content-Security-Policy) — en mode report-only (Content-Security-Policy-Report-Only) elle est ignorée silencieusement avec ce warning.

Comme on est en mode report-only depuis la 0.57.17 (pour observer sans casser), la directive est inutile. Et même : la protection est déjà couverte par HSTS preload 1 an qui force HTTPS au niveau navigateur AVANT que la CSP soit évaluée.

Fix

// 0.57.22 — retirée du tableau CSP_DIRECTIVES
const CSP_DIRECTIVES = [
  "default-src 'self'",
  // ... 11 autres directives
  "frame-ancestors 'self'",
  // 0.57.22 : 'upgrade-insecure-requests' RETIRÉE car ignorée en report-only
  // (warning browser : "ignored when delivered in a report-only policy")
  // Protection couverte par HSTS max-age=1 an + preload
  // À réintroduire si/quand on bascule en CSP enforcing.
];

Résultat : console DevTools propre, 10/10 headers sécurité maintenus, HTTPS toujours forcé par HSTS.

📬 2. Tracking statut envoi mail des invitations

Problème signalé

"les statuts d'envoi de mail sur la liste des invitations et plusieurs étapes set soit fonctionnel"

Avant cette version, le workflow d'invitation était :

  1. User clique "Inviter" dans /utilisateurs
  2. Insert dans table invitations avec un token
  3. Appel Edge Function invite-user qui envoie via Resend
  4. Si succès : popup "Invitation créée"
  5. Si échec : warning UI temporaire (mailWarning)
  6. Mais aucune trace en BDD du succès/échec

Résultat : impossible de savoir plus tard si le mail est parti ou pas. Le warning UI disparaît au reload, et la table invitations n'a aucune colonne de tracking.

Solution : 3 colonnes + affichage

ColonneTypeSens
mail_envoye_atTIMESTAMPTZ NULLDate d'envoi réussi (NULL = pas envoyé)
mail_erreurTEXT NULLMessage d'erreur Resend si échec
mail_tentativesINTEGER DEFAULT 0Nombre total d'essais

Affichage dans la liste :

  • Envoyé si mail_envoye_at IS NOT NULL (tooltip avec date + tentatives)
  • Échec si mail_erreur IS NOT NULL (tooltip avec détail erreur Resend)
  • — sinon (invitations avant 0.57.22)

🚀 Workflow d'application

  1. 📸 Snapshot Supabase (par précaution)
  2. SQL Editor → coller supabase/aveho-PATCH-vers-0.57.22.sql
  3. Lancer le patch (idempotent, peut être relancé sans problème) :
    • ALTER TABLE x3 (ADD COLUMN IF NOT EXISTS)
    • Backfill mail_tentatives=1 pour les invitations > 1h
    • CREATE INDEX partiel sur mail_erreur
    • COMMENT ON COLUMN x3 (documentation)
  4. Vérifier dans la table invitations que les 3 colonnes apparaissent (Supabase Dashboard → Table Editor)
  5. Tester côté app :
    • Créer une invitation avec un email valide → colonne "Mail" affiche Envoyé
    • Créer une invitation avec un email invalide → Échec avec tooltip détaillé
    • Cliquer sur le bouton renvoi → le compteur tentatives s'incrémente

📊 Stats SQL livrées dans le patch

Le patch inclut une requête de stats post-migration que tu peux relancer à tout moment :

SELECT
  COUNT(*) AS total,
  COUNT(*) FILTER (WHERE mail_envoye_at IS NOT NULL) AS mails_envoyes,
  COUNT(*) FILTER (WHERE mail_erreur IS NOT NULL) AS mails_en_echec,
  COUNT(*) FILTER (WHERE mail_envoye_at IS NULL AND mail_erreur IS NULL) AS jamais_tente,
  AVG(mail_tentatives) AS moyenne_tentatives
FROM public.invitations;

Te permet de mesurer la santé de tes envois mail au fil du temps.
