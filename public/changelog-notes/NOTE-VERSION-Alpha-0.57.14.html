📸 Pourquoi du visual regression testing ?

Les tests unitaires Vitest vérifient la logique. Les tests E2E Playwright vérifient le comportement. Mais ni les uns ni les autres ne détectent les régressions visuelles :

  • Un padding qui passe de 12px à 14px → personne ne le remarque tant que ce n'est pas signalé
  • Une couleur primaire qui dérive de #185FA5 vers #2070B0 → idem
  • Une font qui ne charge pas → fallback Arial à la place de Quicksand → "ça a l'air bizarre"
  • Un alignement qui casse après un refacto CSS → bug invisible jusqu'à ce qu'un user le voie

Le visual regression testing prend des screenshots de référence (baselines) et compare pixel-par-pixel à chaque commit. Tout changement visuel est automatiquement détecté.

📋 Workflow utilisateur

# 1. La 1ère fois (ou après refonte UI volontaire)
npm run test:visual:update
# → Génère/écrase les baselines dans tests/e2e/__screenshots__/

# 2. À chaque commit suivant
npm run test:visual
# → Compare le rendu actuel aux baselines, FAIL si diff > tolérance

# 3. Si FAIL : voir le diff dans test-results/<test>/<name>-diff.png
#    - Si c'est une régression bug : fixer le code
#    - Si c'est intentionnel : relancer test:visual:update + commit

🛡️ Difficultés résolues

1. Popup géoloc qui bloque le viewport

Au 1er load, Aveho affiche un modal "Activer la géolocalisation ?" qui couvre tout le viewport central. Sans handling, les baselines screenshotent le popup au lieu de la page.

Solution : Helper setupPopupsSkip(context) qui utilise context.addInitScript() pour pré-remplir le localStorage AVANT le 1er render JS :

async function setupPopupsSkip(context) {
  await context.addInitScript(() => {
    localStorage.setItem("aveho_geoloc_choice", "declined");
    localStorage.setItem("aveho_biometric_optin_shown", "1");
    localStorage.setItem("aveho_install_banner_dismissed", "1");
  });
}

test.beforeEach(async ({ context }) => {
  await setupPopupsSkip(context);  // Avant chaque test
});

2. Numéros de version variables

Le badge "Version Alpha 0.57.X" change à chaque bump → baseline cassée systématiquement.

Solution : injection CSS qui masque les éléments de version :

[class*="version" i], [data-version] { visibility: hidden !important; }

3. Pas de balise <form> dans Aveho login

Le composant Login est un div React avec onClick. Impossible de faire page.locator("form").

Solution : xpath ancestor depuis l'input email :

const card = page.locator("input[type='email']")
  .locator("xpath=ancestor::div[2]");

4. Pages longues instables (variance subpixel)

La note HTML 0.55.0 fait 5800 px de haut. Entre 2 runs, font-rendering subpixel produit ~18 px de différence → fail systématique en fullPage.

Solution : clip sur le header stable :

await expect(page).toHaveScreenshot("note-header.png", {
  clip: { x: 0, y: 0, width: 1280, height: 800 },
  maxDiffPixels: 200,
});

5. Email pré-rempli par localStorage Aveho

Aveho mémorise le dernier email saisi → conflit avec mon fill("demo@aveho.fr").

Solution : clear() avant fill()

⚙️ Configuration Playwright

// playwright.config.js — bloc expect
expect: {
  timeout: 5000,
  toHaveScreenshot: {
    maxDiffPixelRatio: 0.002,  // 0.2 % de diff tolérée par défaut
    animations: "disabled",     // double sécurité (en plus de notre CSS)
    caret: "hide",              // cache le curseur clignotant
  },
},

// Path standardisé des baselines
snapshotPathTemplate: "{testDir}/__screenshots__/{testFileName}/{arg}{ext}"

Helper prepareForScreenshot

async function prepareForScreenshot(page) {
  // 1. Désactiver toutes les animations
  await page.addStyleTag({
    content: `
      *, *::before, *::after {
        animation-duration: 0s !important;
        transition-duration: 0s !important;
      }
      *:focus { outline: none !important; }
      [class*="version" i] { visibility: hidden !important; }
    `,
  });
  // 2. Attendre que les fonts soient chargées
  await page.evaluate(() => document.fonts.ready);
  // 3. Stabilisation finale
  await page.waitForTimeout(300);
}

🎬 Particularités techniques

  • Chromium uniquement : les screenshots ne sont pas portables Firefox/WebKit (font-rendering, antialiasing, sub-pixel positioning différents). Le spec a un test.skip(browserName !== "chromium", ...) au niveau de chaque describe
  • Tolérance par test : maxDiffPixels: 100 desktop, 150 mobile. La différence est plus grande qu'attendue car les fonts mobiles ont plus de variance
  • 2 runs successifs sans regen → 7/7 passed = stabilité confirmée. Si on relance 10 fois, ça passe 10 fois
  • Baselines versionnées dans git : 2.5 MB pour l'instant, gérable. Si on étend à plus de 50 baselines, envisager Git LFS
