1. Résumé exécutif

L'Alpha 0.2 enrichit les fondations posées en 0.1 sans ajouter de nouveau module métier — elle termine ce qui était en chantier. Les utilisateurs gagnent enfin la possibilité de gérer la hiérarchie de leur établissement depuis l'interface (plus besoin de SQL), les pop-ups deviennent homogènes et reconnaissables, et les droits définis dans les rôles s'appliquent réellement dans l'UI.

Priorisation transparente : la roadmap Alpha 0.2 comptait 10 chantiers. Cette version en livre 6 à fort impact immédiat. Les 4 chantiers restants (RLS étanche, domaine email, notifications, mode hors-ligne) sont reportés en Alpha 0.3 car ils nécessitent un travail spécialisé qui aurait été bâclé en lot avec le reste.

3. Détail des nouveautés

3.1 Page Édition de la hiérarchie NOUVEAU

Route : /etablissement/edition — accessible depuis le menu (sous "Mon établissement") ou directement par lien.

Fonctionnement : la page affiche l'arborescence complète de l'établissement courant (bâtiments → étages → services → chambres → lits) avec, à chaque niveau, des actions Ajouter / Modifier / Supprimer. Une seule modale unifiée gère tous les types de création/édition, avec champs spécifiques (niveau pour les étages, type pour les services).

Garde-fou : la page vérifie la permission editer_hierarchie. Un utilisateur en "Lecture seule" voit un message d'accès refusé.

Impact : finie la nécessité de passer par SQL Editor pour créer une chambre. Les utilisateurs métier gèrent eux-mêmes leur établissement.

3.2 Décrément automatique du stock NOUVEAU

Au passage d'un transfert en statut Reçu, si le transfert porte un article entre deux dépôts, la fonction advance() de la page transferts :

  • Décrémente la quantité de l'article dans stock_articles côté dépôt source (sans descendre sous zéro)
  • Incrémente la quantité côté dépôt destination (création de la ligne si elle n'existait pas)

Les transferts vers une chambre, un patient ou un emplacement non-dépôt ne déclenchent pas de mouvement de stock — c'est volontaire (ils sortent du périmètre stock).

4. Système UI unifié

Tous les composants UI partagés ont été regroupés et standardisés dans app/ui.js.

4.1 Table ENTITY — référentiel visuel des entités

Une table centrale associe chaque type d'objet (patient, matériel, dépôt, DI, etc.) à une icône Tabler et une couleur. C'est cette table qui pilote la cohérence visuelle dans toute l'appli.

// Extrait simplifié
ENTITY = {
  patient:   { ic: "ti-user",          color: "#7a6fb0", label: "Patient" },
  materiel:  { ic: "ti-armchair-2",    color: "#142131", label: "Matériel" },
  depot:     { ic: "ti-building-warehouse", color: "#EF9F27", label: "Dépôt" },
  di:        { ic: "ti-tools",         color: "#e35d5b", label: "DI" },
  commande:  { ic: "ti-shopping-bag",  color: "#2a5a5a", label: "Commande" },
  // ... 23 types au total
}

4.2 Composant <Modal> v2

Une seule modale unifiée pour toute l'appli :

  • En-tête coloré selon le type d'entité (la modale "patient" est violette, "matériel" est navy, etc.)
  • Icône de l'entité en haut à gauche de la modale
  • Animation à l'ouverture (subtle slide-up + fade)
  • Bottom-sheet automatique sur mobile (pleine largeur, depuis le bas)
  • Footer flexible pour les boutons d'action

                  <Btn variant="primary" onClick={save}>Enregistrer</Btn></>}>

5. Application des droits de rôle

5.1 Helper auth.can(action)

Le hook useAuth charge maintenant le rôle effectif de l'utilisateur dans la collectivité (table roles liée via membres_structure.role_id), et expose un helper :

const auth = useAuth();
auth.can("ecrire")       // peut créer/modifier ?
auth.can("supprimer")    // peut supprimer ?
auth.can("inviter")      // peut inviter des utilisateurs ?
auth.can("editer_hierarchie")  // peut gérer bâtiments/chambres ?
// ... etc.

5.2 Mapping action → permission

ActionPermission requise

5.3 Raccourcis rôles système

  • "Administrateur" (ou role.systeme === "admin") → toutes les actions autorisées
  • "Lecture seule" (ou role.systeme === "lecture") → aucune action d'écriture
  • Autres rôles → vérifient leur permissions_json (tableau de permissions explicites)

5.4 Application UI

Les composants <Crud> et les pages refondues (Patients notamment) acceptent des props canWrite / canDelete. Les boutons "Nouveau", "Modifier", "Supprimer" disparaissent visuellement quand le rôle ne le permet pas.

8. Procédure de mise à jour depuis Alpha 0.1

Bonne nouvelle : aucune migration SQL nécessaire pour cette version. Les tables existantes (notamment roles et membres_structure) sont suffisantes.

  1. Sauvegarde ton dossier C:\aveho-ec-app par sécurité (Copier/Coller, ou ZIP).
  2. Télécharge le nouveau aveho-ec-app.zip, décompresse-le par-dessus l'ancien dossier (écrase les fichiers).
  3. Dans PowerShell :
    cd C:\aveho-ec-app
npm install
npm run dev
  4. Test en local : ouvre http://localhost:3000, connecte-toi, vérifie que tu vois "Édition hiérarchie" dans le menu et que les modales ont le nouveau look.
  5. Mise en ligne Vercel : 
    git add .
git commit -m "Aveho EC Alpha 0.2"
git push
    Vercel redéploie automatiquement.

9. Chantiers reportés en Alpha 0.3 — pourquoi

Je préfère reporter plutôt que livrer mal. Voici les raisons honnêtes du report :

ChantierRaison du report
RLS étanche par établissement/serviceSécurité critique. Une mauvaise politique RLS peut soit bloquer tout, soit laisser passer ce qui ne devrait pas. Mérite un chantier dédié avec tests d'accès par rôle.
Domaine email pro chez ResendDépend de l'acquisition d'un nom de domaine (~10€/an chez OVH, Gandi…). Tant que tu n'as pas de domaine, on reste sur onboarding@resend.dev qui fonctionne pour le test.
Notifications in-appNouvelle table notifications + UI temps réel (cloche dans la TopBar + panneau déroulant). Travail de qualité demande 2-3h de soin.
Mode hors-ligne PWARefonte complète du service worker avec stratégie cache (network-first / cache-first par type de ressource), gestion des conflits offline→online. Chantier qui mérite isolé.

10. Roadmap Alpha 0.3

Reprise des 4 chantiers reportés + chantiers nouveaux issus du retour Alpha 0.2 :

  1. RLS étanche par établissement — sécurité d'abord
  2. Notifications in-app (cloche) — transferts validés, DI assignées, invitations acceptées
  3. Domaine email pro — dès qu'un domaine sera disponible
  4. Mode hors-ligne PWA — consultation possible sans réseau
  5. Application des droits sur toutes les pages (l'Alpha 0.2 a fait Patients + Crud génériques, reste à étendre aux pages spécifiques)
  6. Export Excel / PDF sur les listes principales (patients, matériel, stock, commandes)
  7. Recherche globale (barre en haut, cherche dans patients, matériels, articles, commandes)
  8. Page paramètres collectivité : préférences d'affichage, libellés métier personnalisables
