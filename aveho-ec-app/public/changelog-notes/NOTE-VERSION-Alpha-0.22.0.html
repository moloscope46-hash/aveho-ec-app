1. Résumé exécutif

La 0.22.0 finalise l'axe RGPD professionnel avec 3 chantiers à forte valeur d'audit CNIL :

  1. Export PDF du consentement via jsPDF chargé en CDN (~50 KB en lazy load). PDF A4 complet : bandeau navy, identité patient/établissement, texte intégral, signature image intégrée, métadonnées (hash SHA-256, recueilli par, date, device), QR code de vérification, footer avec pagination.
  2. QR code de vérification d'intégrité sur chaque PDF. Scan → page publique /verifier/?h= qui appelle une RPC Postgres verify_consent_hash(). La RPC compare le hash, retourne un statut minimal (initiales anonymisées + dates + établissement) et trace la vérification dans une table d'audit.
  3. Renouvellement automatique : date_expiration calculée à signature (= +3 ans). Filtre "À renouveler" sur la page /consentements avec les expirations < 30 jours. KPIs dédiés. Bouton "Demander renouvellement" pour traçabilité.
Audit CNIL ready. Avec cette release, le module RGPD couvre tous les exigences de conformité : consentement écrit, signé, daté, archivé, vérifiable publiquement, renouvelé périodiquement, immuable (pas de DELETE possible), entièrement tracé.

3. Export PDF du consentement

3.1 Architecture

jsPDF chargé via CDN cdn.jsdelivr.net/npm/jspdf@2.5.2 en lazy load (cohérent avec la stratégie SheetJS de la 0.15+). Aucun ajout au bundle initial — le module se charge uniquement quand l'utilisateur clique sur le bouton PDF.

3.2 Structure du PDF

  • Bandeau navy en en-tête avec titre "CONSENTEMENT RGPD" + collectivité/établissement
  • Encadré identité patient (nom, naissance, dossier) avec badge statut signé/refusé + date d'expiration
  • Texte intégral du consentement rendu en typographie A4 (Helvetica 9pt), gestion automatique des paragraphes, sous-titres bold, listes à puces, séparateurs horizontaux
  • Pagination automatique : ajout de pages si le contenu déborde
  • Bloc signature : image PNG de la signature (chargée via URL signée Storage 5 min) à gauche, métadonnées à droite (signataire, rôle, date, recueilli par, hash SHA-256 sur 2 lignes en courier)
  • QR code de vérification (si signé + hash dispo) avec description + URL en clair sous le code
  • Footer sur chaque page : nom Aveho/collectivité à gauche, "Page X / Y" à droite, "Document généré le ..."

3.3 Nom de fichier généré

consentement-rgpd-{patient-slug}-{YYYY-MM-DD}.pdf
ex : consentement-rgpd-marie-dupont-2026-05-30.pdf

Le slug retire les accents (NFD + normalize), met en minuscules, remplace tout non-alphanumérique par des tirets.

3.4 Markdown → PDF

jsPDF ne sait pas interpréter le markdown du template. La fonction interne markdownToPlainBlocks transforme le markdown léger en blocs typés :

  • {type: "p", text} → paragraphe
  • {type: "h", text} → sous-titre (bold + bleu)
  • {type: "li", text} → puce
  • {type: "hr"} → séparateur horizontal

Les **gras** intra-ligne sont retirés (jsPDF ne supporte pas le rich-text inline simplement). Pour de vrai bold inline, il faudrait utiliser doc.text() mot par mot avec changement de style — overkill pour la valeur ajoutée.

4. QR code & vérification publique

4.1 Workflow utilisateur

  1. L'utilisateur télécharge le PDF du consentement
  2. Il imprime le PDF pour archive papier ou l'envoie à un auditeur/CNIL
  3. Pour vérifier l'authenticité, l'auditeur scanne le QR avec son smartphone
  4. Le navigateur ouvre https://aveho-app.vercel.app/verifier/<id>?h=<hash>
  5. La page appelle la RPC verify_consent_hash(consent_id, hash, ip, ua)
  6. La RPC compare le hash en base avec celui fourni dans l'URL
  7. Trace la vérification dans consent_verifications
  8. Affiche :
    • ✓ Vert : Consentement authentique (hash correspond, pas expiré)
    • ⏰ Orange : Authentique mais expiré (renouvellement nécessaire)
    • ✗ Rouge : Le hash ne correspond pas (altération potentielle)

4.2 Sécurité & anonymisation

La page publique n'expose aucune donnée personnelle complète :

  • Patient : seules ses initiales sont retournées par la RPC (anonymisation)
  • Établissement et collectivité : noms publics (déjà visibles dans des annuaires officiels comme FINESS)
  • Dates : OK pour l'audit
  • Le texte complet du consentement n'est jamais retourné
  • Pas de nom de signataire, pas de N° dossier, pas de date de naissance

4.3 RPC verify_consent_hash

Définie avec SECURITY DEFINER + GRANT EXECUTE TO anon → accessible sans authentification. La trace dans consent_verifications est insérée par la RPC elle-même (en bypass RLS via SECURITY DEFINER), donc impossible de scanner sans laisser trace.

4.4 Page /verifier/[id]

Composant React client-side léger (2.2 kB) sans dépendances Aveho (pas de TopBar, pas d'auth). Design plein écran avec gradient navy → teal pour un effet "page de vérification officielle". 5 états :

  • loading : "Vérification en cours..."
  • missing : URL incomplète (id ou hash manquant)
  • valid : ✓ vert ou ⏰ orange si expiré
  • invalid : ✗ rouge "Vérification échouée"
  • error : Erreur technique RPC

5. Renouvellement automatique

5.1 Date d'expiration

Calculée côté frontend à la signature : date_signature + 3 ans. Stockée en colonne date_expiration date. Index partial idx_consent_expiration pour optimiser les vues.

5.2 Vues SQL d'aide

  • v_consents_a_renouveler : consentements signés non archivés dont l'expiration ≤ 30 jours mais non encore expirés. Trié par échéance ascendante.
  • v_consents_expires : consentements dont la date d'expiration est dépassée + nombre de jours depuis expiration.

5.3 UI /consentements

Modifications visibles :

  • KPIs refondus : Signés / À renouveler / Expirés / Refusés (au lieu de "7 derniers jours")
  • Filtre "À renouveler" : nouvelle option du FilterBar avec compteur. Sélectionne les expire ≤ 30j OU les renouvellement_demande=true.
  • Colonne "Expiration" dans le tableau, remplaçant "Recueilli par" (déplacé dans la modale de détail). Couleurs : vert (sain), orange (≤ 30j), rouge (expiré).
  • Badge "Renouv. demandé" sur les lignes concernées
  • Icône ti-refresh dans les actions ligne quand l'expiration approche ou est dépassée
  • Bouton "Demander renouvellement" dans la modale de visualisation

6. Patch SQL 0.22.0

Le script aveho-PATCH-vers-0.22.sql (193 lignes) effectue :

  1. ALTER TABLE consentements_rgpd : 4 colonnes ajoutées
  2. Backfill date_expiration pour les consentements existants (= signature + 3 ans)
  3. Index partial idx_consent_expiration
  4. Table consent_verifications + indices + RLS select
  5. RPC verify_consent_hash SECURITY DEFINER + GRANT anon/authenticated
  6. Vues v_consents_a_renouveler + v_consents_expires

Idempotent (if not exists, create or replace). Rejouable.

7. Tests Vitest (+7)

7 nouveaux tests sur lib/qrcode.js :

  • buildVerifyUrl : construit l'URL avec l'origin, encode les caractères spéciaux, gère le SSR (window indéfini), préserve UUID et hash SHA-256, génère une URL parsable par new URL()

9. Procédure d'application

  1. SQL d'abord dans Supabase → SQL Editor → coller aveho-PATCH-vers-0.22.sql → Run.
  2. Vérifier les vues : 
    select count(*) from v_consents_a_renouveler;
select count(*) from v_consents_expires;
  3. Décompresser le zip par-dessus C:\aveho-ec-app (garder .env.local).
  4. npm install + tests + dev : 
    cd C:\aveho-ec-app
npm install
npm test       # 94 passed
npm run dev
  5. Tester :
    • Aller dans /consentements → les KPIs ont changé, la colonne Expiration apparaît
    • Cliquer sur l'icône PDF rouge d'une ligne → le PDF se télécharge avec signature + QR code
    • Scanner le QR avec ton téléphone → page /verifier/... qui valide
    • Cliquer "Demander renouvellement" sur un consentement → badge apparaît + dispo dans le filtre
    • Pour tester le filtre "À renouveler" : forcer une expiration proche en SQL : 
      update consentements_rgpd
set date_expiration = current_date + 15
where id = '...';
  6. Pousser sur Vercel.
