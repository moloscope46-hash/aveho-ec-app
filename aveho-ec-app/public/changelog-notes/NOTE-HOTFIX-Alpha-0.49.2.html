1 Hydration mismatch sur OfflineBanner

Erreur au load de n'importe quelle page :

Unhandled Runtime Error
Error: Hydration failed because the initial UI does not match what was rendered on the server.
Expected server HTML to contain a matching <div> in <body>.
<RootLayout>
  <html>
    <body>
      <OfflineBanner>
        <div>
        ^^^^^

Diagnostic : React compare ce que le serveur a rendu (HTML envoyé au navigateur) avec ce que le client rend après hydration. Si les deux divergent → erreur.

Le composant OfflineBanner contient :

// Rien à afficher si online + queue vide
if (online && queueCount === 0 && !syncing) return null;

Côté serveur : online par défaut à true, queueCount = 0, syncing = false → return null. Le serveur ne rend RIEN.

Côté client au moment de l'hydration : le hook useOffline a déjà lu navigator.onLine, et selon l'état (offline détecté juste à temps, queue non vide depuis IndexedDB, etc.) le composant peut commencer à rendre un <div>. → mismatch.

Solution — pattern hydration-safe standard React :

  export default function OfflineBanner() {
    const auth = useAuth();
    const { online, queueCount, syncing, ... } = useOffline(userId);
+   // Alpha 0.49.2 : hydration-safe
+   const [mounted, setMounted] = useState(false);
+   useEffect(() => { setMounted(true); }, []);
    
    useEffect(() => { ... }, [showModal, getQueueItems, queueCount]);
    
+   // Tant qu'on n'est pas côté client → null (cohérent avec SSR)
+   if (!mounted) return null;
    
    if (online && queueCount === 0 && !syncing) return null;
    return (
      <> ... </>
    );
  }

Audit des autres composants client dans le layout :

  • InstallPWA : retourne null en static (juste un useEffect pour enregistrer le SW) — pas de risque
  • LectureSeuleBadge : retourne null en static (juste un useEffect pour set un attribute sur body) — pas de risque
  • GlobalSearch : if (!open) return null; au début, et open est false par défaut — pas de risque
  • InstallBanner : a déjà un useState(show) qui démarre à false → pas de risque
  • VersionCheck : a déjà 4 guards typeof window === "undefined" → pas de risque
  • OfflineBanner : seul à risque, fixé

2 Avatar utilisateur hors écran mobile

En 0.49 j'ai ajouté le badge version à côté du logo dans la TopBar. Sur les écrans entre 521 et 900px (tablettes + grands mobiles paysage), tous les éléments restaient affichés simultanément :

  • Burger (40px) + Logo (~120px) + Badge version (~80px nouveau) + Titre page + Search button + Etab-switch + NotifBell + Panier + UserMenu = beaucoup trop pour la largeur dispo
  • Le débordement poussait l'avatar utilisateur hors écran à droite

Correction CSS :

  /* Alpha 0.49.0 : badge version dans la TopBar */
  .version-badge{font-size:10px;font-weight:700;...}
  .version-badge:hover{background:rgba(124,200,200,.28);color:#fff}
- @media(max-width:520px){.version-badge{display:none}}
+ /* Alpha 0.49.1/2 : caché sur tablette/mobile pour ne pas pousser UserMenu hors écran */
+ @media(max-width:900px){.version-badge{display:none}}

- .topbar{... display:flex; ...position:sticky; ...z-index:40}
+ .topbar{... display:flex; ...position:sticky; ...z-index:40; overflow:hidden}

Le badge reste visible sur desktop large (≥900px). Sur mobile, l'info reste accessible via :

  • Le menu profil (qui inclut un lien vers /profil)
  • La future route /changelog qui sera dédiée à l'historique des versions

3 Procédures terminal : PowerShell pur

Tu es sur Windows, dans le terminal cmd.exe (et tu utilises parfois PowerShell). Je mélangeais les deux dans mes procédures, ce qui cassait :

  • Remove-Item -Recurse -Force .next → ne marche qu'en PowerShell, pas en cmd.exe
  • npm test # 869 passed → en cmd.exe le # n'est pas un commentaire, vitest le voit comme un filtre
  • npm install && npm test → en PowerShell ≤5.x, && n'existe pas (juste depuis PS 7)

Convention adoptée : à partir de la 0.49.2, toutes les procédures sont en PowerShell pur. Tape powershell dans cmd.exe pour basculer si nécessaire.

Procédure d'application — PowerShell

  1. Ouvrir PowerShell (Démarrer → "PowerShell")
  2. Décompresser le nouveau zip par-dessus C:\aveho-ec-app\
  3. Installer & lancer : 
    cd C:\aveho-ec-app
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue
npm install
npm test
npm run dev
    Attendu : 869 tests verts, plus d'erreur d'hydration.
  4. Pour le bouton "Installer l'appli" qui ne s'affichait plus (à faire dans DevTools Chrome, pas PowerShell) :
    1. DevTools (F12) → onglet Application
    2. Section Service Workers → cliquer Unregister sur celui d'Aveho
    3. Section Storage en haut → bouton Clear site data (coche tout)
    4. Fermer tous les onglets vers localhost:3000
    5. Ouvrir une nouvelle fenêtre Chrome → localhost:3000
    6. Login + attendre 30 secondes sur la page (Chrome attend "user engagement")
    7. Le bouton "Télécharger l'appli" doit reparaître dans le menu user en haut à droite

9ᵉ réflexe — Tout composant client qui lit navigator.* / window.* / localStorage avant un éventuel return null conditionnel doit avoir un guard mounted state pour éviter les hydration mismatch React. Pattern :

const [mounted, setMounted] = useState(false);
useEffect(() => { setMounted(true); }, []);
if (!mounted) return null;
// Suite du composant qui peut lire navigator/window/localStorage
