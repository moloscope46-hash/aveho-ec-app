3. Fiche matériel 360° NOUVEAU

3.1 Accès

Sur la page Matériels, le libellé d'un matériel devient cliquable et ouvre sa fiche détaillée à l'URL /materiel/[id]. Le reste de la ligne reste sélectionnable pour l'édition rapide via le crayon comme avant.

3.2 Contenu de la fiche

Une page dédiée qui rassemble tout ce qu'on sait sur l'équipement, en 4 blocs :

  1. Entête — libellé, identifiants (S/N, parc, lot), article rattaché, tags actifs, état, dépôt, zone, patient affecté
  2. 4 KPIs — total maintenances, à venir/en cours, en retard, DI ouvertes
  3. Tableau Maintenances — toutes les maintenances liées au matériel (toutes dates, tous statuts) avec statut "En retard" calculé automatiquement
  4. Tableau DI — toutes les demandes d'intervention sur ce matériel, cliquables pour ouvrir /interventions
  5. Tableau Transferts — derniers 20 transferts (origine, destination, statut)

3.3 Cas d'usage

  • Audit pré-révision : "qu'a-t-on déjà fait sur ce lit ?" avant de planifier la prochaine
  • Conflit avec prestataire : on peut sortir tout l'historique d'un appareil en quelques clics
  • Retraçage : "d'où vient ce matériel ?" via le bloc transferts
  • Décision de fin de vie : tags + nombre de DI + maintenances accumulées donnent une vision claire

4. Export PDF planning Maintenance NOUVEAU

Sur la page /maintenance, un nouveau bouton Export PDF planning dans la toolbar permet d'imprimer ou enregistrer en PDF la liste des maintenances actuellement affichées (avec les filtres en cours).

Format du document

  • A4 portrait, marges 12 mm
  • En-tête Aveho avec eyebrow turquoise, titre "Planning Maintenance", nom de la collectivité et de l'établissement
  • Bandeau droit : nombre de maintenances + date d'édition
  • Tableau : Date prévue, Matériel (avec S/N/Parc/Lot en sous-ligne), Type, Intervenant, Statut (badge coloré)
  • Footer : "Document à transmettre au prestataire concerné"

Cas d'usage métier

  • Préparer un PDF pour Bureau Veritas = filtrer Type "Contrôle sécurité" + Export → un document pro
  • Préparer un envoi mensuel à Philips Healthcare pour leurs équipements = filtre matériel + Export
  • Réunion fournisseur : on arrive avec le PDF, ils voient tout d'un coup

5. Statistiques Maintenance NOUVEAU

La page /statistiques gagne une nouvelle section Maintenance qui s'affiche dès qu'il y a au moins une maintenance dans les 6 derniers mois. Trois graphes :

  1. Maintenances par mois (BarChart turquoise) — répartition sur les 6 derniers mois selon la date prévue. Permet de voir la charge de travail mensuelle.
  2. Répartition par statut (Donut) — Planifiée / À faire / Faite / En retard / Annulée avec le calcul "En retard" effectif (la date passée + non Faite/Annulée). Permet de mesurer la dérive.
  3. Top 5 types (barres horizontales) — quels types reviennent le plus souvent. Aide à identifier les chantiers récurrents pour les prestataires.

6. Signalements anonymes NOUVEAU

6.1 Concept

Une boîte à idées et problèmes terrain où n'importe quel membre de la collectivité peut déposer un signalement sans laisser de trace de qui l'a écrit. La signature est optionnelle : on peut signer si on veut être contacté en retour.

6.2 Modèle SQL

signalements (
  id, structure_id, etablissement_id,
  type,            -- "Problème" | "Idée" | "Question" | "Autre"
  titre, description,
  signature,       -- optionnel : nom/poste si l'auteur veut signer
  statut,          -- "Nouveau" | "En cours" | "Traité" | "Archivé"
  reponse,         -- réponse de la direction
  reponse_par,     -- qui a répondu (visible publiquement)
  reponse_le,
  created_at
  -- NOTE : pas de user_id. Volontaire pour garantir l'anonymat.
)

6.3 RLS spéciale

  • INSERT : tous les membres de la collectivité — pas de trace de l'auteur
  • SELECT : tous les membres voient tous les signalements (transparence)
  • UPDATE / DELETE : réservés aux Administrateurs (pour répondre, changer le statut, supprimer)

6.4 Interface

  • 4 KPIs cliquables en haut : Nouveau, En cours, Traité, Archivé (filtrage instantané)
  • Filtre par type dans la toolbar
  • Cartes au lieu d'un tableau : pour mettre en valeur le contenu lisible
  • Chaque carte affiche : type (badge coloré + icône), statut, date, signature ou "Anonyme" en italique, titre, description, et la réponse de l'administration en bloc vert si elle existe
  • Modale de création : "Ton signalement est anonyme par défaut" rappelé en bandeau, champ Signature optionnel en bas
  • Mode admin : bouton "Répondre" sur chaque carte → édition du statut + champ Réponse

6.5 Cas d'usage

  • Problèmes terrain sensibles : un soignant signale un dysfonctionnement sans risquer une retombée hiérarchique
  • Boîte à idées : tout le monde peut proposer une amélioration
  • Questions FAQ : les réponses servent à toute la collectivité
  • Le format "avec signature optionnelle" évite l'auto-censure tout en permettant le suivi quand l'auteur veut être contacté

7. Cron quotidien Supabase NOUVEAU

7.1 Pourquoi

Les automatismes de la 0.11 (création auto de DI quand maintenance en retard, notifs J-7) étaient déclenchés au chargement de la page Maintenance. Si personne n'ouvre l'app pendant une semaine de vacances, rien ne part. La 0.12 livre une Edge Function Supabase qui fait le même travail côté serveur, à programmer en tâche quotidienne.

7.2 Edge Function

Fichier supabase/functions/maintenance-daily-cron/index.ts. Au déclenchement :

  1. Détecte toutes les maintenances dans la fenêtre [aujourd'hui ; +7 jours] sans notif envoyée → notifie tous les membres de la collectivité + flag notif_j7_envoyee à true
  2. Détecte toutes les maintenances en retard sans DI liée → crée la DI + lie via di_id + notifie
  3. Retourne un JSON avec {ok, notifsEnvoyees, disCreees, erreurs}

7.3 Déploiement

# Dans le projet local
supabase functions deploy maintenance-daily-cron

# Dans Supabase SQL Editor, programmer pg_cron une seule fois
select cron.schedule(
  'maintenance-daily-cron',
  '0 6 * * *',   -- tous les jours à 6h UTC
  $$ select net.http_post(
       url := 'https://VOTRE_PROJET.supabase.co/functions/v1/maintenance-daily-cron',
       headers := jsonb_build_object('Authorization', 'Bearer VOTRE_SERVICE_ROLE_KEY')
     ); $$
);

7.4 Limites

  • Nécessite l'activation des extensions pg_cron et pg_net dans Supabase (Pro plan ou Free avec activation manuelle)
  • Le code reste idempotent : si le cron tombe en panne 3 jours, au prochain run il rattrape les maintenances en retard et les J-7 manqués
  • La détection au chargement de la page (0.11) reste active en plus du cron : double sécurité, anti-doublon assuré par les flags

10. Procédure de mise à jour depuis Alpha 0.11

  1. Sauvegarde ton dossier C:\aveho-ec-app.
  2. Décompresse le nouveau zip par-dessus.
  3. Dans Supabase SQL Editor : exécute supabase/16_signalements.sql.
  4. Optionnel mais recommandé : déploie l'Edge Function
    Si tu as installé le CLI Supabase : 
    cd C:\aveho-ec-app
supabase functions deploy maintenance-daily-cron
    Puis programme le cron dans SQL Editor (voir section 7.3 de cette note).
    Si tu sautes cette étape, l'app continue de fonctionner — les automatismes restent déclenchés à l'ouverture de la page Maintenance comme en 0.11.
  5. Dans PowerShell :
    cd C:\aveho-ec-app
npm install
npm run dev
  6. Tests rapides :
    • Sur Matériels, clique le libellé d'un matériel : tu arrives sur sa fiche complète
    • Sur Maintenances, clique Export PDF planning : un nouvel onglet s'ouvre avec le PDF, dialogue d'impression automatique
    • Sur Statistiques : si tu as des maintenances dans les 6 derniers mois, la section Maintenance apparaît avec 3 graphes
    • Sur /signalements : 3 signalements démo (1 anonyme, 1 signé "Marie IDE", 1 avec réponse de l'admin)
    • Dépose un signalement anonyme : aucune trace de ton compte n'est enregistrée
    • Si tu es admin, clique "Répondre" sur un signalement : tu peux changer le statut et écrire une réponse publique
  7. Mise en ligne :
    git add .
git commit -m "Aveho EC Alpha 0.12"
git push

Pistes pour la prochaine version :

  1. Statistiques signalements — graphes par type / statut / taux de réponse

📌 Pièges connus (rétro-doc depuis 0.17.0)

Cette section a été ajoutée après les sessions de migration 0.15.6 et 0.16.1, qui ont permis de documenter les écarts entre le schéma de la 0.12 et la réalité du terrain.

⚠️ Piège : table signalements à créer manuellement

Le script SQL 16_signalements.sql doit être exécuté côté Supabase pour que la page /signalements fonctionne. Si tu as installé la 0.12 mais que la table n'est pas créée, l'app plantera silencieusement avec un résultat vide.

Pour valider : select tablename from pg_tables where tablename = 'signalements'; doit retourner 1 ligne.

⚠️ Piège : RLS du script 16 (corrigé en 0.15.0)

La version originale du script 16_signalements.sql contenait une politique RLS faisant join roles r on r.id = ms.role qui plantait avec operator does not exist: uuid = text. Corrigé en 0.15.0 : les RLS de signalements n'utilisent plus que mes_structures() sans dépendance à roles.

Si tu migres depuis une 0.12 d'origine, exécute aveho-PATCH-vers-0.15.sql (section 3) qui réécrit les policies proprement.
