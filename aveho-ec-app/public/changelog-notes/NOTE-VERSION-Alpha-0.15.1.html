3. Détail des fonctionnalités

3.1 Module Achats — workflow 7 statuts

Brouillon → À valider → Validée → Commandée → Reçue

Plus deux statuts annexes : Refusée (motif obligatoire visible par le demandeur) et Annulée. KPIs cliquables par statut + KPI Budget engagé en gradient navy/teal (somme des montants Validée + Commandée + Reçue). Lignes détaillées par commande (table achats_lignes) avec total auto. Notifications via logEvent à chaque transition.

3.2 Recherche globale Cmd+K

5 préfixes pour filtrer instantanément le type de résultat : p: patients, m: matériels, d: demandes d'intervention, s: signalements, a: achats. Panneau d'aide visuelle automatique quand l'input est vide. Navigation clavier ↑↓ Enter Échap.

3.3 Journal d'activité

Nouvelle page /journal avec timeline visuelle groupée par jour ("Aujourd'hui", "Hier", date longue). Trait vertical avec points colorés par action, phrasé naturel, badges colorés par entité. Filtres : période (1/7/30/90j), entité, utilisateur.

3.4 Étiquettes patient sur fiche

Sur la fiche patient, bouton dashed "Gérer" à côté des pastilles d'étiquettes. Ouvre une modale avec toggles directs sur toutes les étiquettes de la collectivité. Mise à jour optimiste + persistance Supabase.

3.5 Export Excel multi-feuille

Bouton "Export Excel" sur Statistiques. Charge SheetJS depuis CDN au premier appel, génère bilan-aveho-2026-XX-XX.xlsx avec 7 feuilles : Patients, Matériels, DI, Maintenances, Stock, Achats, Informations (méta + compteurs).

4. Corrections post-livraison RÉVISION

Lors de la migration réelle d'une base 0.1 vers 0.15, plusieurs bugs des scripts SQL initiaux ont été identifiés et corrigés. Le code applicatif a aussi été rendu plus tolérant aux variations de schéma.

4.1 Collision de noms — table commandes

Le module Achats utilisait initialement les tables commandes et commande_lignes, qui existaient déjà dans la base 0.1 pour le workflow panier magasin. Résultat : le create table if not exists ne créait rien et le code plantait à l'exécution.

Correction : renommage en achats et achats_lignes. Le code Next.js a été mis à jour (.from("achats") dans les pages concernées). Les tables 0.1 commandes / commande_lignes restent intactes pour le panier magasin.

4.2 RLS avec dépendance à ms.role

Les scripts SQL initiaux 16 et 17 contenaient des politiques RLS qui joignaient roles r on r.id = ms.role. Or la colonne role de membres_structure est de type text (legacy), tandis que role_id est uuid. La jointure plantait avec ERROR: operator does not exist: uuid = text.

Correction : les politiques RLS de signalements, achats, achats_lignes n'utilisent plus aucune référence à roles. La sécurité repose uniquement sur la fonction mes_structures() qui cloisonne par collectivité.

4.3 useAuth qui cherche permissions_json alors que la base a droits

La table roles dans les anciennes bases utilise la colonne droits (jsonb). Le code useAuth faisait un select(...,roles(id,nom,permissions_json)) qui plantait sur les bases anciennes.

Correction côté code : useAuth fait un fallback en deux temps. Première requête avec les deux noms tentés (droits,permissions_json), et si la colonne n'existe pas, deuxième requête minimaliste. Le hook accepte les deux formats de droits (array ["write","read"] ou objet par module {"stock":["read"]}).

Correction côté SQL : le script 06_utilisateurs.sql ajoute désormais une colonne permissions_json en alias de droits. Pas de migration de données nécessaire, juste un duplicata du contenu.

4.4 Page Journal cassée — table evenements qui n'existe pas HOTFIX 0.15.1

Première version de la page /journal requêtait une table evenements et des colonnes membres_structure.prenom, nom, email qui n'existent pas dans ta base. Résultat : la page plantait en 404 / 400.

Correction :

  • app/journal/page.js requête désormais audit_log (la vraie table d'audit)
  • Le nom de l'auteur est récupéré depuis membres_structure.nom_affiche (colonne réelle, vs les 3 champs séparés qu'on imaginait)
  • Fallback sur audit_log.user_email (snapshot conservé) si l'utilisateur n'est plus dans membres_structure
  • Bonus : la section "Historique d'activité" de la fiche patient utilisait aussi evenements → corrigée vers audit_log

Pas de SQL à exécuter pour cette correction, c'est purement côté code. Re-déploiement du zip 0.15.1 suffit.

4.5 Boutons de création invisibles malgré rôle Administrateur

Symptôme : l'utilisateur s'authentifie correctement mais ne voit aucun bouton "Nouveau patient", "Nouvelle commande", etc. sur les pages.

Cause : le rôle est bien créé dans roles avec la colonne droits (jsonb par module), mais useAuth cherchait permissions_json qui n'existait pas → fallback déclenché → mais sans la bonne info de droits.

Correction côté SQL : ajout de la colonne permissions_json en alias de droits (voir patch).

Correction côté code : useAuth accepte les deux noms de colonne et gère les deux formats de droits (array ["write"] ou objet par module {"stock":["read"]}).

5. Pièges connus (à éviter) IMPORTANT

⚠️ Piège n°1 : ne PAS supprimer commande_lignes

Cette table appartient au workflow panier magasin 0.1. Si tu la supprimes (par exemple en exécutant un mauvais drop table commande_lignes cascade), la page /panier casse avec l'erreur "Could not find the table public.commande_lignes in the schema cache".

Récupération : exécute le bloc de récupération du aveho-PATCH-vers-0.15.sql (section "2) Récupération de commande_lignes si supprimée par mégarde").

⚠️ Piège n°2 : ne PAS toucher à la table commandes

La table commandes appartient au workflow panier magasin 0.1. Le module Achats utilise achats, jamais commandes.

Si tu te demandes : "quelle table contient mes commandes d'achat fournisseur ?", c'est achats.

⚠️ Piège n°3 : auth.uid() retourne NULL dans le SQL Editor

Si tu exécutes select auth.uid() dans Supabase SQL Editor, ça retourne NULL. C'est normal : le SQL Editor tourne avec le rôle postgres (admin), pas avec ton compte authentifié. Pour insérer manuellement avec ton user_id, va dans Authentication → Users dans Supabase Dashboard, récupère l'id du compte concerné, et utilise-le en littéral dans tes requêtes SQL.

⚠️ Piège n°4 : mot de passe en clair dans les logs console

Si tu copies-colles les logs de la console navigateur (F12) pour les partager en debug, vérifie qu'il n'y a pas de mot de passe. Le tag <input type="password" value="XXX"> peut apparaître dans certains messages d'erreur React. Bonne pratique : utiliser le magic link (passwordless) pour l'authentification.

⚠️ Piège n°5 : la table d'audit s'appelle audit_log

Le code applicatif tente d'abord de requêter evenements (nom envisagé pendant la conception), mais en base la table créée par 10_audit.sql s'appelle audit_log. Le hotfix 0.15.1 corrige le code en conséquence.

Pour insérer des événements depuis le SQL Editor :

insert into audit_log (structure_id, user_id, user_email, action, entite, entite_id, details)
values ('aaaaaaaa-...', '945c466a-...', 'moloscope46@gmail.com', 'creer', 'patient', null, '{}'::jsonb);

⚠️ Piège n°6 : membres_structure n'a pas prenom / nom / email séparés

Le code envisageait initialement 3 colonnes prenom, nom, email pour afficher le nom de l'auteur dans le Journal. Mais la vraie table a une seule colonne nom_affiche (text). Le hotfix 0.15.1 utilise cette colonne et tombe sur audit_log.user_email en fallback.

7. Procédure de migration (3 cas)

Cas A — Base vierge (nouveau déploiement)

  1. Dans Supabase → SQL Editor → coller le contenu de aveho-0.15-complet.sql → Run.
  2. Cela crée toutes les tables, RLS et quelques données démo.
  3. Configure l'auth, déploie le code, c'est parti.

Cas B — Base 0.1 existante (cas Cédric)

  1. Dans Supabase → SQL Editor → exécuter chaque script de 02_referentiel.sql à 17_commandes.sql dans l'ordre. Ignorer les warnings "already exists".
  2. Si quelque chose plante, exécuter aveho-PATCH-vers-0.15.sql qui répare tous les cas connus.
  3. Vérifier les tables : select tablename from pg_tables where schemaname='public' order by tablename; Tu dois en voir 31.

Cas C — Base 0.15 partielle (récupération)

  1. Exécuter aveho-PATCH-vers-0.15.sql intégralement. Idempotent.
  2. Si /panier plante avec "Could not find the table commande_lignes" → section 2 du patch récupère cette table.
  3. Si les boutons de création n'apparaissent pas → section 1 du patch ajoute permissions_json.
  4. Si /signalements ou /achats plantent → sections 3 et 4 du patch créent les tables.

Côté code (tous cas)

  1. Sauvegarder ton .env.local.
  2. Décompresser aveho-ec-app.zip dans ton dossier (écrase le code).
  3. Remettre ton .env.local (sinon le build plante).
  4. PowerShell :
    cd C:\aveho-ec-app
npm install
npm run build
npm run dev
  5. Tests : Cmd+K affiche les 5 préfixes, /achats et /journal accessibles, boutons de création visibles.
  6. Mise en ligne : git add . ; git commit -m "Aveho EC 0.15" ; git push
