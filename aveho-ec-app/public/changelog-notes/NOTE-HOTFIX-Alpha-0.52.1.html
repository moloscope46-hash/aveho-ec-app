Patch 0.52.1 — Bug racine du Service Worker Explication enfin du pattern récurrent "la bannière n'apparaît pas après chaque MAJ"

Date : 31 mai 2026 Version : v0.52.1-alpha Type : Hotfix critique infrastructure Tests : 944 verts (inchangé)

Le pattern récurrent

À chaque version livrée depuis la 0.49, le même bug ressort :

  • Le code est correctement déployé (zip extrait, npm install OK, build OK)
  • /api/version renvoie bien la nouvelle version
  • Mais les nouveaux composants du layout ne se montent pas (AnnoncesBanner, VersionCheck toast, FocusMode, etc.)
  • Solution provisoire à chaque fois : DevTools → Unregister SW → Clear site data → Re-ouvrir

Cette session, on a enfin compris pourquoi.

Diagnostic forensique

Cause racine Le Service Worker était bloqué à la version aveho-ec-0.48.1

Dans public/sw.js, la constante VERSION n'avait plus été bumpée depuis le hotfix 0.48.1 (post-page offline statique). Donc :

  • 0.49.0 à 0.52.0 ont toutes été livrées avec le SW aveho-ec-0.48.1
  • Quand le SW n'a pas changé de version, le navigateur ne re-télécharge PAS le SW
  • Le SW continue de servir les caches existants (notamment les chunks _next/static/chunks/app/layout.js)
  • Le nouveau HTML (avec le nouveau layout) est servi correctement, mais quand le navigateur va chercher le chunk layout.js, il reçoit la version cachée de la 0.48.1
  • Cet ancien chunk ne contient PAS AnnoncesBanner, VersionCheck mis à jour, FocusMode, etc.
  • Résultat : le runtime exécute un layout obsolète, mais tu vois la 0.52 sur /api/version qui n'est pas intercepté par le SW

💡 Pourquoi seul "Clear site data" fonctionnait ? Parce que cette action vide le cache du SW, le force à se ré-télécharger, et au prochain chargement les chunks neufs sont récupérés depuis le serveur.

Correction structurelle

2 changements pour éviter que ça se reproduise :

1. Bump immédiat du SW à la version courante

// public/sw.js
- const VERSION = "aveho-ec-0.48.1";
+ const VERSION = "aveho-ec-0.52.1";

2. Script de synchronisation automatique

Nouveau fichier scripts/sync-sw-version.js qui lit package.json et met à jour le SW :

const pkgVersion = pkg.version.replace(/-alpha$/, "");
const target = `aveho-ec-${pkgVersion}`;
// → écrase la constante VERSION dans public/sw.js

Ajouté au cycle de vie npm :

"scripts": {
  "prebuild": "node scripts/sync-sw-version.js",
  "sync-sw": "node scripts/sync-sw-version.js"
}

Conséquence : à partir de la 0.53 et toutes les suivantes, npm run build appelle automatiquement le sync avant le build, donc le SW sera toujours à la bonne version sans intervention manuelle.

Procédure d'application — une dernière fois manuelle, puis plus jamais

Cette installation requiert une dernière fois le clear site data pour casser la chaîne du vieux SW. Après ça, le système est auto-correctif.

  1. Décompresser le zip 0.52.1 par-dessus C:\aveho-ec-app\
  2. Installer + lancer : 
    cd C:\aveho-ec-app
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue
npm install
npm run dev
  3. Clear site data une dernière fois :
    • F12 → Application → Service Workers → Unregister
    • F12 → Application → Storage → Clear site data
    • Fermer tous les onglets localhost:3000
    • Ouvrir une nouvelle fenêtre → localhost:3000
  4. Vérifier :
    • Badge en haut affiche v0.52.1
    • Crée une annonce dans /annonces → la bannière apparaît directement sous la TopBar
    • Pour les FUTURES versions, le clear site data ne sera plus nécessaire

Garantie pour les futures versions

À partir de la 0.53 et au-delà :

  1. Quand on bumpera package.json de 0.52.1 à 0.53.0
  2. npm run build exécute automatiquement scripts/sync-sw-version.js
  3. Le SW devient aveho-ec-0.53.0
  4. Quand l'user charge la page, le navigateur détecte un nouveau SW (byte-diff sur public/sw.js)
  5. Le nouveau SW s'active → invalide les anciens caches → re-télécharge les chunks neufs
  6. VersionCheck détecte le changement → toast vert → user clique "Recharger"
  7. Tout fonctionne sans intervention manuelle

Plus jamais de "la bannière n'apparaît pas après MAJ" sauf si on désactive le prebuild.

Auto-critique honnête

J'aurais dû identifier ce bug dès la 2ème fois. Au lieu de ça, j'ai :

  • 0.49 → "Clear site data manuel" comme solution
  • 0.49.3 → ajout du VersionCheck reload qui unregister le SW (mais ne marche que si le toast s'affiche...)
  • 0.50 → "Clear site data manuel" encore
  • 0.51 → diagnostic console qui conclut "tout fonctionne" sans aller chercher la cause système
  • 0.52 → encore "ça ne marche pas"

À chaque fois, j'ai accepté le symptôme au lieu de creuser. Ce hotfix répare la cause racine.

Nouveau réflexe (15ᵉ) ajouté à ma checklist :

Bump VERSION dans public/sw.js à CHAQUE release applicative (ou utiliser le prebuild script qui le fait automatiquement). Sans ça, le SW continue de servir les anciens chunks et les nouveaux composants ne se montent pas.
