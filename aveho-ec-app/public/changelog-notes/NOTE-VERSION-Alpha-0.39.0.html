1. EntityPreview — composant générique

Le composant <EntityPreview> encapsule toute la logique de hover/positionnement, et délègue le rendu du popover à une fonction passée en prop.

// API
<EntityPreview
  entity={obj}                    // l'objet (patient, di, achat...)
  href="/route/destination"       // pour le clic
  renderPopover={({ entity, navigate }) => (
    <MonPopoverPersonnalise ... />
  )}
  onHover={fetchDataLazy}          // optionnel : callback à l'ouverture (fetch async)
  disabled={false}                  // si true, wrapper transparent (pas de hover)
  width={320}                       // largeur popover
  maxHeight={400}                   // hauteur max
>
  <span>{trigger}</span>
</EntityPreview>

Comportement (commun à tous les preview)

  • Hover desktop > 500ms → popover apparaît + onHover() appelé
  • Hover sortie → délai 150ms avant fermeture (laisse bouger vers le popover)
  • Hover sur popover → annule la fermeture
  • Clic court → navigation via router.push(href)
  • Mobile (pointer: coarse) → désactivé → tap = navigation normale
  • Positionnement intelligent (clamp aux bords de viewport)

4. Dernière DI lazy (L)

Auparavant le PatientPreview affichait juste un compteur "3 DI actives". Maintenant on voit aussi le détail de la dernière DI du patient, fetchée à la demande au hover :

// Dans PatientPreview
const [lastDI, setLastDI] = useState(null);
// 4 états : null (initial) | "loading" | "none" | objet DI

async function fetchLastDI() {
  if (lastDI !== null) return;  // évite re-fetch
  setLastDI("loading");
  const { data } = await supabase
    .from("interventions")
    .select("id, numero, statut, urgence, created_at")
    .eq("patient_id", patient.id)
    .order("created_at", { ascending: false })
    .limit(1);
  setLastDI(data?.[0] || "none");
}

// Passé à EntityPreview via onHover
<EntityPreview onHover={fetchLastDI} ... />

Affichage progressif : spinner pendant le chargement → texte italique "Aucune DI" si vide → ligne complète avec badge urgent + statut coloré + date si trouvée.

5. Filtres avancés stats activité (J)

3 nouveaux selects

  • Établissement : peuplé depuis parEtab (vue v_stats_activite_par_etab)
  • Utilisateur : peuplé depuis users (v_stats_activite_par_user)
  • Catégorie d'action : 7 valeurs hardcodées (creer/modifier/supprimer/valider/refuser/recevoir/cloturer)

Les filtres impactent les KPIs et le podium. Une note discrète signale que la heatmap et les tendances mois courant/précédent restent globales car elles utilisent des vues SQL préagrégées par structure (filtrer côté front fausserait les chiffres globaux).

Bouton "Réinitialiser"

Apparaît dès qu'un filtre est actif. Remet tous les selects à vide en un clic.

6. Export CSV (J)

Nouveau bouton à côté de "Export PDF" :

// Fetch limité à 5000 lignes max
const { data } = await supabase
  .from("audit_log")
  .select("created_at, action, entite, entite_id, user_email, user_id, etablissement_id, details")
  .eq("structure_id", auth.structureId)
  .gte("created_at", since)
  .order("created_at", { ascending: false })
  .limit(5000);
// + filtres etab/user/catégorie appliqués si actifs

// CSV avec BOM UTF-8 + CRLF + séparateur ; (compatibilité Excel FR)
const csv = "\uFEFF" + lines.join("\r\n");

Format CSV

  • 7 colonnes : Date, Action, Entité, ID entité, Utilisateur (email), Établissement, Détails
  • BOM UTF-8 en tête → Excel FR ouvre directement avec accents corrects
  • CRLF en fin de ligne
  • Séparateur point-virgule (standard FR)
  • Échappement : si le contenu contient ;, ", \n ou \r → entouré de quotes, quotes internes doublées (RFC 4180)
  • Nom de fichier : audit-aveho-YYYY-MM-DD.csv

Pourquoi pas de SQL

Tout est côté front (composants React + fetch ciblé) + côté UI sur la page stats activité. Le SQL existant suffit (les vues 0.31 et la table audit_log restent les sources). Aucune migration nécessaire.
