Résumé

Première version après le cap des 50. 5 chantiers fonctionnels, 1 patch SQL léger (1 vue + 1 index GIN). Tout polish/complétion : finir la migration confirm() (AA fini une bonne fois pour toutes), ajouter des stats utiles sur les annonces de la 0.50, étendre la recherche audit qui était partielle, créer la page Statut système, exploiter la vue v_achats_a_valider créée en 0.50.

5 modules livrés :
AQ Endpoint /api/health + page /statut avec ping Supabase PostgreSQL + REST + Realtime (WebSocket côté client). Refresh 30s, historique 12 derniers checks en mémoire visualisé en mini bandeaux colorés.
AZ Vue SQL v_annonces_stats qui calcule nb_destinataires, nb_dismisses, taux_dismiss_pct par annonce. Affichée sur la page admin /annonces avec barre de progression et pastille de couleur.
BA Recherche audit étendue : le filtre cherche maintenant aussi dans details::text (le JSON sérialisé). Index GIN ajouté sur audit_log.details pour les requêtes structurées.
BB Widget <MesValidationsEnAttente /> sur l'accueil : liste les commandes "À valider" + celles en "Validée (1/2)" qui ne sont pas validées par l'utilisateur courant (séparation des pouvoirs). Visible uniquement pour managers/admins.
AA Migration confirm() finale : 4 derniers confirm() migrés (parametres-rgpd × 2 avec variable confirmMsg + crud.js × 2). Total cumulé sur 0.49 + 0.50 + 0.51 : 23 confirm() natifs → dialogs.confirm() stylé.

Chantiers livrés

AQ Statut système — page de monitoring

  • Nouvel endpoint /api/health (Next.js Route Handler) :
    • Ping Supabase PostgreSQL via count head sur structures (mesure latency_ms)
    • Ping Supabase REST endpoint via HEAD sur /rest/v1/
    • Renvoie { overall, services: [{name, status, latency_ms, error}], timestamp }
    • dynamic = "force-dynamic" + revalidate = 0 pour éviter tout cache
  • Nouvelle page /statut :
    • Poll /api/health toutes les 30 secondes
    • Check Realtime côté client en parallèle (subscribe sur un channel jetable, mesure du temps avant état "SUBSCRIBED")
    • Bandeau principal coloré selon overall (vert/orange/rouge/gris)
    • Cards par service avec icône + statut + latence + erreur éventuelle
    • Historique des 12 derniers checks visualisé en mini bandeaux colorés (style status page)
    • Bouton "Rafraîchir" manuel
  • Lien menu ajouté dans Administration (entre Performance SQL et Dashboard direction)
  • Pas d'auth requis sur l'endpoint /api/health — il faut pouvoir vérifier le statut même quand on n'est pas loggé

AZ Statistiques annonces

  • Vue SQL v_annonces_stats (créée dans le patch 0.51) :
    • Pour chaque annonce : nb_destinataires (count membres de la structure), nb_dismisses (count dismissees), taux_dismiss_pct (calculé avec round 1 décimale)
    • Gestion de la division par zéro (si 0 membres → 0%)
    • grant select to authenticated
  • Chargement parallèle dans la page /annonces : Promise.all sur annonces + stats
  • Nouvelle colonne "Réception" dans le tableau admin :
    • Compteur nb_dismisses / nb_destinataires
    • Barre de progression 80px avec couleur selon taux (bleu < 25% lecture, orange 25-50%, vert > 50%)
    • Pourcentage affiché en dessous
  • Pourquoi "dismiss = lecture" : un user qui dismisse a forcément vu l'annonce. Un taux de dismiss élevé indique donc une bonne visibilité (les users prennent connaissance et ferment activement). Un taux faible = soit l'annonce est récente, soit les users ne la voient pas.

BA Recherche audit étendue

  • Avant : le commentaire dans le code disait "Cherche dans entite_id, user_email, ou details" mais le code ne cherchait que dans user_email et entite_id
  • Maintenant : ajout de details::text.ilike.%texte% dans la clause OR Supabase. Cherche dans le JSON sérialisé.
  • Patch SQL : index idx_audit_log_details_gin de type GIN sur audit_log.details jsonb. Accélère les requêtes structurées details @> '{...}' ou @? '$.key'. Pour ilike sur cast text, un seq scan reste nécessaire — mais reste rapide grâce aux autres filtres préalables (struct, période, action).
  • Placeholder enrichi : "🔍 Recherche email / ID / contenu…" + title explicite
  • Min-width input augmenté de 180px à 220px

BB Mes validations en attente (widget accueil)

  • Composant <MesValidationsEnAttente /> dans app/MesValidationsEnAttente.js
  • Visible uniquement pour les managers/admins (auth.can("valider_achat") || role.nom === "Administrateur")
  • Deux requêtes en parallèle :
    • 1) Achats statuts "À valider" / "En attente" → première validation possible
    • 2) Achats statut "Validée (1/2)" où valideur_id ≠ auth.user.id → seconde validation possible (séparation pouvoirs respectée)
  • UI : card orange avec bordure gauche + titre + badge count + bouton "Voir tout →"
  • Items : chip "1ère validation" (orange) ou "2nde validation" (violet), numéro, fournisseur, motif tronqué, budget formaté en € français, badge "Double valid." si budget > seuil
  • Limité aux 5 premiers + message "+ N autre(s)" si dépassement
  • Clic sur item → navigate /achats
  • Caché si items.length === 0 (zéro pollution si rien à valider)

AA Migration confirm() — FINALE

  • 4 derniers confirm() migrés :
    • /parametres-rgpd × 2 (avec variable confirmMsg) — script Python n'a pas matché car le regex demandait une string littérale. Migré manuellement.
    • app/crud.js × 2 (composant générique CRUD utilisé par /articles, /materiels, /depots, /stock, /collectivite). Plus utilisé partout.
  • Total cumulé migration confirm() depuis le début :
    • 0.49 : 8
    • 0.50 : 11
    • 0.51 : 4
    • Total : 23 confirm() natifs migrés vers dialogs.confirm() stylé
  • Plus aucun confirm() natif dans le code applicatif. Toutes les modales de confirmation sont désormais ConfirmModal de la dialogs API (cohérence visuelle, accessibilité, support du focus trap, etc.).
