3. RLS étanche par établissement SÉCURITÉ

Pourquoi c'était important

Jusqu'à la 0.4, le filtrage par établissement était fait côté application (chaque requête ajoutait .eq("etablissement_id", auth.etabId)). Ça marche pour l'usage normal, mais ça n'est pas étanche : un utilisateur technique qui contournerait l'UI (via l'API Supabase directement, ou un bug applicatif) pourrait potentiellement voir des données d'autres établissements de sa collectivité.

La 0.5 ajoute une seconde couche en base : même si l'app ne filtre rien, PostgreSQL refuse de retourner les lignes des établissements auxquels l'utilisateur n'est pas rattaché.

3.1 Architecture en deux couches

┌─────────────────────────────────────────────────────────────┐
│ Couche 1 : RLS COLLECTIVITÉ (existante depuis schema.sql)   │
│   structure_id ∈ mes_structures()                            │
│   → empêche de voir une autre collectivité                   │
├─────────────────────────────────────────────────────────────┤
│ Couche 2 : RLS ÉTABLISSEMENT (nouveau, Alpha 0.5)           │
│   etablissement_id ∈ mes_etablissements() OU NULL            │
│   → empêche de voir un autre établissement de SA coll.       │
└─────────────────────────────────────────────────────────────┘
                Les deux couches s'appliquent (AND)

3.2 Fonction mes_etablissements()

create function mes_etablissements() returns table(etab_id uuid)
language sql security definer set search_path = public as $$
  with rattachements as (
    select etablissement_id from membres_etablissements where user_id = auth.uid()
  )
  -- Si l'user a au moins un rattachement : on prend ses établissements
  select etablissement_id from membres_etablissements where user_id = auth.uid()
  union
  -- Sinon (admin collectivité sans rattachement) : on lui donne tous les étab
  -- de sa collectivité, pour ne pas bloquer l'admin
  select e.id from etablissements e
  where not exists (select 1 from rattachements)
    and e.structure_id in (select mes_structures());
$$;

3.4 Comportement de bordure

  • Lignes sans etablissement_id (NULL) : visibles par tous les membres de la collectivité (cas des données legacy ou globales). C'est volontaire — ça permet à la 0.5 de ne casser aucune donnée existante.
  • Utilisateur sans rattachement à un établissement : il voit tous les établissements de sa collectivité (= admin collectivité). C'est volontaire pour ne pas bloquer les admins par défaut.
  • Utilisateur avec rattachement(s) : il ne voit QUE ses établissements. Pour qu'il voie aussi d'autres établissements, il faut explicitement le rattacher.

4. Page profil utilisateur NOUVEAU

Nouvelle page /profil accessible depuis le menu Administration → Mon profil. Permet à l'utilisateur connecté de :

  • Voir ses infos : email, collectivité, rôle, établissements accessibles, permissions
  • Modifier son nom d'affichage (stocké dans auth.users.user_metadata.nom_affiche)
  • Changer son mot de passe (avec confirmation + min. 6 caractères)
  • Voir son ID utilisateur (utile pour les requêtes SQL d'admin)

5. Logs de connexion NOUVEAU

Chaque connexion réussie crée maintenant une entrée dans audit_log :

{
  action: "connexion",
  entite: "session",
  user_email: "cedric@aveho.fr",
  details: { ua: "Mozilla/5.0 ... Chrome/148..." }
}

Visible dans la page Historique en filtrant sur "Connexion".

6. Libellés métier propagés

En 0.4, seule la page Patients utilisait useLibelles. En 0.5, c'est étendu à :

  • Interventions : KPI "Patients", références dans les DI
  • Vue globale : KPI "Patients (total)", "Matériel (total)"

Les pages restantes (Mon établissement, Magasins, etc.) seront adaptées en 0.6 — c'est mécanique mais demande de modifier chaque "Patient" en dur.

7. Filtres temporels sur l'historique NOUVEAU

La page Historique a maintenant un sélecteur de période en premier filtre :

  • 7 derniers jours
  • 30 derniers jours (défaut)
  • 90 derniers jours
  • Tout

Combinable avec les filtres action et entité existants. Le bouton "Effacer filtres" devient "Réinitialiser" et remet la période à 30j par défaut.

8. Notifications ciblées

Le helper logEvent accepte maintenant notifUserId pour cibler un utilisateur précis au lieu de diffuser "à tous" :

// Notif diffusée à tous (comportement par défaut depuis 0.4)
await logEvent(supabase, auth, { ..., notif: true });

// Notif ciblée sur un utilisateur précis (nouveau en 0.5)
await logEvent(supabase, auth, {
  ...,
  notif: true,
  notifUserId: assigneeUserId,    // un seul destinataire
  titre: "Tu as été assigné à cette DI",
});

Pour l'instant ce paramètre est juste exposé techniquement — il sera utilisé en 0.6 quand on ajoutera l'assignation explicite des DI à un utilisateur.

11. Procédure de mise à jour depuis Alpha 0.4

1 script SQL critique à exécuter :

  1. Sauvegarde ton dossier C:\aveho-ec-app ET ta base Supabase (Project Settings → Database → Backups).
  2. Décompresse le nouveau zip par-dessus.
  3. Dans Supabase SQL Editor : exécute supabase/11_rls_etanche.sql.
    ⚠️ Important : si ton compte de test n'est rattaché à AUCUN établissement, tu verras quand même tout (fallback admin). Pour tester l'étanchéité, crée un user de test et rattache-le explicitement à un seul établissement via SQL : 
    insert into membres_etablissements (user_id, etablissement_id, structure_id)
values ('UID_DE_TEST', 'UUID_HOPITAL_CEDRIC', 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa');
  4. Dans PowerShell : 
    cd C:\aveho-ec-app
npm install
npm run dev
  5. Mise en ligne : 
    git add .
git commit -m "Aveho EC Alpha 0.5"
git push

12. Tests de sécurité à faire après mise à jour

Vérification que le RLS étanche fonctionne :

  1. Crée un user de test "test@aveho.fr" via Supabase Auth → Users → Add user.
  2. Rattache-le à la collectivité ET à un seul établissement (Hôpital Cédric) : 
    insert into membres_structure (user_id, structure_id, role)
values ('TEST_UID', 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa', 'lecture');

insert into membres_etablissements (user_id, etablissement_id, structure_id)
select 'TEST_UID', id, 'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa'
from etablissements where nom = 'Hôpital Cédric';
  3. Connecte-toi avec ce user, va sur la page Patients.
  4. Tu dois voir uniquement les patients d'Hôpital Cédric, pas ceux d'EHPAD Les Tilleuls.
  5. Va dans Supabase → Table Editor → patients : tu dois voir le même filtrage côté requête directe (preuve que la RLS marche, pas seulement l'app).
