🐛 Diagnostic — le 503 sur tooltip

Symptôme

Sur /changelog, au survol d'un titre de version ou d'une évolution, le popup HTML affichait "Impossible de charger {fichier}". Console F12 :

changelog:1 Failed to load resource: 
the server responded with a status of 503 (Offline)

Cause

Le Service Worker traitait les requêtes /changelog-notes/*.html en networkFirst (dernière règle catch-all). Quand le fetch échouait ou que le SW interceptait mal (cas typique : reload rapide pendant une mise à jour), il tombait sur le fallback ligne 116 :

return new Response(
  "Hors-ligne — aucune donnée en cache.", 
  { status: 503, statusText: "Offline" }
);

Et comme ces fichiers ne sont jamais préchargés au install (pas dans STATIC_ASSETS), le cache était vide.

Fix 1 — cacheFirst sur /changelog-notes/

Ces fichiers ne changent jamais une fois publiés (chaque note est figée pour une version donnée). Donc cacheFirst est le bon pattern :

if (url.pathname.startsWith("/changelog-notes/")) {
  event.respondWith(cacheFirst(req, STATIC_CACHE));
  return;
}

Au 1er hover : fetch réseau → mis en cache. Aux hovers suivants : réponse instantanée depuis le cache, plus de 503 possible.

Fix 2 — cacheFirst plus robuste

Quand fetch échoue dans cacheFirst, ancien code retournait Response.error() (erreur réseau brute). Maintenant : pour /changelog-notes/, on renvoie une vraie 503 avec un HTML lisible :

return new Response(
  '<p style="...">Note non disponible hors-ligne...</p>',
  { status: 503, headers: { "Content-Type": "text/html" } }
);

Fix 3 — Retry côté client

Dans fetchNoteHtml de la page changelog : si le 1er fetch (avec cache: "force-cache") renvoie pas .ok, on retry avec cache: "no-cache". Et le fallback final est élégant :

return `<div style="...">
  ⏳ <b>Aperçu indisponible</b>
  Réessaie le hover dans quelques secondes ou télécharge directement la note.
</div>`;

Et surtout : ce fallback n'est pas cacheé dans noteCacheRef, ce qui permet de retenter au prochain hover.
