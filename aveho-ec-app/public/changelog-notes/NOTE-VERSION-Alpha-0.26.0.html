3. Migration safeWrite

3.1 Crud.js (effet de levier maximal)

Le composant <Crud> est utilisé par toutes les pages référentiel : articles, dépôts, étiquettes, magasins, transferts, promotions, vue-globale, etc. Migrer ce seul composant rend offline-ready une douzaine de pages d'un coup.

Modifs :

  • Import safeInsert, safeUpdate, safeDelete + hook useAuth
  • save() : update via safeUpdate, insert via safeInsert avec UUID client
  • del() : safeDelete
  • bulkDelete() reste en direct Supabase (action de masse, on assume online)

4. Cache de lecture

4.1 Architecture

Base IndexedDB aveho-offline-cache avec un store unique :

Store: cache
  - key: "patients:structureId" (PK)
  - data: any (résultat du SELECT)
  - at: timestamp d'enregistrement
  Index sur "at" pour purge éventuelle

4.2 API safeFetch

Helper unique pour lire avec cache transparent :

const { data, error, fromCache, fresh } = await safeFetch(
  "patients:" + structureId,
  () => supabase.from("patients").select("*").eq("structure_id", structureId)
);

// 4 cas de retour :
// online + fresh fetch : { data, error: null, fromCache: false, fresh: true }
// online + erreur, cache existe : { data: cached, error, fromCache: true, fresh: false }
// offline + cache existe : { data: cached, error: null, fromCache: true, fresh: false }
// offline + pas de cache : { data: null, error: "Hors-ligne...", fromCache: false, fresh: false }

4.3 TTL

Le cache expire après 7 jours. Au-delà, cacheGet retourne null comme si l'entrée n'existait pas. Évite les données stale qui restent en cache des mois.

4.4 Convention de nommage des clés

Pattern recommandé : {table}:{structureId}[:{filter}]. Exemples :

  • patients:aaaaaaaa-... → tous les patients d'une structure
  • materiels:aaaaaaaa-...:type=lit → matériels filtrés
  • patient:abc-123 → fiche d'un patient précis
  • patient:abc-123:interventions → ses interventions

Les clés permettent de cibler invalidation ou refresh ciblé plus tard.

4.5 Migration progressive

Les pages peuvent migrer vers safeFetch au cas par cas :

// AVANT
const { data } = await supabase.from("patients").select("*").eq("structure_id", id);

// APRÈS (cache + offline)
const { data, fromCache } = await safeFetch(
  "patients:" + id,
  () => supabase.from("patients").select("*").eq("structure_id", id)
);
if (fromCache) console.log("Lu depuis cache (offline ou erreur réseau)");

Pour la 0.26 le cache est livré mais aucune page ne l'utilise encore. C'est volontaire : on stabilise d'abord. Migration en 0.27.

5. Détection de conflit

5.1 Scénario problématique

Imagine : Alice est sur un patient en mode offline et change sa chambre. Bob (au bureau, online) change le médecin traitant du même patient. À la reconnexion d'Alice, sa modif "chambre" écrase tout, et la modif "médecin traitant" de Bob disparaît silencieusement.

5.2 Solution optimistic locking

  1. Quand Alice met une update en queue, on capture l'updated_at du patient à ce moment (stocké dans __staged_updated_at du payload)
  2. À la sync (replayQueue), avant d'appliquer l'UPDATE, on lit l'updated_at actuel en base
  3. Si différent (avec tolérance 1s) → CONFLIT : on n'écrase pas, on garde l'op en queue avec last_error = "Conflit : modifié depuis (par un autre user le ...)"
  4. Si identique → on applique, on retire __staged_updated_at du payload, et on bump l'updated_at

5.3 Helper buildUpdatePayloadWithLock

import { buildUpdatePayloadWithLock } from "../../lib/conflictCheck";

const originalRow = patient; // chargé avant édition
const payload = buildUpdatePayloadWithLock(
  { chambre: "205" },
  originalRow
);
// payload = { chambre: "205", __staged_updated_at: "2026-05-31T10:00:00Z", updated_at: "...maintenant..." }

await safeUpdate(supabase, "patients", payload, { id: patient.id }, { userId });

5.4 Tolérance 1 seconde

Les timestamps de PostgreSQL et Supabase peuvent avoir des différences de précision. On considère donc qu'une différence ≤ 1 seconde n'est pas un conflit (c'est probablement la même modif aller-retour). Au-delà, c'est un vrai conflit.

5.5 Compteur de conflits

replayQueue retourne maintenant { tried, succeeded, failed, conflicts, remaining }. Les conflits sont une catégorie distincte des "failed" (erreur réseau / contrainte / etc.).

5.6 UX en cas de conflit

Pour la 0.26, l'op reste en queue avec un message clair dans last_error visible dans la modale "Actions en attente". L'utilisateur peut :

  • Cliquer "Réessayer" → si Bob a refait quelque chose entre-temps, ça réessaiera
  • Supprimer manuellement de la queue (abandon)
  • Plus tard (0.27+) : modale dédiée "Voir ce qui a changé" + "Forcer ma version" / "Garder la version actuelle"

8. Procédure d'application

  1. Pas de SQL. Aucun changement de schéma.
  2. Décompresser le zip par-dessus C:\aveho-ec-app\.
  3. npm install + tests + dev : 
    cd C:\aveho-ec-app
npm install
npm test       # 176 passed
npm run dev
  4. Tester en local :
    • Aller dans /achats
    • F12 → Network → Offline
    • Créer un achat avec lignes → enregistré localement, bandeau rouge apparait
    • Reconnect → sync auto, achat apparaît en base avec son UUID
    • Pareil pour /interventions, /signalements
    • Tester aussi un référentiel (ex: /etiquettes) → via Crud, offline OK aussi
  5. Test conflit (avancé) :
    • Charger un patient en local, passer offline
    • Modifier sa chambre → en queue
    • Dans un autre navigateur/onglet (toujours online), modifier le même patient (médecin traitant)
    • Reconnect le 1er navigateur → la sync va échouer pour cause de conflit, visible dans la modale "Actions en attente"
