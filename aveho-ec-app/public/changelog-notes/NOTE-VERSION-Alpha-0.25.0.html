1. Résumé exécutif

La 0.25.0 ajoute un véritable mode hors-ligne avec queue d'écritures persistante via IndexedDB. C'était la grosse lacune d'Aveho EC pour les usages terrain : un soignant dans un ascenseur, un livreur en zone blanche, un infirmier en domicile sans réseau pouvaient perdre leur saisie. Plus maintenant.

  1. Queue IndexedDB : module lib/offlineQueue.js avec API simple (enqueue, list, count, replay, clear). Stocke les opérations Supabase à exécuter dans aveho-offline-queue (DB IndexedDB du navigateur).
  2. Helpers safeWrite : safeInsert, safeUpdate, safeDelete, safeRpc. En online → exécution normale Supabase. En offline → mise en queue automatique + retour "pseudo-succès" pour ne pas bloquer le flow UI.
  3. Hook useOffline : expose { online, queueCount, syncing, lastSync, syncNow(), clearAll() } pour les composants UI.
  4. OfflineBanner enrichi : 3 états visuels (rouge offline, orange queue non vide, bleu syncing) + modale détail des actions en attente avec liste, tentatives, erreurs.
  5. Intégration sur /patients : page modèle utilisant safeWrite. Les autres pages peuvent migrer progressivement.
Sync automatique transparente. Quand l'utilisateur reconnecte le réseau, le hook détecte l'événement online, attend 1.5s (laisser stabiliser), et rejoue la queue dans l'ordre FIFO. Chaque opération tentée échoue ou réussit indépendamment. Maximum 5 tentatives avant abandon (configurable).

3. Architecture

3.1 Flow online classique

  1. L'utilisateur clique "Enregistrer" sur un patient
  2. Le code appelle safeInsert(supabase, "patients", payload, { userId })
  3. isOnline() retourne true → exécution normale supabase.from("patients").insert(payload)
  4. Retour { data, error, queued: false }
  5. UI se met à jour, modale se ferme, liste reload

3.2 Flow offline avec queue

  1. L'utilisateur est dans un ascenseur, perd le réseau
  2. Il continue à utiliser l'app, clique "Enregistrer" sur un patient
  3. Code appelle safeInsert
  4. isOnline() retourne false → l'opération est mise en queue IndexedDB avec un timestamp
  5. Pour les inserts : un UUID est généré côté client (crypto.randomUUID()) et utilisé comme id provisoire
  6. Retour { data: { _queueId, ...payload }, error: null, queued: true }
  7. L'UI continue normalement (modale RGPD s'ouvre, rattachement au lit fonctionne, etc.)
  8. Le bandeau orange apparaît : "1 action non synchronisée"
  9. L'utilisateur sort de l'ascenseur, retrouve le réseau
  10. Le navigateur émet l'event online
  11. Le hook useOffline attend 1.5s, appelle replayQueue
  12. Bandeau bleu "Synchronisation en cours…"
  13. Chaque opération est rejouée dans l'ordre FIFO
  14. Succès : retire de la queue. Échec : incrémente attempts, reste en queue.
  15. Quand attempts >= 5 : abandonné (visible dans la modale, à supprimer manuellement)
  16. Bandeau disparaît quand queue vide + plus de sync

4. Queue IndexedDB

4.1 Structure de la base

Database: aveho-offline-queue (v1)
Store: queue
  - id: auto-increment (clé primaire)
  - table: text (ex: "patients", "materiels")
  - op: text ("insert" | "update" | "delete" | "rpc")
  - payload: any (données ou args RPC)
  - match: { id: "...", ... } (pour update/delete)
  - rpcName: text (pour op rpc)
  - user_id: text (index, pour filtrer)
  - created_at: number (timestamp, index)
  - attempts: number
  - last_error: text | null

4.2 API exposée

FonctionUsage
enqueueOp(op)Ajoute une opération, retourne son id auto-incrément
listQueue(userId)Liste FIFO des opérations pour l'utilisateur
countQueue(userId)Compte rapide pour le badge UI
bumpAttempts(id, error)Incrémente attempts + stocke last_error
removeOp(id)Supprime (utilisé après succès)
clearQueue(userId)Vide toute la queue d'un user
isOnline()navigator.onLine + fallback SSR-safe
replayQueue(supabase, userId, opts)Rejoue toute la queue, retourne { tried, succeeded, failed, remaining }

4.3 Persistance

IndexedDB est persistant : la queue survit au refresh, à la fermeture du navigateur, voire au redémarrage de l'OS. Tant que l'utilisateur ne vide pas le cache du navigateur, ses actions sont préservées.

Limite : la queue est par appareil/navigateur. Si l'utilisateur ouvre Aveho sur un autre appareil, il ne verra pas la queue de l'appareil hors-ligne. Acceptable car les soignants en déplacement utilisent presque toujours le même appareil.

5. Helpers safeWrite

5.1 Usage

import { safeInsert, safeUpdate, safeDelete, safeRpc } from "../../lib/safeWrite";

// Insert
const { data, error, queued } = await safeInsert(
  supabase, "patients", { nom: "Dupont" }, { userId: auth.user?.id, returning: true }
);
if (queued) toast("Enregistré localement, sync à la reconnexion");

// Update
await safeUpdate(supabase, "patients", { etat: "Sorti" }, { id: "abc" }, { userId });

// Delete
await safeDelete(supabase, "patients", { id: "abc" }, { userId });

// RPC (attention : uniquement les RPC idempotents)
await safeRpc(supabase, "mark_consent_notified", { ids: ["1"] }, { userId });

5.2 UUID client pour INSERT offline

Quand on insère un patient offline, on ne peut pas attendre l'id généré par Supabase. Solution : on génère un UUID v4 côté client avec crypto.randomUUID() et on l'envoie comme id dans l'insert. Postgres accepte parfaitement les UUID client-fournis pour les colonnes uuid primary key default gen_random_uuid().

Avantage : l'app peut immédiatement rattacher le patient à un lit, ouvrir la modale RGPD, etc. Le flow ne casse pas.

5.3 Retour { queued } pour adapter l'UI

Le booléen queued permet à l'appelant d'afficher un toast spécifique :

if (queued) {
  toast("✓ Enregistré localement, sera synchronisé à la reconnexion");
} else if (error) {
  toast.error(error.message);
} else {
  toast.success("Enregistré");
}

6. Hook useOffline

Hook React unifié pour les composants UI :

const {
  online,        // boolean — true si en ligne
  queueCount,    // number — nombre d'actions en attente
  syncing,       // boolean — rejeu en cours
  lastSync,      // timestamp — dernière sync
  lastResult,    // { tried, succeeded, failed, remaining }
  syncNow,       // () => rejouer manuellement
  clearAll,      // () => vider la queue (avec confirm)
  getQueueItems, // () => liste détaillée pour modale
  refreshCount,  // () => recompter
} = useOffline(userId);

Auto-refresh toutes les 10s pour capturer les ajouts queue par d'autres parties de l'app.

Auto-sync à la reconnexion (event online + délai 1.5s).

8. Intégration page patients

La page /patients sert de modèle. Modifications :

  • Import : import { safeInsert, safeUpdate, safeDelete } from "../../lib/safeWrite";
  • save() : supabase.from("patients").update() → safeUpdate(supabase, "patients", payload, { id }, { userId })
  • save() insert : génère UUID côté client si offline, utilise safeInsert
  • Updates des lits (rattacher/libérer) : safeUpdate
  • del() : safeDelete

Migration progressive : les autres pages (achats, matériels, interventions, etc.) peuvent migrer une par une vers safeWrite. Tant qu'elles utilisent supabase.from().insert() directement, elles échouent en offline (comportement avant 0.25, pas de régression).

10. Procédure d'application

  1. Pas de SQL. Aucun changement de schéma.
  2. Décompresser le zip par-dessus C:\aveho-ec-app\ (ou aveho-ec-app-01\).
  3. npm install + tests + dev : 
    cd C:\aveho-ec-app
npm install
npm test       # 156 passed
npm run dev
  4. Tester en local :
    • Ouvrir l'app, aller dans /patients
    • Ouvrir DevTools → Network → cocher Offline
    • Créer un nouveau patient → le bandeau rouge apparaît, le patient s'enregistre quand même
    • Cliquer sur le bandeau → modale "Actions en attente" avec l'insert visible
    • Décocher Offline dans DevTools → le bandeau passe en bleu "Synchronisation…" → puis disparaît
    • Vérifier en base Supabase que le patient est bien arrivé avec l'UUID généré côté client

11. Reste à faire (0.26+)

Pistes pour la suite :

  • Migration de toutes les pages vers safeWrite (achats, matériels, interventions, signalements, etc.). Aujourd'hui seul /patients est offline-ready.
  • Cache de lecture offline : actuellement, en offline, les pages affichent les données déjà chargées dans React state, mais à un refresh, c'est vide. Solution : mise en cache des SELECT dans IndexedDB aussi.
  • Conflit de version : si Bob modifie le même patient pendant qu'Alice est offline, à la sync Alice écrase Bob. À gérer plus tard avec un champ updated_at et un check optimiste.
  • Indicateur "queue cleared" : toast de confirmation quand la queue passe à 0.
  • Tests Playwright sur le flow offline complet (DevTools throttling)
  • Quality of life : sauvegarde des filtres par utilisateur (localStorage), préférences notif par user
  • Dashboard statistiques RGPD
  • Modèles consentement personnalisables
