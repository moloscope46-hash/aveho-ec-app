🏗 1. Table dédiée etablissements_partenaires

Pourquoi une table séparée ?

Avant : etablissements.est_partenaire = true → mélange dans la même table, requêtes polluées par les filtres, RLS partagée, pas de champs spécifiques.

Maintenant : table dédiée etablissements_partenaires avec 29 colonnes :

  • Identité : nom, type, type_relation (Prescripteur / Fournisseur / Sous-traitant / Confrère / Autre)
  • Identifiants officiels : finess, siret, siren (un partenaire externe a souvent un SIRET et pas de FINESS)
  • Adresse : adresse, cp, ville, pays, latitude, longitude
  • Contact référent : contact_nom, contact_fonction, telephone, email, site_web
  • Métadonnées : notes, tags[], groupement_id
  • Transition douce : link_to_etablissement_id (pointe vers etablissements si bascule depuis legacy)
  • État : actif, archive
  • Audit : created_at, created_by, updated_at, updated_by

Index sur structure_id, finess, siret, groupement_id. RLS member_rw. Trigger updated_at automatique.

📜 2. Table d'audit dédiée etab_partenaires_audit

Schéma

create table etab_partenaires_audit (
  id uuid primary key,
  ts timestamptz,
  action text,        -- 'INSERT' | 'UPDATE' | 'DELETE'
  partenaire_id uuid,
  structure_id uuid,
  user_id uuid,       -- auteur de l'action (auth.uid())
  old_data jsonb,     -- snapshot AVANT (UPDATE/DELETE)
  new_data jsonb,     -- snapshot APRÈS (INSERT/UPDATE)
  changes jsonb       -- diff colonne-par-colonne (UPDATE)
);

Trigger automatique

  • AFTER INSERT → log avec new_data
  • AFTER UPDATE → calcule le diff colonne-par-colonne, log SEULEMENT si au moins un champ a changé (skip si seul updated_at/updated_by ont bougé)
  • AFTER DELETE → log avec old_data

RLS

  • SELECT : seulement les admins de la structure (parametres_admin OU utilisateurs_write)
  • INSERT : ouvert (les triggers y écrivent via security definer)

Visualisation dans l'UI

Bouton "Audit" en haut de la page /etablissements-partenaires → modale avec les 50 dernières actions :

  • Badge coloré par action (INSERT vert, UPDATE ambre, DELETE rouge)
  • Nom du partenaire concerné + timestamp
  • Sur UPDATE : <details> dépliable avec diff champ-par-champ (rouge barré → vert)

📦 3. Migration automatique des données

Le patch SQL fait automatiquement (et idempotent) :

for e in (select * from etablissements where est_partenaire = true)
  if not already_migrated(e.id):
    insert into etablissements_partenaires (...) values (...);
    set link_to_etablissement_id = e.id

Affiche le compte dans NOTICE PostgreSQL : Migration : N partenaires copiés vers etablissements_partenaires

Pas de DELETE sur l'ancienne table pour garder la rétrocompatibilité (l'ancienne UI continue de fonctionner). La déduplication est gérée côté vue-globale.

🔄 5. Vue-globale dual-source

La page /vue-globale charge maintenant depuis 2 tables séparées en parallèle :

Promise.all([
  supabase.from("etablissements").select("...").eq("structure_id", id),
  supabase.from("etablissements_partenaires").select("...").eq("archive", false),
  // + patients, materiels, di, commandes
])

Puis fusion intelligente :

  • mineRows = etablissements WHERE !est_partenaire
  • partnersFromNewTable = etablissements_partenaires (archive=false)
  • legacyPartners = etablissements WHERE est_partenaire=true ET NOT IN (link_to_etablissement_id) — pour éviter les doublons avec la migration

Le toggle Mes / Partenaires / Tous (de 0.55.29) continue de fonctionner.

🔧 6. RPC convert_etab_to_partner

Pour basculer manuellement un établissement legacy vers la nouvelle table :

const { data, error } = await supabase.rpc("convert_etab_to_partner", {
  p_etab_id: "uuid-de-l-etab"
});
// → { ok: true, partenaire_id: "nouveau-uuid" }
// L'ancien est marqué est_partenaire=true pour cohérence

Vérif droits parametres_admin · security definer · grant authenticated.
