1. Résumé exécutif

L'Alpha 0.6 livre le dernier gros chantier reporté depuis la 0.2 : le mode hors-ligne PWA. La consultation devient possible sans réseau (lectures servies depuis le cache). L'écriture hors-ligne (mode brouillon avec sync différée) n'est pas livrée — c'est trop risqué à faire en lot, je le réserve pour une 0.7 dédiée si tu en as besoin. C'est aussi la version qui met enfin en pratique les notifications ciblées (assignation de DI) et qui rend l'accueil personnalisable.

Transparence sur le hors-ligne : ce qui est livré = consultation des dernières données vues quand on coupe le réseau, avec un bandeau rouge visible et une stratégie de cache adaptée par type de requête. Ce qui n'est PAS livré = pouvoir créer/modifier en mode déconnecté avec sync au retour. C'est volontairement reporté.

3. Mode hors-ligne PWA NOUVEAU

3.1 Stratégies de cache par type de requête

Le service worker (public/sw.js) applique 3 stratégies différentes selon le type de la requête interceptée :

TypeStratégiePourquoi
Manifest, icônes, fontscache-firstStatique, change rarement
JS/CSS Next.js (/_next/static/)cache-firstHashés et immutables par build
Pages HTML (navigation)network-firstToujours la dernière version, fallback cache si déconnecté
GET Supabase REST/RPCstale-while-revalidateAffichage immédiat du cache + refresh en arrière-plan
POST/PATCH/DELETE Supabasenetwork-onlyÉcritures ne doivent JAMAIS passer en cache

3.2 Bandeau hors-ligne

Quand le navigateur signale qu'il est hors-ligne (évènement offline), un bandeau rouge s'affiche en haut de toutes les pages :

┌─────────────────────────────────────────────────────────────┐
│ 📡 Mode hors-ligne. Tu peux consulter les dernières données │
│    vues, mais les modifications seront refusées tant que    │
│    la connexion n'est pas rétablie.                          │
└─────────────────────────────────────────────────────────────┘

Au retour en ligne (évènement online), le bandeau disparaît automatiquement.

3.3 Trois caches séparés

Chaque déploiement crée 3 caches versionnés (ex: aveho-ec-0.6-static, aveho-ec-0.6-data, aveho-ec-0.6-pages). Au prochain déploiement, les anciens caches sont automatiquement supprimés — pas de croissance infinie.

4. Assignation explicite des DI NOUVEAU

4.1 Nouvelle colonne SQL

alter table interventions
  add column assignee_id uuid references auth.users(id) on delete set null,
  add column assignee_email text;  -- snapshot pour affichage rapide

create index idx_interv_assignee on interventions (assignee_id);

4.2 Modale d'assignation

Sur chaque ligne de DI, un bouton Assigner / Réassigner ouvre une modale qui liste les membres de la collectivité. Clic sur un membre →

  1. Met à jour interventions.assignee_id
  2. Pose une trace dans audit_log (action "modifier")
  3. Crée une notification ciblée (user_id = l'assigné), avec le titre "DI qui t'est assignée". La cloche de l'assigné pulse aussitôt.

Bouton Désassigner aussi disponible.

4.3 Le paramètre notifUserId de logEvent enfin utilisé

En 0.5 j'avais exposé techniquement le paramètre notifUserId du helper logEvent mais pas encore utilisé. En 0.6 c'est fait : la modale d'assignation est le premier cas d'usage réel. Pattern réutilisable pour toute future fonctionnalité avec destinataire identifié.

5. Dashboard accueil personnalisable NOUVEAU

Bouton Personnaliser en haut à droite de l'accueil → panneau avec 4 cases à cocher :

  • Indicateurs clés (KPIs promotions, commandes, montant à régler)
  • Raccourcis vers les modules (4 boutons : patients, matériel, stock, DI)
  • Dernières commandes (top 5)
  • Notifications récentes (top 5)

Les choix sont mémorisés dans localStorage sous la clé aveho_dashboard — donc personnels au navigateur, pas synchronisés entre appareils (volontaire pour simplifier).

9. Procédure de mise à jour depuis Alpha 0.5

  1. Sauvegarde ton dossier C:\aveho-ec-app.
  2. Décompresse le nouveau zip par-dessus.
  3. Dans Supabase SQL Editor : exécute supabase/12_di_assignation.sql
  4. Dans PowerShell :
    cd C:\aveho-ec-app
npm install
npm run dev
  5. Pour tester le hors-ligne en local :
    • Ouvre l'app dans Chrome
    • F12 → onglet Network → coche Offline
    • Le bandeau rouge doit apparaître en haut
    • Recharge la page : les données déjà chargées s'affichent toujours (depuis le cache du SW)
    • Essaie de créer un transfert : l'erreur réseau apparaît (normal, l'écriture exige le réseau)
  6. Mise en ligne :
    git add .
git commit -m "Aveho EC Alpha 0.6"
git push
    ⚠️ Important côté production : le service worker est versionné (aveho-ec-0.6), donc au prochain déploiement Vercel les anciens caches seront automatiquement nettoyés. Les utilisateurs avec l'app PWA installée verront le nouveau SW au prochain rafraîchissement.

10. Limites assumées du mode hors-ligne

Pour que tu saches exactement ce que tu as et ce que tu n'as pas :

Cas d'usageStatut 0.6
Consulter une liste déjà chargée auparavant✓ OK (servi depuis cache)
Naviguer entre pages déjà visitées✓ OK
Consulter une liste jamais chargée✗ Erreur "hors-ligne"
Créer / modifier / supprimer un patient✗ Erreur, réessayer connecté
Mémorisation d'un brouillon offline✗ Pas implémenté (en 0.7 si besoin)
Synchronisation automatique au retour en ligne✗ Pas implémenté
Cache des images médias✗ Pas géré (les images Supabase Storage passent en réseau direct)

Ce niveau (consultation seule) couvre 80% des cas d'usage en mobilité (regarder un dossier patient dans un service sans wifi). Si tu as besoin du mode écriture différée, dis-le moi et je prépare une 0.7 dédiée.
