🔒 1. Durcissement SQL

security_invoker sur toutes les vues récentes

Par défaut, les vues PostgreSQL exécutent les requêtes avec les droits de leur créateur (souvent postgres ou service_role), ce qui peut contourner les RLS. Avec security_invoker = true, les vues respectent les RLS de l'appelant.

alter view v_users_auth_methods set (security_invoker = true);
alter view v_my_webauthn_credentials set (security_invoker = true);
alter view v_user_complete set (security_invoker = true);

Index manquants pour performance

  • idx_webauthn_user_active (user_id WHERE active=true) — gain sur listage des credentials
  • idx_invitations_token_active (token WHERE archive=false) — gain sur lookup d'invitations
  • idx_audit_log_struct_user_date — gain sur historique d'activité utilisateur
  • idx_app_logs_user_date — gain sur logs applicatifs
  • idx_membres_matricule (structure_id + matricule, partial) — pour la recherche par matricule (nouveau en 0.55.25)

GRANT explicites sur les RPCs

revoke all on function reset_user_password(uuid) from public;
grant execute on function reset_user_password(uuid) to authenticated;
-- idem pour get_invitation_full, revoke_webauthn_credential, update_webauthn_last_used

Table d'audit security_audit_log

Stocke les événements sensibles (changements de rôle, demandes de réinit mdp, etc.) avec RLS qui limite la lecture aux admins de la structure. Un trigger sur membres_structure log automatiquement les changements de role_id.

🔇 2. Logger sécurisé avec redaction

Nouveau lib/logger.js

  • En développement (localhost) → tous les logs passent comme avant
  • En production (Vercel) → logger.debug, logger.info, logger.warn sont silencieux. Seuls logger.error et logger.security passent
  • Redaction automatique : avant d'imprimer, les clés sensibles (password, token, refresh_token, credential_id, etc.) sont remplacées par "[REDACTED]"
  • Troncature strings : les valeurs > 100 caractères sont tronquées (12 premiers chars + "[redacted]") — évite que des tokens longs ne fuitent
  • Helpers globaux : tu peux activer/désactiver les debug logs en prod depuis la console : 
    __avehoEnableDebug()    // active les logs
__avehoDisableDebug()   // désactive

⚡ 5. Service Worker — cache borné

Le cache pouvait croître indéfiniment (chaque page visitée, chaque RPC Supabase fetché). Sur les comptes utilisateurs intensifs ça pouvait représenter plusieurs Mo après quelques semaines.

const MAX_DATA_CACHE_ENTRIES = 100;   // Supabase REST/RPC
const MAX_PAGE_CACHE_ENTRIES = 30;    // pages HTML

async function trimCache(cacheName, maxEntries) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length <= maxEntries) return;
  const toDelete = keys.slice(0, keys.length - maxEntries);
  await Promise.all(toDelete.map((k) => cache.delete(k)));
}

Appelé après chaque cache.put dans networkFirst et staleWhileRevalidate. LRU : supprime les plus anciennes entrées.
