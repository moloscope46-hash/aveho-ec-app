Résumé

La 0.28.0 finit le travail entamé sur le mode hors-ligne en s'attaquant aux deux gros points qui restaient :

  1. Invalidation cache automatique : tant qu'on ne vide pas le cache après une modification, on sert des données stale jusqu'à expiration (7 jours par défaut). Désormais, safeInsert, safeUpdate et safeDelete appellent automatiquement cacheInvalidate("{table}:") en cas de succès online. Option skipInvalidate: true pour opt-out si nécessaire.
  2. Couverture quasi-totale des écritures : 6 pages métier supplémentaires migrées vers safeWrite, soit ~95% des écritures applicatives. Les soignants en mobilité peuvent désormais travailler offline sur la quasi-totalité des workflows.

Couverture offline ≈ 95%. Les pages restantes non migrées (utilisateurs, parametres, etablissement/edition, collectivite, NotifBell, NotificationOptIn, login) sont principalement de la configuration/admin avec faible usage en mobilité — leur migration est cosmétique et peut attendre.

Invalidation cache auto

Problème

Avant la 0.28, si un utilisateur modifie un patient en online, le cache IndexedDB contenait toujours l'ancienne version (TTL 7 jours). Au refresh suivant en offline, il revoyait l'ancienne valeur jusqu'à expiration. Données stale → frustration et bugs métier.

Solution

// Nouvelle fonction dans offlineCache.js
export async function cacheInvalidate(prefixes) {
  // Parcourt IndexedDB store "cache"
  // Supprime toutes les clés commençant par un préfixe
  // ex: cacheInvalidate("patients:") supprime
  //   "patients:etab:struct1", "patients:etab:struct2", etc.
}

Intégration transparente dans safeWrite

// Dans safeUpdate (idem safeInsert et safeDelete)
const res = await q;
if (!res.error && !skipInvalidate && table) {
  cacheInvalidate(`${table}:`).catch(() => {});
}
return { ...res, queued: false };

Donc maintenant, dès qu'un patient est modifié avec succès, toutes les clés cache patients:* sont purgées. Le prochain safeFetch("patients:etab:...") ira chercher la version fraîche en base.

Opt-out via skipInvalidate

Pour les rares cas où on veut éviter la purge (ex: bulk update qui sera suivi d'autres écritures sur la même table, on n'invalide qu'à la fin) :

await safeUpdate(supabase, "patients", payload, { id }, { userId, skipInvalidate: true });
// ... autres updates ...
await cacheInvalidate("patients:"); // manuel à la fin

Migration safeWrite — 6 pages

Transferts

Workflow complet migré : save() avec UUID client, advance() sur les statuts, et la cascade de mise à jour stock à réception (safeUpdate sur stock_articles, safeInsert si nouvelle ligne stock).

Maintenance

3 fonctions migrées :

  • save() : update ou insert avec UUID client
  • save() : récurrence auto-créée → safeInsert avec UUID
  • del() : safeDelete

Panier

La validation de commande crée une commande + N commande_lignes en cascade. Tout est passé en safeWrite avec UUID client : le cmdId est généré côté JS pour pouvoir rattacher les lignes immédiatement, même en offline.

Patient / [id] (fiche patient)

Toggle étiquettes via safeInsert/safeDelete sur patient_etiquettes. Permet à un soignant de tagger un patient (urgence, sous oxygène, etc.) même offline.

Materiels (liste)

Pareil pour les tags matériels : toggle via safeWrite sur materiel_tags.

ConsentementRGPD

Les deux inserts (refus et signé) passent par safeInsert. Conséquence : un consentement peut être recueilli offline (signature tactile capturée localement, hash calculé, payload stocké en queue). À la reconnexion, l'insert se fait et la signature est uploadée.

Note : l'upload de la signature PNG dans Storage reste en direct (pas mis en queue). Si offline, l'upload échouera et le consentement aura un signature_storage_path null. À améliorer en 0.29+ avec une queue d'uploads séparée.

4e page avec cache lecture

Clé cache : signalements:etab:{etabId|all}. Bandeau StaleDataBanner ajouté juste sous le PageHead.

Procédure d'application

  1. Pas de SQL.
  2. Décompresser le zip par-dessus C:\aveho-ec-app\.
  3. npm install + tests + dev : 
    cd C:\aveho-ec-app
npm install
npm test       # 210 passed
npm run dev
  4. Test invalidation cache :
    • Aller dans /patients, charger la page (cache se remplit)
    • Modifier un patient (changer sa chambre par ex) → save
    • F12 → Network → Offline
    • F5 → la liste s'affiche depuis cache MAIS doit contenir la modif (car invalidation a forcé un refetch avant de cacher la version à jour)
  5. Test offline complet sur transferts :
    • Aller dans /transferts
    • Offline → créer un transfert → bandeau rouge, transfert en queue
    • Reconnect → sync auto, le transfert apparaît avec son numéro
  6. Test ConsentementRGPD offline :
    • Ouvrir un patient sans consentement
    • Offline → cliquer "Refuser" → consentement refus en queue
    • Reconnect → sync, le refus apparaît dans /consentements
