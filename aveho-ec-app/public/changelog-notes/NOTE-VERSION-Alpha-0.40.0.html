Résumé

5 chantiers en une version, sélectionnés directement dans la roadmap. Audit préalable (leçon de la 0.35) : aucun doublon détecté. Build clean, 607 tests verts.

5 modules livrés d'un coup :
F Préférences digest email + Edge Function send-digest qui envoie des récaps personnalisés.
K Signalements enrichis avec système de votes (1 vote / user) + champ catégorie libre + badge "Sujet populaire" automatique.

Chantiers livrés

F Notifications digest (email récap automatique)

  • Table SQL notification_digest_prefs : 1 ligne par user avec frequence (jamais / quotidien / hebdo)
  • Table SQL notification_digest_log : trace anti-doublon
  • Composant React <DigestPreferences> : 3 cartes cliquables avec auto-save
  • Integration dans /profil juste sous le bloc "Mes notifications"
  • Edge Function send-digest : envoie via Resend, template HTML brandé avec compteurs colorés par catégorie (DI / Achats / Signalements / Renouvellements RGPD)
  • Logique : quotidien tous les jours à 8h UTC, hebdo uniquement le lundi. Filtre côté SQL.
  • Anti-spam intelligent : si hasContent === false (rien à signaler), pas d'envoi (sauf dry_run pour test)
  • RLS : un user ne lit/écrit que ses propres prefs et logs

Test manuel de la Edge Function

# Dry-run pour un user spécifique
curl -X POST https://<projet>.functions.supabase.co/send-digest \

  -H "Content-Type: application/json" \
  -d '{"dry_run": true, "user_id": "<ton-uuid>"}'

K Signalements enrichis : votes + catégories

  • Colonne SQL signalements.categorie (text libre, optionnel) — alimenté par un input avec datalist de suggestions (UI/UX, Bug, Performance, Sécurité…)
  • Colonne SQL signalements.nb_votes (int, maintenu par trigger)
  • Table SQL signalement_votes : PK composite (signalement_id, user_id) garantit 1 vote / user / signalement
  • Trigger trg_signalement_votes : maintient automatiquement nb_votes sur INSERT/DELETE
  • RLS : tout user authentifié peut voir les votes (transparence), insérer/supprimer ses propres votes uniquement
  • UI : bouton like compact à côté de chaque signalement, état actif coloré navy, animation transition
  • Badge "Sujet populaire" automatique dès 3 votes (flame orange à côté du compteur)
  • Champ catégorie dans le formulaire de création/édition avec autocomplete via <datalist>
  • Affichage : badge violet visible sous le titre du signalement

L Stats RGPD enrichies (3 nouveaux blocs)

  • Heatmap des signatures v_stats_rgpd_heatmap : signatures par jour de semaine × heure sur 90 jours (vert au lieu de bleu pour différencier de la heatmap d'activité)
  • Vue v_stats_rgpd_par_finalite : compteurs par finalité avec tendance ce mois — drill complémentaire à v_stats_rgpd_finalites qui agrégeait déjà mais sans le détail temporel
  • Vue v_stats_rgpd_renouvellements : compteurs des consentements qui arrivent à expiration (en supposant un renouvellement annuel à 365j)
    • Expirés (passé 365j)
    • Expire dans ≤ 7 jours
    • Expire dans ≤ 15 jours
    • Expire dans ≤ 30 jours
  • UI : 4 cartes "RenouvCard" colorées (rouge si expiré, orange si urgent, bleu sinon). Bordure gauche orange sur le panneau pour signaler une zone d'attention
  • UI finalités : barres horizontales avec gradient violet→vert, ordre décroissant par nb_acceptations, top 10 affichés, badge "+N ce mois" en vert si actualité récente

G Variables custom dans les templates RGPD

  • Stockage dans structures.parametres.rgpd_custom_vars (jsonb array — pas de nouvelle table)
  • Format : [{ key, label, value, example }] avec validation key minuscules + underscores uniquement
  • Helpers lib/rgpd.js :
    • loadCustomVariables(supabase, structureId)
    • saveCustomVariables(supabase, structureId, variables)
  • UI nouveau panneau dans /parametres-rgpd avec bordure gauche violette, liste des variables actuelles en grille + bouton "Modifier"
  • Modale d'édition : 4 colonnes par ligne (clé, libellé, valeur, suppression), bouton "+ Ajouter une variable", nettoyage automatique de la clé (regex)
  • Intégration dans renderConsentement : substitution des {{cle}} custom appliquée après les variables standard. Sécurité : la clé est re-nettoyée à la substitution pour éviter toute injection regex
  • validateTemplate signature étendue : 2e paramètre optionnel customVarKeys évite les warnings "variable inconnue" sur les clés custom de la structure
  • ConsentementRGPD (signature côté patient) charge les variables custom et les passe au render — le texte final substitue tout en une passe

Exemple d'usage : une collectivité partenaire d'un télé-service ajoute :

key: partenaire_nom        value: TéléSuivi+ SAS
key: partenaire_url        value: https://telesuivi.fr

Puis dans le template : "Les données pourront être partagées avec notre partenaire {{partenaire_nom}} ({{partenaire_url}})."

J PatientPreview étendu à /interventions

  • Le PatientPreview de la 0.38 ne fonctionnait que dans /patients
  • Extension : wrap du nom patient dans la liste DI (/interventions)
  • Select Supabase enrichi pour inclure patient.id, date_naissance, numero_dossier
  • Le preview affiche les infos disponibles (sans lit ni étiquettes ni compteur DI/achats préchargés), mais la dernière DI lazy est toujours fetchée au hover
  • Note : pour /achats et /transferts, le patient n'est pas affiché dans les listes actuelles → reporté à plus tard si besoin métier

Procédure d'application

  1. SQL d'abord dans Supabase → SQL Editor → coller aveho-PATCH-vers-0.40.sql → Run (idempotent).
  2. Vérifier : 
    -- Nouvelles tables
select count(*) from notification_digest_prefs;
select count(*) from signalement_votes;
-- → 0 (vide au début)

-- Colonnes ajoutées
select column_name from information_schema.columns 
where table_name='signalements' 
  and column_name in ('categorie','nb_votes','reponse_notifie');
-- → 3 lignes

-- Vues RGPD
select * from v_stats_rgpd_heatmap limit 5;
select * from v_stats_rgpd_renouvellements 
  where structure_id='aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa';
  3. Déployer la Edge Function send-digest (Supabase CLI ou copier le code via Dashboard) : 
    supabase functions deploy send-digest
# Vérifier les secrets : RESEND_API_KEY, RESEND_FROM_EMAIL déjà en place depuis 0.33
  4. Programmer le cron côté Supabase : 
    -- Tous les jours à 8h UTC
select cron.schedule(
  'aveho-digest-8h',
  '0 8 * * *',
  $$ select net.http_post(
       url := 'https://<projet>.functions.supabase.co/send-digest',
       headers := jsonb_build_object(
         'Authorization', 'Bearer <service-role-key>',
         'Content-Type', 'application/json'
       ),
       body := '{}'::jsonb
     ); $$
);
  5. Décompresser le zip par-dessus C:\aveho-ec-app\.
  6. Nettoyer le cache + npm install + tests + dev : 
    cd C:\aveho-ec-app
Remove-Item -Recurse -Force .next -ErrorAction SilentlyContinue
npm install
npm test       # 607 passed
npm run dev
  7. Tester :
    • /profil → nouveau bloc "Récap email automatique" → choisir "Quotidien" ou "Hebdo"
    • /signalements → bouton 👍 sur un signalement → compteur s'incrémente. Réessayer = retrait. À partir de 3 votes : badge "Sujet populaire"
    • Créer un signalement → champ catégorie avec autocomplete (Bug, UI/UX…)
    • /statistiques-rgpd → bloc Heatmap signatures (vert), bloc Renouvellements (4 cartes), bloc Acceptation par finalité (barres horizontales)
    • /parametres-rgpd → nouveau Panel "Variables personnalisées" → "Définir des variables" → modale d'édition → ajouter partenaire_nom = "Société XYZ" → enregistrer
    • Créer ou modifier un template, utiliser {{partenaire_nom}} dans le contenu → preview live montre la substitution
    • Signer un consentement réel pour un patient → le PDF/affichage contient bien la valeur substituée
    • /interventions → hover sur le nom d'un patient dans la liste DI → mini-preview avec dernière DI lazy
