1 Crossover lib/↔app/ dans les dialogs

Erreur dans la console runtime, sur toutes les pages :

Unhandled Runtime Error
TypeError: Cannot read properties of undefined (reading 'call')

  Call Stack
    options.factory (webpack.js:715)
    __webpack_require__ (webpack.js:37)
    fn (webpack.js:371)
    requireModule (react-server-dom-webpack-client.browser…)
    initializeModuleChunk
    readChunk
    mountLazyComponent
    beginWork$1
    …

Diagnostic : ces erreurs options.factory sur un requireModule indiquent toujours qu'un import résout sur undefined à l'exécution. 3 causes possibles :

  1. Cycle d'import (A importe B qui importe A indirectement)
  2. Re-export mal formé (export { X } sur quelque chose qui n'existe pas)
  3. Crossover de dossiers dans Next.js App Router : un fichier dans lib/ importe depuis ../app/... qui ré-importe vers app/ui.js

Cause exacte ici : c'était le cas 3. La chaîne d'import était :

app/layout.js  (Server Component)
  ↓ import { DialogsHost }
lib/dialogs.js  ("use client")
  ↓ import { ConfirmModal, AlertModal }
app/modals/index.js  ("use client")
  ↓ import { Modal, Btn }
app/ui.js  ("use client")

Le passage par lib/ au milieu de cette chaîne casse la résolution des modules client côté server-component du layout. Webpack n'arrive pas à fournir le bon module à React quand il instancie DialogsHost.

Correction : consolider tous les dialogs dans un seul fichier côté app/ uniquement, sans repasser par lib/.

- lib/dialogs.js          (SUPPRIMÉ)
- app/modals/index.js     (SUPPRIMÉ)
+ app/dialogs.js          (CRÉÉ — tout en un)

  Imports modifiés :
- app/layout.js  : import { DialogsHost } from "../lib/dialogs"
+ app/layout.js  : import { DialogsHost } from "./dialogs"

- app/admin-perf/page.js  : import { useConfirm } from "../modals"
+ app/admin-perf/page.js  : import { useConfirm } from "../dialogs"

Le nouveau app/dialogs.js regroupe :

  • <ConfirmModal>, <AlertModal> (composants)
  • useConfirm(), useAlert() (hooks programmatiques)
  • dialogs.confirm(), dialogs.alert() (singleton global)
  • <DialogsHost /> (à mettre dans le layout, une seule fois)

Leçon : si un composant client doit être référencé par le layout root (Server Component), le garder dans app/ ET éviter les chaînes d'imports qui traversent lib/ au milieu. Le pattern sûr est :

  • lib/ = utilitaires purs (format, helpers, hooks Supabase) sans composants JSX
  • app/ = composants UI et logique de pages
  • Le layout importe uniquement depuis app/ ou ses sous-dossiers

2 router non importé dans /profil

Erreur au clic sur "Refaire la visite guidée" dans /profil :

Unhandled Runtime Error
ReferenceError: router is not defined

  Source
  app\profil\page.js (251:19) @ router
    249 |   onClick={() => {
    250 |     resetOnboarding();
  > 251 |     router.push("/accueil");
                  ^
    252 |   }}

Cause : j'ai utilisé router.push() dans le handler du bouton, mais je n'ai jamais importé useRouter ni initialisé la variable router dans cette page. Le npm run build ne détecte pas ce genre d'erreur en JavaScript pur (TypeScript l'aurait attrapée).

Correction : utiliser window.location.href qui ne nécessite aucun hook. Bonus : c'est en réalité préférable pour ce cas car ça force un full reload, ce qui permet au <OnboardingTour> de bien se remonter et de relire localStorage dans son useEffect.

  <Btn 
    variant="ghost" 
    icon="ti-map-2" 
    onClick={() => {
      resetOnboarding();
-     router.push("/accueil");          // ❌ router undefined
+     window.location.href = "/accueil"; // ✓ force reload + remount du Tour
    }}
  >
    Refaire la visite guidée
  </Btn>

Audit : j'ai vérifié toutes les pages avec router. sans useRouter, aucune autre occurrence. C'était bien isolé.

Leçon : avant chaque livraison, faire un npm run dev minimal et cliquer au moins sur les nouvelles fonctionnalités. Le npm run build n'attrape pas les ReferenceError côté browser car JS n'a pas de type checking statique.

À retenir pour les prochaines versions

Deux nouveaux réflexes à ajouter à ma checklist (qui en compte maintenant 6) :

  1. Composants client dans app/ : si un composant client doit être référencé par le layout root, le garder dans app/ sans crossover vers lib/. lib/ = utilitaires purs sans JSX. 
    // ❌ Mauvais (crossover qui plante webpack)
// app/layout.js → import "../lib/foo" → import "../app/bar"

// ✓ Bon (tout côté app/)
// app/layout.js → import "./foo" → import "./bar"
  2. Tester en dev avant livraison : npm run build ne suffit pas. JS n'a pas de typage statique, donc des erreurs comme router is not defined ne sont visibles qu'au runtime. À l'avenir je validerai avec un test rapide : 
    npm run dev
