Diagnostic

D'où vient la requête

Page app/patients/page.js ligne 131 (code livré en Alpha 0.38.0). Le but était de pré-calculer les compteurs "DI ouvertes" et "achats récents" par patient pour le composant <PatientPreview> (l'overlay qui apparaît au hover sur une ligne patient).

Pourquoi ça plante

Le code suppose que la table achats a une colonne patient_id. Faux.

Vérification du schéma actuel de la table :

create table achats (
  id, structure_id, etablissement_id,
  numero, fournisseur, motif,
  budget_estime, budget_reel, statut,
  date_souhaitee, date_commande, date_reception,
  demandeur_id, valideur_id, motif_refus, notes,
  created_at, updated_at,
  /* + colonnes 0.50 workflow double validation */
  seuil_double_validation, second_valideur_id, 
  date_second_validation, workflow_etape
);  -- ❌ AUCUN patient_id

C'est cohérent métier : un achat dans Aveho est rattaché à un établissement (besoin global de l'établissement), pas à un patient spécifique. Les achats individualisés au patient s'appelleraient des commandes nominatives, ce qui n'existe pas dans la 0.52.

Pourquoi le bug a survécu 14 versions

  • La requête était dans un Promise.all([...]) avec un .then() qui itérait sur achResp.data
  • Quand Supabase renvoie 400, le SDK retourne { data: null, error: {...} }
  • (achResp.data || []).forEach(...) itère sur tableau vide → pas d'erreur JS
  • L'erreur 400 apparaissait uniquement dans la console, jamais dans l'UI
  • Le compteur "X achats" affichait toujours 0 dans le preview hover, ce qui pouvait paraître normal ("ce patient n'a pas eu d'achats récents") → personne n'a tilté

Correction

Retrait pur et simple de la requête achats. Le compteur n'aurait jamais marché de toute façon vu le modèle de données. Le preview hover reste utile pour nbDI qui lui fonctionne correctement.

Diff dans app/patients/page.js :

// AVANT
Promise.all([
  supabase.from("interventions").select("patient_id, statut")...,
  supabase.from("achats").select("patient_id, statut")...,  // ❌
]).then(([diResp, achResp]) => {
  // ... itération sur diResp + achResp
});

// APRÈS
supabase.from("interventions")
  .select("patient_id, statut")
  .eq("etablissement_id", auth.etabId)
  .not("statut", "in", "(\"Clôturée\",\"Refusée\")")
  .then((diResp) => {
    const stats = {};
    (diResp.data || []).forEach((d) => {
      if (!d.patient_id) return;
      if (!stats[d.patient_id]) stats[d.patient_id] = { nbDI: 0 };
      stats[d.patient_id].nbDI++;
    });
    setPatStats(stats);
  });

nbAchats retiré du calcul mais le composant PatientPreview reste avec nbAchats: patStats[r.id]?.nbAchats || 0 (toujours 0) — c'est défensif et permettra de réactiver le compteur si un jour achats reçoit une colonne patient_id.

Audit de bugs similaires

J'ai écrit un script qui inspecte toutes les requêtes Supabase .from('tableName').select('col1, col2, ...') sur les tables connues (achats, annonces) et vérifie chaque colonne contre le schéma SQL.

Résultat : aucun autre bug similaire sur ces 2 tables. La seule requête fautive était celle-ci.

Audit étendu aux autres tables possible si un autre 400 apparaît.

Apprentissage / 16ᵉ réflexe

Bug de catégorie "silencieux" qui a survécu 14 versions car :

  1. Pas de visibilité métier (un compteur à 0 n'alerte personne)
  2. Aucune erreur JS levée (data null géré par || [])
  3. Visible uniquement dans la console Network, jamais dans l'UI

16ᵉ réflexe à ajouter à ma checklist :

"Lors de chaque nouvelle requête Supabase, grep `create table` pour vérifier QUE TOUTES LES COLONNES dans le `select(...)` existent. Pas seulement le nom de la table — c'est facile d'inventer un `patient_id` qui n'existe pas."

Le réflexe 2 (vérif schéma) existait déjà mais s'appliquait surtout aux noms de tables et aux colonnes des INSERT/UPDATE. À étendre aux colonnes des SELECT.
