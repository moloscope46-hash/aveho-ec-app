1. Résumé exécutif

L'Alpha 0.1 d'Aveho — Espace Collectivité est la première version déployée et utilisable du produit. Elle pose les fondations métier et techniques de la suite : multi-établissements, sélecteur d'établissement permanent, plan/arborescence avec lits et patients, matériel avec traçabilité, stock multi-dépôt, transferts inter-dépôts, demandes d'intervention, et gestion des utilisateurs avec invitations par email.

Cette version est hébergée chez Vercel (HTTPS, CDN global), s'appuie sur Supabase (Postgres + Auth + Edge Functions) et envoie ses emails de bienvenue via Resend. Elle est installable en PWA sur mobile et PC.

2. Périmètre fonctionnel

2.1 Hiérarchie organisationnelle

Le modèle suit la réalité d'une collectivité de santé :

Collectivité (structure propriétaire, avec SIRET / FINESS juridique)
   └── Établissement(s) (Hôpital, EHPAD, Foyer… avec FINESS géographique)
          └── Bâtiment(s)
                └── Étage(s)
                      └── Service(s)
                            └── Chambre(s)
                                  └── Lit(s) → rattaché à un patient

6. Authentification & droits

6.1 Modes de connexion

  • Email + mot de passe (provider Email activé dans Supabase)
  • Magic link par email (Supabase Auth + Resend)
  • SSO / carte CPS : UX en place, pas encore branchés (cf. limitations)

6.2 Modèle de droits

Un utilisateur est rattaché à :

  • Une collectivité (table membres_structure) → définit son périmètre haut-niveau
  • Un ou plusieurs établissements (table membres_etablissements) → filtre du contenu
  • Optionnellement un ou plusieurs services (table membres_services) → granularité fine future
  • Un rôle avec permissions JSON personnalisables (table roles)

Le rôle par défaut "Lecture seule" / "Administrateur" / "Cadre de santé" est livré. RLS active au niveau structure_id.

7. Système d'emails

Flux d'invitation utilisateur

  1. Un admin invite un email depuis /utilisateurs → onglet Invitations
  2. L'app insert dans la table invitations + appelle l'Edge Function invite-user
  3. La fonction tente auth.admin.inviteUserByEmail :
    • Si l'email n'existe pas : un lien d'activation est généré → mail "Bienvenue sur votre Espace Collectivité Aveho"
    • Si l'email existe déjà : bascule sur auth.admin.generateLink(magiclink) → mail "Votre lien de connexion Aveho"
  4. Le mail (template HTML aux couleurs Aveho) est envoyé via Resend
  5. Le destinataire clique sur le bouton → arrive directement connecté sur /accueil

7.1 Contenu du mail

  • Bandeau dégradé navy → teal avec logo Aveho
  • Nom du destinataire + nom de la collectivité
  • Carte "rôle" + "établissements rattachés" en pastilles 🏥
  • Bouton "Activer mon compte" pointant vers l'action_link Supabase
  • Bloc d'invitation à installer la PWA (Android / iPhone / PC)
  • Pied réglementaire (HDS, RGPD)

7.2 Configuration Resend

8. PWA & responsive

8.1 Progressive Web App

  • Manifest : /manifest.json (nom, icônes, couleurs, mode standalone)
  • Service worker : /sw.js, non-intrusif (n'intercepte que les ressources statiques)
  • Icônes : 192px, 512px, maskable 192/512, apple-touch-icon — fond navy + croix médicale teal + "aveho"
  • Composant d'installation : InstallPWA.js — détecte mobile/PC/iOS et propose le bon parcours
  • Installable en HTTPS uniquement (Vercel ✓, localhost ✗)

8.2 Responsive mobile

  • Tableaux à scroll horizontal au lieu d'écraser les colonnes (.panel{overflow-x:auto} + table{min-width:560px})
  • KPIs : 4 cols sur desktop, 2 cols sur mobile, 1 col sur très petit écran
  • Modales en bottom-sheet sur mobile (animation depuis le bas, plein écran)
  • Filtres et toolbars empilés en pleine largeur
  • Padding réduit (18px 12px au lieu de 30px 24px)

11. Limitations connues — Alpha 0.1

Ces points sont connus et assumés dans cette version, pas des bugs. Ils font partie du périmètre prévu pour les versions suivantes.

LimitationImpactSolution prévue
RLS par établissement/service non verrouillée en baseFiltrage côté app, pas étanche en cas d'accès direct à la basePolitiques RLS fines par etablissement_id + role
Décrément du stock à la réception non automatiqueLes transferts tracent le mouvement mais le stock doit être ajusté à la mainFonction SQL trigger à la transition statut "Reçu"
SSO / Carte CPS pas branchésUX en place, non fonctionnelsIntégration ProSantéConnect + IDPro Santé (contrats externes)
Boutons d'écriture non masqués selon le rôleLes permissions sont définies mais pas appliquées dans l'UIHelper can(role, action) sur chaque bouton
Édition des chambres/services depuis l'UILa page "Mon établissement" affiche le plan mais ne permet pas de créer/modifier — SQL nécessaireMode édition sur le plan
Resend limité à l'email du compteEn mode test, on n'envoie qu'à l'email d'inscription ResendVérifier un domaine pro chez Resend
PWA non installable en local (HTTP)Contrainte navigateur, non contournableTester sur l'URL Vercel HTTPS

12. Roadmap version suivante (Alpha 0.2)

  1. Édition de la hiérarchie depuis l'UI : créer/modifier bâtiments, étages, services, chambres, lits sans passer par SQL
  2. Refonte visuelle des pop-ups : uniformisation du style, animations, validation inline
  3. Cohérence visuelle inter-pages : système de design unifié (boutons, badges, en-têtes, icônes par type d'entité)
  4. RLS étanche par établissement : politiques fines + tests d'accès
  5. Application des droits de rôle : masquage des boutons d'écriture / suppression selon les permissions
  6. Décrément automatique du stock à la réception d'un transfert (trigger SQL)
  7. Commentaires détaillés dans tout le code (commencé sur patients/page.js)
  8. Domaine email pro vérifié chez Resend (envoi depuis bienvenue@aveho.fr par exemple)
  9. Notification in-app (cloche) pour les transferts validés, DI assignées, etc.
  10. Mode hors-ligne PWA : cache des données critiques pour consulter sans réseau
