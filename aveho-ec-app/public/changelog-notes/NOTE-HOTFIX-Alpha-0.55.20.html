👆 Fix 2 — Profil : Empreinte + Facial séparées

Avant : Une seule section repliable "Connexion par empreinte" qui contenait les 2 méthodes mélangées.

Après : 2 sections repliables distinctes :

  • 🔵 Connexion par empreinte digitale — icône bleue · uniquement la ligne empreinte + liste des credentials de type empreinte
  • 🟣 Connexion par détection faciale — icône violette · uniquement la ligne face + liste des credentials de type face

Comment

Ajout d'une prop methodFilter sur BiometricSection :

<CollapsibleSection title="Connexion par empreinte digitale" icon="ti-fingerprint" iconColor="#185FA5">
  <BiometricSection auth={auth} methodFilter="empreinte" />
</CollapsibleSection>

<CollapsibleSection title="Connexion par détection faciale" icon="ti-face-id" iconColor="#7a6fb0">
  <BiometricSection auth={auth} methodFilter="face" />
</CollapsibleSection>

Quand methodFilter est défini, le composant n'affiche que la MethodRow correspondante et filtre la liste des credentials par auth_method.

⚠ Fix 3 — Warning 'Banner not shown'

Chrome loggait : Banner not shown: beforeinstallpromptevent.preventDefault() called. The page must call beforeinstallpromptevent.prompt() to show the banner.

C'est un warning informatif (pas une erreur) qui signale qu'on a bloqué le banner natif (via preventDefault()) sans appeler .prompt() immédiatement. Notre flow appelle bien .prompt() au click du bouton "Installer", mais Chrome ne le sait pas avant.

Fix

On ne fait plus preventDefault si l'install a déjà été dismissed "forever" — dans ce cas on laisse Chrome gérer nativement, et le warning disparaît :

const onPrompt = (e) => {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    if (raw && JSON.parse(raw).dismissed === "forever") return;
  } catch {}
  e.preventDefault();
  setInstallPrompt(e);
};

Pour les utilisateurs qui voient le banner pour la 1ère fois, le warning peut encore apparaître brièvement — c'est inoffensif et attendu (Chrome documente ce comportement comme normal pour les sites avec banner custom).

⚡ Fix 4 — Forced reflow 106ms

Chrome dev tools : [Violation] Forced reflow while executing JavaScript took 106ms

La cause : dans la modale highlight changelog, on faisait setTimeout(50) puis querySelectorAll + scrollIntoView, ce qui forçait le navigateur à recalculer le layout 2x.

Fix

// Avant (force reflow)
setTimeout(() => {
  container.querySelectorAll("mark.active").forEach((el) => el.classList.remove("active"));
  target.classList.add("active");
  target.scrollIntoView({ behavior: "smooth", block: "center" });
}, 50);

// Après (RAF synchronisé)
requestAnimationFrame(() => {
  container.querySelectorAll("mark.active").forEach((el) => el.classList.remove("active"));
  target.classList.add("active");
  requestAnimationFrame(() => {
    target.scrollIntoView({ behavior: "smooth", block: "center" });
  });
});

Le 1er RAF applique les classes, le 2e RAF (frame suivant) déclenche le scroll avec le layout déjà calculé. Plus de violation.
